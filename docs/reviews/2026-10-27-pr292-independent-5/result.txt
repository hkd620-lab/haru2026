## A 반영 확인: 오류 진단 코드 — **해소**

```ts
if (typeof code === 'string' && known.has(code)) return code;
for (const candidate of [code, value?.status, value?.statusCode]) {
  if (... /^(4\d\d|5\d\d)$/.test(String(candidate))) return `http_${candidate}`;
}
return fallback;
```

- 공용 `getAiUsageErrorCode`를 주입하지 않은 판단이 옳습니다.
  - 공용 함수는 `error.message.slice(0, 120)`로 fallback합니다.
  - OpenAI 어댑터 오류는 메시지에 purpose와 설정 키 이름을 담습니다. 공급자 오류 메시지에는 입력 일부가 섞일 가능성도 있습니다.
  - 실행4의 제안을 그대로 따랐다면 원문이 노출될 수 있었습니다. 허용목록 방식이 더 안전합니다.
- 실제 SDK 오류 모양과도 맞습니다.
  - Gemini `GoogleGenerativeAIFetchError`는 숫자 `status`를 가집니다. 따라서 `http_429`·`http_503`이 됩니다.
  - OpenAI `APIError`는 `code`가 `'rate_limit_exceeded'` 같은 미허용 문자열입니다. 이 값은 허용목록과 정규식을 모두 통과하지 못합니다. 그다음 `status` 429가 잡혀 `http_429`가 됩니다. 순서가 올바릅니다.
- 요청 단계 회귀가 없습니다.
  - 입력 거부와 quota 거부는 `HttpsError.code`가 `'invalid-argument'`·`'resource-exhausted'`입니다. 둘 다 허용목록에 있어 기존과 같은 값이 남습니다.
- 안전성
  - `null`과 원시값 throw는 `?.`로 안전하게 처리됩니다.
  - 미지 문자열 코드는 시험 `private-user-content`로 처리 범주에 떨어짐이 확인됩니다.

## B 반영 확인: 단계 이후 요청 실패 — **해소**

```ts
if (hasStageFailure && error === lastStageError) return;
const outcome = stagesStarted === 0 ? 'rejected' : 'processing_error';
```

경로별로 추적한 결과입니다.

| 경로 | 단계 행 | 요청 행 | quota 환원 |
|---|---|---|---|
| 본문 단계 실패 E → 외부 catch `rejected(E)` | 1 (실패) | 0 (동일 객체라 생략) | 1회 |
| 통계 실패 E_s 흡수 → 이후 W throw | 3 | 1 (W≠E_s) | 1회 |
| 한마디 실패 E_c 흡수 → 이후 W throw | 3 | 1 | 1회 |
| 전 단계 성공 → paid log의 `logger.warn` throw | 3 | 1 | 1회 |
| 단계 진입 전 거부 (입력/quota) | 0 | 1 (`rejected`) | 기존과 동일 |

- 요청 행에 `modelInvoked:false`를 쓴 결정은 실행4의 제안 (a)인 `true`보다 낫습니다.
  - `modelInvoked` 행 수가 그대로 논리 호출 수가 됩니다. 이중 계산이 없습니다.
  - 시험이 `filter(modelInvoked).length === 3`으로 이를 고정합니다.
- 단계는 순차 실행이므로 `lastStageError`에 경쟁 조건이 없습니다.
- `log`는 모든 예외를 삼킵니다. 따라서 `finally`가 원래 오류를 덮지 않는 점도 유지됩니다.
- 실패 후 성공 응답이 실패로 바뀌는 동작은 이번 변경이 아닙니다. 기존 catch 구조 그대로이며 판정 범위 밖입니다.

## 병합 전 문서 보완 (코드 재검토 불요)

### C. 요청 행의 `purpose`가 `'sayuPolish'`에서 `'polishContent'`로 바뀌었으나 반영내역에 없음

```diff
-        ...base, purpose: 'sayuPolish', stage: 'request', model: null,
+        ...base, purpose: 'polishContent', stage: 'request', model: null,
```

- 의미상으로는 개선입니다. 이전 값은 요청 단위 행을 본문 모델 단계 purpose로 잘못 분류했습니다. purpose별 집계에서 오해를 낳을 여지가 있었습니다.
- 다만 이 변경은 A·B 범위 밖입니다. 반영내역과 커밋 메시지에도 적혀 있지 않습니다. 사용자 지시에 "CC 통계·합본과 분리"가 있으므로 purpose 값 변경은 명시해 두어야 합니다.
- 처리 방법
  - PR 본문에 요청 행의 의미를 한 줄로 추가합니다. 내용은 "요청 행 purpose=`polishContent`, stage=`request`, modelInvoked=false"입니다.
  - 가능하면 요청 행 purpose를 고정하는 단언 1개를 시험에 추가합니다.
- **조건부 차단:** `purpose` 필드는 이 PR에서 새로 추가된 것으로 보입니다. `AiUsageLogInput` 말미의 optional 필드 묶음이 그 근거입니다. 만약 이미 운영에 배포되어 `purpose='sayuPolish'` 요청 행이 쌓여 있다면 이 항목은 차단 사항이 됩니다. 이 경우 집계 소비처를 확인해야 합니다.

## 비차단 참고
- **클라이언트 측 시간 초과 구분:** OpenAI의 `APIConnectionTimeoutError`와 Gemini의 abort 오류에는 `code`·`status`가 없습니다. 그래서 `provider_error`로 떨어집니다. 그러나 `polishContent`는 timeout 옵션을 넘기지 않으므로 현재는 해당 경로가 없습니다. 다른 기능에 재사용할 때 `error.name` 허용목록(`AbortError` 등)을 검토하면 됩니다.
- **사소한 사항:**
  - `known` Set이 호출마다 새로 생성됩니다. 모듈 상수로 올려도 됩니다.
  - 시험 이름 `http_429`가 중복됩니다. 표시 문제일 뿐입니다.
- **빌드:**
  - `index.ts`에 `getAiUsageErrorCode` import가 남아 있어도 빌드는 성공했습니다. "기존 import 유지" 원칙에도 부합합니다.
  - `functions/lib` 차이를 커밋에서 제외했으므로, 배포 전에 predeploy build가 설정되어 있는지 실측해야 합니다.
- **작업트리:** 세션 시작 시 `functions/node_modules`가 untracked로 보였습니다. 커밋에 섞이지 않도록 주의하십시오.
