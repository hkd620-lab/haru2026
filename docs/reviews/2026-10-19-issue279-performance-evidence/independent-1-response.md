# #279 장문 추천 성능 계측·범위 검토 (독립 검토 1회차)

## 근거: 주장과 코드·데이터의 정합성
- **소스 대조**
  - `SayuPage.tsx:5420-5453`의 `assistantContent` IIFE는 `isOpen`을 보지 않습니다. `firestoreId`로 record를 찾고, 있으면 `getAssistantRecommendations`를 호출합니다.
  - `handleModalClose`(`:2627`)는 상태를 비워 record를 못 찾게 하므로 계산이 0회가 됩니다.
  - 구조화 분기(`:2377`)는 `isOpen:false`만 바꾸고 이전 `firestoreId`·`formatKey`를 남깁니다. 보고서의 "숨김 상태 재계산 경로" 설명은 코드와 맞습니다.
  - `assistantRecommendations.ts:227-237`의 `matchesKeyword`는 호출마다 `RegExp`를 만들어 전체 source를 검색합니다. 151개 정규식이 모두 전체 문자열을 도는 구조라서, 비용이 길이에 선형으로 늘고 키워드 위치와 무관하다는 해석과 일치합니다.
  - `RecordPage.tsx:686-687`은 저장 후 1회 호출입니다. 보고서 설명과 맞습니다.
- **원시 데이터**
  - `chrome-results.json`을 앞부분까지 읽었습니다. 표의 p50/p95/길이/ids가 원시 표본과 일치합니다(예: 100,012자 p50 319.4, p95 339.7).
  - 길이에 거의 선형으로 늘어나고(1k→1M), 무키워드(308)와 키워드 있음(306~319)이 같은 수준입니다. 이는 검색 횟수가 지배한다는 주장과 맞습니다.
  - AI 본문 사례의 결합 길이 30,053은 원문 10,012 + AI 5,018 + 원본 10,012 + 구분자와 대략 맞습니다. AI 경로가 실제로 들어갔다고 볼 수 있습니다.
  - 읽지 못한 부분: `node-results.json`과 `chrome-results.json`의 뒷부분(캐시 진단, 렌더 진단)은 읽지 못했습니다. `recommendation-tests.log`도 읽지 않았습니다. 표의 해당 수치는 이 검토에서 원시 데이터와 대조하지 못했습니다.
- **벤치 방법**
  - 예열 3회, 표본 20회, `ceil(0.95n)-1` p95, 길이 실측 보고, `near` 88,481자 명시, 계측(Proxy)과 비계측 분리는 적절합니다.
  - n=20의 p95는 사실상 최댓값 근처이고, 보고서가 SLO 확정을 부인하므로 수용합니다.
  - 합성 입력(반복 문장)은 정규식 비용을 대표하지만 실제 한국어 사용자 글의 분포는 아닙니다. 보고서가 한계로 적었습니다.
- **오해 방지**
  - "메모이제이션만으로 장문 성능 전체를 완료 처리하면 안 됨"이 결론, 1단계, 순서 절에 반복 명시되어 있습니다. #279의 최초 장문 비용 항목은 계속 미완료로 남긴다고 했습니다. 이 점은 양호합니다.
  - 앱 소스·정책 변경은 없고, 진단 안의 useMemo는 "반사실 비교"로 표시했습니다. `git status` 기준 미추적 문서·진단 파일만 있습니다.

## 비차단 의견
- Chrome이 Node보다 약 2배 느린 것(같은 V8 계열)은 설명되지 않았습니다. `near` 표본은 약 187ms와 약 280ms로 갈립니다. 코어 배정이나 전원 상태 같은 환경 영향일 수 있으니 한계 절에 한 줄 추가하길 권합니다. Chrome 절댓값은 상대 비교용으로만 쓰는 것이 안전합니다.
- 렌더 진단의 baseline 과 memo 모드는 컴포넌트가 달라 순수한 대조는 아니지만, 호출 횟수 비교라는 목적에는 충분합니다.
- 실제 앱에서는 `handleModalClose`가 `getRecords`로 records를 다시 불러와 record 참조가 바뀝니다. 참조 기반 memo의 재계산 빈도는 구현 시 전용 시험으로 확인하세요. 보고서의 record 복제 한계 절과 같은 맥락입니다.
- 2단계 사전검사는 "후보, 미측정"으로 정직하게 표기되어 있습니다. 구현 전에 반환 배열이 같은지 기준 구현과 비교하는 시험이 필요합니다.
