### 중간

**M1. 확정 값이 있는 상태에서 '다시 시도'하면 8초 시간 제한이 꺼집니다. 새 리스너의 캐시 스냅샷이 확정 값을 덮어써 실패 대신 '0편'이 보일 수 있습니다.**
위치: `frontend/src/app/records/monthProgressController.ts:73-75`, `:83-90`

```ts
timer = deps.setTimer(() => {
  if (mine !== token || view.hasConfirmed) return;   // retry(keepValues) 뒤에는 hasConfirmed=true 라 항상 그냥 return
...
docs = snapshot.docs.map(...);                        // 새 리스너의 첫 캐시 스냅샷도 docs 를 그대로 교체
} else if (view.hasConfirmed) {
  recompute({ stale: true, status: 'ready' });        // 이번 open 에서는 확정을 한 번도 못 받았는데 '오프라인 유지'로 처리
```

재현은 sim.mjs로 확인했습니다.
1. 확정 스냅샷 1건을 받은 뒤 onError가 오고, '다시 시도'를 누릅니다.
2. 타이머가 울려도 상태는 `loading`에서 바뀌지 않습니다. 카드에는 "다시 확인하는 중이에요."가 계속 보이고 '다시 시도' 버튼도 없습니다.
3. 이어서 새 리스너가 `fromCache: true`인 빈 스냅샷을 줍니다. 오프라인이고 memoryLocalCache의 eager GC 때문에 캐시가 비어 있는 경우이며, 실제 SDK 동작은 '추정'입니다. 그러면 결과가 `status:'ready', stale:true, count:0`이 됩니다.
4. 카드에는 "이번 달 아직 남긴 기록이 없어요." 문구와 "연결을 확인하고 있어요." 안내가 같이 나옵니다.

이는 설계 3절의 "조회 실패는 0건과 구분한다"와 3.1의 "8초 타이머를 재구독 때마다 시작한다"를 어깁니다. 같은 리스너가 오프라인으로 바뀌는 일반적인 경우는 캐시에 같은 문서가 남아 있어서 문제가 없습니다. 이 버그는 재시도 경로에서만 생깁니다.

수정 제안 스케치:
```ts
let confirmedThisOpen = false;            // open() 에서 false 로
let confirmedDocs: Array<Record<string, any>> = [];
// timer:   if (mine !== token || confirmedThisOpen) return; emit({ ...view, status: 'error' });
// onNext:  if (confirmed) { confirmedThisOpen = true; docs = confirmedDocs = next; ... }
//          else if (confirmedThisOpen) { docs = next; stale... }          // 같은 리스너의 오프라인
//          else if (view.hasConfirmed) { /* 재시도 중 캐시: docs 유지(confirmedDocs) */ }
//          else { docs = next; recompute(); }
```
테스트도 두 개 추가해야 합니다. (a) 확정 뒤 재시도한 다음 타이머가 울리면 `error`가 되는지, (b) 재시도 뒤 빈 `fromCache` 스냅샷이 와도 count가 유지되는지.

### 낮음

**L1. 쓰기 대기 중인 serverTimestamp가 null이 되어, 막 저장한 기록이 같은 날 정렬에서 맨 뒤로 밀립니다.**
위치: `useMonthRecordProgress.ts:164`, `monthProgressController.ts:83`, `monthProgress.ts:307-323`

`d.data()`의 기본값이 `serverTimestamps:'none'`이라서 대기 중인 `updatedAt`이 `null`이 되고, 정규화하면 0이 됩니다. sim.mjs로 확인했습니다. 오늘 기록이 3건 있는 상태에서 4번째를 저장하면 서버가 받을 때까지 그 기록이 최근 3건에서 빠집니다. serverTimestamp는 RecordPage, SayuPage 쪽 저장 경로가 씁니다. 홈에 머무는 동안 그 경로로 저장되는 일은 드물어서 영향이 작습니다.
제안: `snapshot.docs.map((d) => ({ ...d.data({ serverTimestamps: 'estimate' }), id: d.id }))`로 바꾸고, `SnapshotLike`의 `data` 시그니처에 옵션 인자를 받게 합니다.

**L2. 훅의 `auth.currentUser?.uid !== uid` 확인이 effect 의존값에 없습니다.**
위치: `useMonthRecordProgress.ts:182`

두 값이 어긋나면 idle을 반환하고 끝납니다. effect가 `[uid, enabled]`에만 반응하므로 다시 실행되지 않고, 카드는 시간 제한 없는 스켈레톤으로 남습니다. AuthContext는 `setUser(mapUser(firebaseUser))`로 두 값을 맞춰 주고, 706·736행에도 같은 가드가 있어서 실제로 일어날 가능성은 낮습니다('추정'). 걱정되면 이 경우에도 오류 상태를 내보내면 됩니다.

**L3. 다시 시도가 지난달로 열릴 수 있습니다.**
위치: `monthProgressController.ts:523-526`

월이 바뀐 직후, refreshToday가 돌기 전에 오류 상태에서 다시 시도를 누르면 `view.monthKey`(지난달)로 다시 엽니다. 이어지는 스냅샷이나 1분 간격 갱신에서 바로 새 달로 다시 열리므로 M 읽기가 한 번 더 생기는 정도입니다. 제안: `retry`에서 `monthKeyOf(deps.todayKey())`를 사용합니다.

**L4. `aria-live`가 새로 마운트되는 요소에 붙어 있습니다.**
위치: `MonthProgressCard.tsx:98`, `:116`

스켈레톤에서 내용으로, 0건에서 1건 이상으로 바뀔 때마다 분기가 달라져 `aria-live` 요소가 새로 생깁니다. 새로 생긴 live region은 대부분의 스크린리더가 읽지 않습니다. 같은 자리에 늘 있는 live 요소 하나에서 숫자 문구만 바꾸는 편이 안전합니다. 스켈레톤의 `role="status"` + `aria-label`은 텍스트 노드가 없어서 안내되지 않을 수 있습니다('추정').

**L5. 제목을 20자로 자를 때 말줄임표가 없습니다.**
위치: `monthProgress.ts:344-348`

잘린 제목이 원래 그런 제목처럼 보입니다. 잘렸을 때 `…`를 붙이기를 제안합니다(문구 결정 사항).

**L6. 0이 채워지지 않은 날짜는 미래 날짜로 판정되어 빠집니다.**
`'2026-11-6'`처럼 0이 없는 날짜 문자열은 서버 범위에는 들어오지만, `date > todayKey`(`'2026-11-6' > '2026-11-06'`) 조건 때문에 미래로 보고 뺍니다. 저장 원칙상 YYYY-MM-DD만 허용되므로 기록용으로만 남깁니다.

### 문제없다고 확인한 영역
- **11종 집계**: `getCardFormat`이 `STATS_MERGE_RECORD_FORMATS`와 `recordHasFormat`(`isAssistantRecord` 포함)을 그대로 씁니다. `result_ai_chat`·`growthTimeline`·`ai_log`, 가계부·보조장부·주식·성장기록·배뇨일지, 영문 `diary`, `formats`가 없는 옛 문서는 모두 제외됩니다.
- **편 수**: 문서 id 기준이고, 형식이 여럿인 문서도 1편으로 셉니다. 중복 id는 Set으로 거릅니다.
- **기간**: 월초부터 오늘까지만 셉니다. 시각이 붙은 문자열은 `slice(0,10)`으로 세고, Timestamp 타입 date는 제외합니다. 12월 다음 달 계산도 맞습니다.
- **Firestore 쿼리**: 같은 필드 `date`에 `>=`/`<` 범위와 `orderBy`만 걸어서 단일 필드 자동 색인으로 동작합니다. 복합 색인은 필요 없고, 기존 `getRecordsInRange`와 같은 형태입니다.
- **서버 확정 판정**: `!metadata.fromCache`를 확정으로 보는 것과, `includeMetadataChanges: true`로 오프라인 전환 시 fromCache 스냅샷을 받는 것은 SDK 의미와 맞습니다. 확정 뒤 `hasPendingWrites` 스냅샷이 와도 스켈레톤으로 돌아가지 않습니다.
- **구독 수명**: 구독은 항상 하나이고, token으로 이전 구독의 늦은 콜백을 버립니다. 오류 뒤 리스너를 종료 처리하고, 재시도 전에 기존 구독을 해제합니다. 언마운트하면 interval·visibilitychange·controller를 정리합니다. StrictMode에서는 effect마다 controller를 새로 만들고 `disposed`로 막으므로 안전합니다(개발 모드에서만 M을 두 번 읽음). 의존값은 `[uid, enabled]`라 1분마다 다시 구독하지 않습니다. 같은 달 안에서 자정을 넘기면 재구독 없이 다시 계산하고, 달이 바뀌면 새로 열면서 지난달 값을 버립니다.
