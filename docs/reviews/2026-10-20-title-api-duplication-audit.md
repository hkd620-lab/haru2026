## 확인 결과

### 1. 유효한 AI 제목을 건너뛰지 않는다 — 주 개선 대상

[서버:4741](https://github.com/hkd620-lab/haru2026/blob/be7f9afe/functions/src/index.ts#L4741)는 `${prefix}_title`만 검사한다. [저장:4776](https://github.com/hkd620-lab/haru2026/blob/be7f9afe/functions/src/index.ts#L4776)은 `${prefix}_ai_title`이므로, 첫 실행이 성공해도 다음 실행에서 완료한 AI 제목을 인식하지 못한다. 운영 배포 소스와 실행 JS에도 같은 조건이 있다.

| 합성 조건 | 첫 실행 → 재실행 모델 호출 | 의미 |
|---|---|---|
| 제목 없음·본문 있음 | 1 → 1 | 첫 성공으로 AI 제목을 저장해도 다시 생성 |
| 유효한 AI 제목만 있음 | 1 → 1 | 이미 존재하는 AI 제목 재생성·덮어쓰기 |
| 유효한 사용자 제목 있음 | 0 → 0 | 사용자 제목 유지, 정상 대조군 |
| 숫자형 무효 사용자 제목 + 유효한 AI 제목 | 1 → 1 | 유효한 AI 제목이 있어도 다시 생성 |
| 무효 AI 제목만 있음 | 1 → 1 | 최초 보정은 필요하나 성공 후에도 재실행됨 |
| 본문 없음·AI 제목만 있음 | 0 → 0 | AI 제목만으로 본문을 만들지 않음 |

여기서 1은 기록 1개·형식 1개의 논리 모델 호출이다. SDK 내부 재시도·토큰·실청구액을 뜻하지 않는다. 실제 운영 사용 빈도·대상 기록 수·재실행 빈도는 조회하지 않아 월 절감액은 산정하지 않았다.

### 2. 중도 실패와 재시작도 완료 기록을 다시 처리한다

합성 기록 2개 중 첫 문서는 AI 제목 저장 성공, 두 번째 문서는 생성 후 저장 실패하도록 했다. 첫 시도는 모델 2회/문서 저장 1회, 재시작은 다시 모델 2회/저장 2회였다. 이미 저장된 첫 문서까지 재생성했다.

따라서 유효한 AI 제목 skip은 순차 재실행뿐 아니라 중도 실패 후 완료분을 보존하는 데에도 효과가 있다. 단, 생성 후 저장 자체가 실패한 문서의 재호출은 기존 AI 제목 skip만으로 없앨 수 없다. 생성 결과 임시 보존·작업 큐는 더 큰 별도 범위다.

### 3. 동시에 시작한 두 요청은 같은 기록을 중복 생성한다

동일한 초기 스냅샷을 읽은 두 요청을 겹치게 실행하니 모델 2회/저장 2회였다. 현재 핸들러에는 작업 claim/lease·트랜잭션 재확인·공통 잠금이 없다. AI 제목 skip만 추가해도 **저장 전 동시 실행**은 차단하지 못한다.

[SettingsPage:591](https://github.com/hkd620-lab/haru2026/blob/be7f9afe/frontend/src/app/pages/SettingsPage.tsx#L591)의 실행 중 상태와 [버튼:1278](https://github.com/hkd620-lab/haru2026/blob/be7f9afe/frontend/src/app/pages/SettingsPage.tsx#L1278)의 disabled는 한 화면의 조작 제어다. 여러 탭/독립 RPC 요청의 서버 중복 실행을 보장하지 않는다. 실제 사용자 중복 클릭을 관찰한 것은 아니다.

### 4. 방어가 필요한 입력 경계

- `formats: ['메모', '메모']`라는 합성 중복 목록에서는 같은 필드를 모델 2회 생성하고 count=2를 반환했지만 저장된 AI 제목 필드는 1개였다. 운영에 이런 목록이 존재하는지는 미확인이다. 형식/접두어 단위 중복 제거는 작은 방어 후보다.
- 사용자 제목 값이 문자열이 아닌 숫자면 `isValidTitle`의 `.trim()`에서 TypeError가 나며 해당 예외가 형식별 try 바깥이어서 작업 전체가 중단된다. 실제 레거시 데이터 존재는 미확인이다. 기존 사용자 값은 지우지 않고 문자열 여부를 먼저 판단하는 경계 검증이 필요하다.
- 인증 없음/개발자 아님은 조회·모델 호출 전에 차단됨을 모의 대조했다. 권한 범위 확대는 필요 없다.

## 영향 범위와 배포 차이

활성 웹 진입은 설정의 개발자 전용 수동 버튼이다. 일반 사용자의 상시 자동 호출로 확대 해석하지 않는다. 형식은 등록된 10종, 쿼리는 사용자 기록 최대 500문서이며 페이지네이션이 없다. 완전히 제목 없는 500문서×10형식이면 이론상 후보는 최대 5,000쌍이지만 순차 실행과 300초 제한 때문에 이를 실제 완료 호출 수로 계산하면 안 된다. 대상 수와 실행 빈도는 미확인이다.

운영 함수는 Google SDK 직접 호출이고 main은 `callAi(recordTitleBackfill)`로 전환돼 있다. 현재 설정상 공급자·모델은 둘 다 Gemini / `gemini-3.1-flash-lite`지만 호출 창구·Secret 연결 선언·형식 맵 생성 방식이 다르다. 추출 핸들러의 중복 동작은 세 버전에서 같았다. **나중에 현재 main으로 함수를 배포하면 이 선행 변경도 포함되므로, skip 수정만 배포된다고 표현해서는 안 된다.** 실제 구현·배포 단계에서 별도 diff와 게이트웨이 호환 검증이 필요하다.

AI 제목은 실제 표시 필드다. [목록:3198](https://github.com/hkd620-lab/haru2026/blob/be7f9afe/frontend/src/app/pages/SayuPage.tsx#L3198)은 사용자 제목을 우선하는 경로가 있고, [표시 헬퍼:4004](https://github.com/hkd620-lab/haru2026/blob/be7f9afe/frontend/src/app/pages/SayuPage.tsx#L4004)는 AI 제목을 우선한다. 따라서 생성 중복은 비용뿐 아니라 일부 화면의 표시 제목 변동으로 이어질 수 있다. 이번 점검은 UI 우선순위 통일을 개선 범위에 넣지 않는다. 사용자 제목 필드 삭제·덮어쓰기 없이 기존 값을 보존해야 한다.

## 권장 개선 범위 — 아직 구현하지 않음

**1차: 좁은 범위의 순차 재실행 방지부터.**

- `generateTitlesForAll`에서 유효한 사용자 제목 **또는 유효한 기존 AI 제목**이 있으면 호출 전에 skip.
- 같은 기존 `isValidTitle` 기준을 사용하되 비문자열 값을 안전하게 판정. 사용자 제목을 AI 제목으로 복사하거나 기존 값을 일괄 정리하지 않음.
- 한 요청 내 같은 형식/접두어는 한 번만 처리. 대상 데이터에 실제 중복이 있는지는 별도 확인 사항.
- count 응답 형태·권한·형식10종·모델·프롬프트·600자 입력/20자 후처리·저장 경로·리전 유지. 기존 UI와 공용 `extractTitle`은 수정하지 않음.
- 기존 AI 제목이 있으면 본문이 변경됐더라도 일괄 버튼은 보존하는 정책을 권장. 버튼 문구가 ‘제목 없는 기록 채우기’이기 때문이다. 자동 갱신·강제 재생성은 이번 범위에서 제외하고 별도 결정.

**2차: 동시 요청 방지는 별도 설계.**

실제 중복 실행 빈도 확인 후 사용자/기록/형식 단위의 서버 claim·lease와 완료 직전 재확인을 검토한다. 시간 만료·실패 복구·본문 변경을 다뤄야 하므로 기존 AI 제목 skip과 같은 완료 조건으로 묶지 않는다. 모델 호출을 Firestore 트랜잭션 콜백 안에 넣으면 트랜잭션 재시도 때문에 오히려 모델 호출이 반복될 수 있으므로 피한다. 새로운 저장 경로나 잠금 문서를 이번 점검에서 만들지 않았다.

**1차 구현 시 필요한 회귀 조건:** 최초 생성 후 재실행0회, 유효 사용자 제목0회/원값 보존, 유효 AI 제목0회/원값 보존, 무효·비문자열 값의 안전한 처리, 본문 없는 기록0회, 한 요청 중복 형식1회, 중도 실패 후 완료 문서0회, 인증/권한 거부0회. 동시 요청2회 가능성은 1차의 명시적 제한으로 남기고 2차에서 별도 검증한다. Functions 빌드·해당 시험·export diff·배포 소스 차이 및 독립 검토는 구현 때 수행한다.
