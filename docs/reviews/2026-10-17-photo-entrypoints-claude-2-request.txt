## 1. 병합 전 필수 수정 (결함)

### R1. 60MiB 합계 상한의 집계 오류: 정상 사진까지 전부 실패할 수 있음

`selectionBytes`는 모든 파일이 동시에 읽는 공용 카운터입니다. 그런데 실패하거나 취소된 파일의 바이트를 빼지 않습니다.

- **실제 동작**: 실제 스트림은 작은 조각(약 64KB) 단위로 여러 파일이 번갈아 읽힙니다.
  - 예를 들어 16MB 사진 4장(합계 64MB)을 고르면, 각 파일이 15MB쯤 읽힌 시점에 합계가 60MB를 넘습니다.
  - 그때 먼저 넘긴 파일이 실패합니다. 그 파일이 이미 읽은 바이트가 카운터에 남아 있어서, 나머지 파일도 다음 조각을 읽는 순간 모두 실패합니다.
  - 결과는 "3장 성공, 1장 실패"가 아니라 **0장 성공**일 수 있습니다. "나누어 추가해주세요"라는 안내와도 맞지 않습니다.
- **20MB 초과 사진도 같은 문제**: 실패하기 전까지 읽은 최대 20MB가 카운터에 남아 다른 정상 사진의 몫을 잡아먹습니다. 중간에 읽기 오류가 난 경우도 마찬가지입니다.
- **영향 범위**: 이 헬퍼는 PR #275의 새 기록 경로도 함께 씁니다. 그래서 이미 승인된 경로에도 같은 영향이 갑니다. 보조장부는 최대 10장이라, 50MP 이상 촬영 사진이 섞이면 현실적으로 일어날 수 있습니다.
- **시험이 놓친 이유**: 60MiB 시험은 파일당 조각이 1개이고 읽는 순서가 정해져 있어 이 경우를 재현하지 못합니다.
- **수정**
  - 실패 경로(20MB 초과, 합계 초과, catch) 모두에서 `selectionBytes -= totalBytes`로 해당 파일이 읽은 몫을 되돌립니다.
  - 여러 조각을 번갈아 읽는 시험을 추가합니다. 예: 16MB 4장을 1MB 조각으로 번갈아 읽으면 3장 이상 성공하는지 확인합니다.
  - 어느 파일이 실패하는지는 여전히 순서와 무관하게 정해질 수 있습니다. 안내 문구가 이를 감안하는지도 확인하세요.

**맞는 부분**
- `files.map(async ...)`는 첫 `await` 전까지 동기적으로 실행됩니다. 그래서 모든 `source.arrayBuffer()` 호출이 변경 이벤트 핸들러 안에서 즉시 시작됩니다. 비이미지 파일은 읽지 않고 걸러지며, 이 동작은 테스트로 검증됩니다.
- 헬퍼의 promise는 reject되지 않고 항상 `{ok}` 형태로 resolve됩니다. 핸들러가 중간에 빠져나가도 unhandled rejection이 생기지 않습니다.
- 기존에는 `throw fileError` 때문에 루프 전체가 중단됐습니다. 이제는 파일 단위 `continue`로 바뀌어, 이미 성공한 업로드가 결과에 반영됩니다. 테스트에서 `tracked`와 `images`가 일치하는 것도 확인됩니다.
- 0장 성공일 때 `return`해도 `finally`가 실행되므로 `setIsUploading(false)`와 input 초기화가 유지됩니다. 테스트로 확인됩니다.

**확인·수정이 필요한 부분**
1. **`lastModified` 소실 (회귀 가능성 높음)**: `new File([buffer], name, { type })`로 만들면 `lastModified`가 생성 시각(현재 시각)이 됩니다. `readOriginalImageMeta`가 EXIF가 없을 때 `file.lastModified`를 촬영 시각으로 대신 쓴다면, EXIF 없는 사진과 HEIC→JPEG 변환본의 날짜가 업로드 시각으로 바뀝니다. 원본의 `lastModified`를 읽지 않는 것이 이번 설계의 전제이므로, 대체값 로직을 제거하거나 "메타데이터 없음"으로 명시하는 처리가 필요합니다. 해당 함수의 사용처를 꼭 확인하세요.
2. **헬퍼 호출 이전의 원본 접근 여부**: diff에는 `files.length`, `slice`만 보입니다. 하지만 `handleImageUpload`에서 `startSelectedRecordPhotoReads` 호출 전 구간이나 `onChange` 상위에서 `file.size`, `file.name`, 미리보기 `URL.createObjectURL` 같은 접근이 없는지 전체 핸들러를 확인해야 합니다. 같은 문제를 가진 다른 업로드 진입점(다른 기록 형식, 프로필, 가계부 등)은 이번 범위 밖이라 여전히 취약합니다.
3. **죽은 분기**: HEIC 변환 catch의 `NotReadableError` 분기는 이제 메모리 버퍼만 다루므로 사실상 실행될 일이 없습니다. 테스트 이름("Android HEIC NotReadableError ... before calling the server")도 실제로는 헬퍼의 catch를 검증합니다. 해롭지는 않지만, 분기를 제거하거나 주석으로 의도를 밝히는 편이 낫습니다.
4. **겹치는 검사**: 루프 안의 20MB 검사와 형식 검사는 헬퍼와 중복이고, 형식 판정 기준도 미묘하게 다릅니다(헬퍼는 type의 heic/heif 정규식, 모달은 확장자 위주). 지금은 결과가 같지만, 한쪽만 수정되면 어긋날 수 있습니다.
5. **토스트 잔존**: 바깥 `catch`의 `toast.error`에는 `{ id: uploadNoticeId }`가 없습니다. 그래서 장수 초과 경고 토스트가 오류 토스트와 함께 남습니다(경미).

## 2. 메모리 위험 (주요 수정 사항)

- **동시 전량 적재**: 선택한 모든 파일을 한꺼번에 `ArrayBuffer`로 읽습니다. 20MB를 넘는 파일도 **전부 읽은 뒤에야** 거절됩니다. size를 읽을 수 없다는 제약상 불가피하지만, 대형 파일이 섞이면 순간 메모리가 크게 튑니다.
- **이중 보유와 해제 불가**: 반환값에 `buffer`와 `new File([buffer])`가 함께 담깁니다. Blob 생성 시 데이터가 복사되므로 파일당 약 2배를 차지합니다. 게다가 `selectedPhotoReads` 배열이 resolve된 promise, 곧 버퍼를 핸들러가 끝날 때까지 참조합니다. 이미 처리한 사진의 버퍼도 GC되지 않습니다. 최대 장수 × 20MB × 2에 압축 캔버스와 HEIC base64 문자열(UTF-16 이진 문자열 포함 수 배)까지 더하면, 저사양 Android Chrome에서 탭 강제 종료(OOM)가 날 수 있습니다.
- **권장 수정**:
  - 헬퍼는 메모리 기반 `File`(Blob)만 반환하고 `buffer`는 반환하지 않습니다. Chrome은 Blob 데이터를 JS 힙 밖 blob 저장소로 옮길 수 있습니다.
  - HEIC 경로는 메모리 기반 `file.arrayBuffer()`를 다시 호출합니다. 원본이 아니므로 ERR_UPLOAD_FILE_CHANGED 위험이 없습니다.
  - 처리가 끝난 항목은 배열 슬롯을 `undefined`로 비워 참조를 끊습니다.
  - HEIC base64 변환은 `String.fromCharCode` 누적 대신 `FileReader.readAsDataURL`처럼 중간 문자열이 적은 방식을 검토합니다(선택 사항).

## 3. 테스트

**좋은 점**: 원본의 `size`·`lastModified`·`slice` 접근을 getter가 던지는 예외로 막아 검증하는 방식이 이번 수정의 핵심 불변식을 잘 고정합니다. 부분 실패, 재시도, 20MiB 경계 테스트도 적절합니다.

**한계와 누락**

- 누락된 테스트:
  - `periodRow`(가계부 기간 입력) 경로
  - `readOriginalImageMeta`에 넘어가는 `lastModified` 값(위 회귀 검증용)

## 4. 운영 판정의 한계

- 근본 원인 가설은 이렇습니다. Chrome이 content URI 파일의 snapshot(size/mtime)을 처음 접근할 때 확정하고, 이후 읽기에서 provider 값이 달라지면 오류가 납니다. 이 가설로 보면 이번 수정은 **실패 창을 줄이는 것이지 없애는 것이 아닙니다**. 클라우드 전용 항목처럼 provider가 읽는 도중 내용을 실체화하는 경우에는 여전히 실패할 수 있고, 이때는 "기기에 다운로드" 안내로 넘어갑니다.

- 현재는 실패가 `console.error`로만 남아 현장 재발 여부를 판단할 수 없습니다. 실패 사유 범주(읽기 실패/용량/형식/업로드)별 카운트를 분석·로그로 수집하면 효과를 판정할 근거가 생깁니다. 개인정보가 포함되지 않도록 사유 코드만 남기세요.

## 2. 정확성 재확인

- **읽기 즉시 시작**: `map(async …)`는 첫 `await` 전까지 동기적으로 실행됩니다. 그래서 `stream().getReader()`와 첫 `read()`가 change 핸들러 안에서 모든 파일에 대해 바로 시작됩니다. 시험의 `started = [0, 1]`이 이를 확인합니다.
- **스트림 정리**: 초과 경로는 `cancel` 후 `finally`에서 `releaseLock`을 호출합니다. 오류 경로에서 이미 오류가 난 스트림의 `cancel`이 reject돼도 `.catch`로 흡수됩니다. `stream()` 자체가 예외를 던지면 `reader`가 `undefined`라 안전하게 지나갑니다. 순서와 예외 처리 모두 문제없습니다.
- **reject 없는 promise**: 바깥 `catch`로 핸들러가 중간에 빠져나가도 큐에 남은 promise는 reject하지 않습니다. 따라서 unhandled rejection이 생기지 않습니다.
- **제외된 파일**: 장수 제한을 넘은 파일은 `files.length`만 확인하고 읽지 않습니다. 맞는 처리입니다.

## 3. 남은 항목 (병합을 막지 않음, 후속 권장)

1. **불필요한 복사**: `chunks.push(new Uint8Array(value))`는 기본 reader가 돌려준 조각을 한 번 더 복사합니다. `value`를 그대로 넣으면 순간 메모리가 줄어듭니다. 그 뒤 `new File(chunks)`에서 또 복사되므로, 지금은 파일당 순간 최대 약 2~3배를 씁니다.
2. **동시 전량 읽기**: 모든 파일을 동시에 끝까지 읽는 구조는 그대로입니다. 최대 장수 × 최대 20MiB가 한꺼번에 올라갈 수 있습니다. 즉시 읽기를 시작해야 하는 설계상 감수할 부분이지만, 최대 장수가 크면 저사양 기기에서 확인이 필요합니다.
3. **실행되지 않는 분기**: HEIC 변환 catch의 `NotReadableError` 분기는 이제 메모리 File만 다루므로 사실상 실행될 일이 없습니다. 시험 이름 "Android HEIC NotReadableError…"도 실제로는 헬퍼를 검증합니다. 1차 지적이 그대로 남아 있습니다.
4. **시험 갱신 누락**: `does not read non-image selections` 시험은 아직 `arrayBuffer`를 막고 있습니다. `stream`이 없어서 우연히 같은 효과를 내고 있으니, `stream`이 예외를 던지도록 바꾸는 편이 의도에 맞습니다.
5. **중복 검사**: 루프 안의 20MB 검사와 형식 검사가 헬퍼와 겹칩니다. 바깥 `catch`의 토스트에는 `{ id: uploadNoticeId }`가 빠져 있습니다. 둘 다 경미합니다.
6. **취약한 시험 구조**: 소스 문자열을 잘라 vm에서 실행하는 방식이 남아 있습니다. EXIF 시험도 `import` 줄을 문자열로 치환합니다. 리팩터링에 약하므로 장기적으로 순수 함수로 분리하길 권합니다.

## 4. 운영 판정의 한계 (1차와 동일하게 유효)

## 1. 정확성과 회귀

**맞는 부분**
- **경로 분기**: HEIC는 기기에서 먼저 처리합니다. `compressImage`가 heic2any로 변환하고 800px로 압축합니다. 여기서 실패하면 서버 변환을 1회 시도하고, 받은 JPEG를 다시 압축합니다. HEIC가 아닌 파일은 실패해도 오류를 그대로 전파하고 서버를 호출하지 않습니다. 네 가지 경우 모두 순수 함수 시험으로 고정되어 있습니다.
- **대체 경로가 실제로 동작하는 이유**: `normalizeHeicToJpeg`는 heic2any가 실패하면 예외를 삼키고 원본을 돌려줍니다. Android Chrome은 HEIC를 `<img>`로 디코딩하지 못하므로, 그다음 `img.onerror`에서 reject가 일어나고 서버 대체 경로로 넘어갑니다. iOS 17 이상 Safari는 HEIC를 직접 디코딩하므로, heic2any가 실패해도 압축은 성공합니다. 어느 쪽이든 끝에서 막히지 않습니다.
- **JPEG·PNG 경로**: 바뀌지 않았습니다. iPhone은 보통 파일 선택 단계에서 JPEG로 바꿔 넘기므로(`isHeic=false`) 대부분 기존 경로를 그대로 탑니다.
- **PR #275 유지**: 즉시 스트림 읽기, 20MiB 상한, 0장 성공 차단, 부분 성공 보존이 그대로입니다. 서버 경로도 메모리 `File`만 다시 읽으므로 ERR_UPLOAD_FILE_CHANGED 위험이 다시 생기지 않습니다.
- **2차 검토 지적 반영**: 2차 검토가 "실행되지 않는 분기"로 지적한 `NotReadableError` 분기가 이번에 없어졌습니다.
- **정리 경로**: 변환은 Storage 업로드 전에 끝나므로, 변환이 실패해도 Storage에 남는 고아 객체가 없습니다. 실패 시 정리 로직은 바뀌지 않았습니다.

**경미한 점 (병합을 막지 않음)**
- 로컬 처리가 실패한 원인을 버리고 기록하지 않습니다. 그래서 운영에서 "로컬 성공률"이나 "서버 대체 비율"을 알 수 없습니다. 개인정보 없이 사유 코드만 남기는 계측을 권합니다. 1·2차 검토의 계측 권고와 같은 맥락입니다.
- 로컬 처리 중 `FILE_READER_ERROR`가 나고 서버 대체까지 실패하면, 사용자에게는 "HEIC 변환 실패"만 보입니다. 메모리 `File`에서는 생기기 어려운 경우라 영향은 작습니다.

## 2. 큰 HEIC의 자원 사용 (주요 운영 위험)

- **메모리가 늘어남**: 이전에는 기기가 base64 문자열만 만들었습니다. 이제는 기기에서 전체 해상도를 디코딩합니다.
  - 순간 최고 메모리 구성: libheif WASM 힙, RGBA 버퍼(12MP 기준 약 48MB), 전체 해상도 캔버스, 품질 0.9 전체 해상도 JPEG, DataURL 문자열, `Image`의 전체 해상도 재디코딩
  - 12MP에서도 수백 MB까지 갈 수 있습니다. S21의 4.5MB 사례는 성공했지만, 저사양 기기이거나 해상도가 아주 큰 HEIC는 다릅니다.
- **탭이 죽으면 대체 경로가 없음**: heic2any가 예외를 던지면 서버로 넘어갑니다. 하지만 탭이 메모리 부족으로 강제 종료되면 대체할 방법이 없고, 사진 업로드 전체가 끝나지 않습니다. 이전 서버 우선 방식에는 없던 실패 유형입니다.
- **여러 장일 때**: 처리는 한 장씩 순서대로라 동시에 디코딩하지는 않습니다. 다만 emscripten WASM 힙은 늘어난 뒤 줄지 않는 것이 일반적이고, PR #275 구조상 선택한 모든 원본의 메모리 `File`도 동시에 보유합니다.
- **시간 제한이 없음**: 로컬 변환에는 타임아웃이 없습니다. 서버 호출에는 callable 기본 타임아웃이 있습니다. heic2any 내부 워커가 응답 없이 멈추면 "업로드 중" 상태가 풀리지 않을 수 있습니다. 일반적으로는 reject로 끝나므로 위험도는 낮게 봅니다.
  - 후속으로 시간 상한을 두고 상한을 넘으면 서버로 넘기는 방식을 권합니다. 이때 heic2any 작업은 중단되지 않고 뒤에서 계속 돈다는 점을 감안해야 합니다.
- **메인 스레드**: heic2any의 변환 단계(캔버스 인코딩 등)가 메인 스레드에서 도는지 확인하지 못했습니다. 진단은 Worker와 `createImageBitmap`을 썼고, 제품은 heic2any 기본 동작과 FileReader/Image를 씁니다. 그래서 진단에서 잰 4.77초는 제품 경로의 시간이 아닙니다. PR 본문도 이 점을 정확히 밝히고 있습니다. 변환하는 몇 초 동안 화면이 멈추는지도 실기기 확인 항목입니다.
- **오래된 libheif**: heic2any에 들어 있는 libheif는 버전이 오래되었습니다. 지원하지 않는 HEIC 변형은 예외를 던지고 대체 경로로 가므로 안전합니다. 하지만 예외 없이 잘못된 결과를 내는 경우, 예컨대 색이나 방향이 틀린 이미지는 대체 경로가 잡지 못합니다.

## 3. 메타데이터 보존

- `readOriginalImageMeta(file)`은 변환 전에, 원본 HEIC의 메모리 `File`로 실행됩니다. EXIF 촬영일과 GPS는 이전처럼 원본에서 추출되고, 대체 경로 시험(`takenDate` 2020-01-02)으로도 고정되어 있습니다.
- 업로드되는 JPEG는 캔버스를 거치므로 EXIF가 없습니다. 이전과 같습니다.
- 개인정보 측면에서는 개선입니다. 로컬 처리가 성공하면 원본 HEIC가 서버(Cloudinary 임시 객체)로 전송되지 않습니다.
- 방향(orientation): libheif는 기본적으로 회전 변환을 적용하고, heic2any 결과물에는 EXIF가 없어 두 번 회전될 위험이 낮습니다. 그래도 세로 사진은 실기기에서 확인해야 합니다.

### 8.1 자동 검토 체계 (2026-10-07 허대표님 결정)

허대표님이 AI끼리 검토·판정하고 대표님은 결과 보고만 받는 방식을 승인했다. 이 절은 8절의 "ChatGPT 공식 판정"과 같은 효력을 가진다. 허대표님이 ChatGPT 판정을 따로 요청한 건은 기존 방식을 따른다.

역할:

| 역할 | 담당 | 방법 |
|---|---|---|
| 실행 | Claude Code(CC) | 구현·문서·검증·Git·병합·배포 |
| 코드·문서 검토 | Codex 자동 리뷰 (`chatgpt-codex-connector`) | PR 생성 시 자동, 수정 push 후 CC가 `@codex review`로 재요청 |
| 설계·완료 검토 | 독립 Claude 검토자 | CC가 작업 맥락을 넘기지 않은 별도 에이전트·세션에 저장소·PR·근거 링크만 주고 검토를 맡긴다. 검토자는 파일을 수정하지 않는다 |
| 판정 기록 | CC | 위 두 검토 결과를 근거로 Slack `#haru2026-감사`에 판정 기록을 게시한다 |
| 최종 결정 | 허대표님 | 아래 "멈춤 조건"과 결과 보고 확인 |

판정 규칙:

- **판정①(확정)**은 다음을 모두 만족할 때만 기록한다.
  1. 최신 HEAD에서 PR CI 통과.
  2. **변경 유형별 필수 검증**을 CC가 실행하고 로그(명령·결과 요약)를 PR에 첨부: 프론트 코드 → `npm run build` + 변경 영역 `frontend/test/*` 테스트, Functions 코드 → `functions` 빌드 + 변경 영역 `functions/test/*` + export 목록 diff, Rules → Rules 테스트, 문서만 → `git diff --check`. PR CI는 프론트 빌드만 하므로 CI 통과만으로 이 항목을 대신하지 않는다.
  3. Codex 지적이 모두 **해결**됨: 해결은 수정 커밋 또는 CC의 반박을 독립 검토자가 수용한 경우만이다. CC가 스레드를 resolve한 것만으로는 해결이 아니다. 최신 HEAD에 대한 Codex 재검토가 완료되어야 하며, Codex가 응답하지 않으면 통과가 아니다.
  4. 독립 검토자 판정이 "승인".
- 독립 검토자가 "수정 후 승인"이면 CC가 수정 → Codex 재검토 → 검토자 재검토를 한다. 재검토 질문에는 **이전 판정 원문과 CC의 반영 내역을 반드시 함께** 넘긴다. 같은 건에서 "수정 후 승인"이 **3회를 넘으면** CC는 판정하지 않고 허대표님께 보고한다.
- 독립 검토자가 "재설계"를 내거나, CC가 검토자 지적을 받아들이지 않으려면 **CC는 판정하지 않고 허대표님께 보고**한다.
- 작업 규모(소·중·대)와 멈춤 조건 해당 여부는 CC가 단독으로 정하지 않는다. 독립 검토자 확인 항목에 포함한다.
- CC는 자기 작업을 스스로 승인하지 않는다.

검토 기록 (재롤링·요약 왜곡 방지):

- **모든 검토 실행**(질문 원문·결과 원문·시각·대상 HEAD)을 승인이 아닌 결과까지 빠짐없이 **아래 보관 위치 중 하나에 원문으로** 남기고, `#haru2026-감사`에 판정과 링크를 게시한다. 보관 위치는 검토 종류별로 다음과 같으며, 어느 경우든 저장소 `docs/reviews/`에서 원문에 닿을 수 있어야 한다.
  - 독립 Claude 검토자: 질문·결과 원문을 `docs/reviews/`에 파일로 남긴다(원문이 저장소 밖에 따로 남지 않기 때문).
  - Codex 리뷰: 원문은 GitHub PR 리뷰·리뷰 댓글이다. 저장소 `docs/reviews/`에는 실행마다 **요청 댓글 링크(질문 원문, 자동 실행이면 그 사실)·실행 완료 시각·검토 커밋·결과 리뷰 ID**와 지적마다 **제목·원문 댓글 링크·반영 커밋**을 담은 **색인 파일**을 새 파일로 추가한다. 빠진 항목이 생기면 기존 색인을 고치지 않고 보조 색인 파일을 새로 추가한다. 판정 기록에는 해당 PR의 Codex 색인 파일 링크를 붙인다.
  - **중단·대체된 Codex 실행**: 결과 없이 끝난 실행(새 push·새 요청으로 대체된 실행, 응답이 없던 실행)도 색인에서 빼지 않고 실행 번호를 매긴다. 그 행에는 다음을 적는다. ① 실행 대상 커밋(요청 시점의 PR HEAD) — 요청 문구가 그와 다른 "검토 대상 HEAD"를 지목했다면 그 커밋을 별도 칸에 따로 적어 둘이 섞이지 않게 한다. ② 요청 시각(요청 댓글이 없는 자동 실행이면 "없음(자동)")과 확인 가능한 시작 시각 — 확인할 수 없으면 "확인 불가"로 적고 추정하지 않는다. ③ 결과 = "대체됨" 또는 "응답 없음"과 그 사유. "대체됨"은 같은 PR에서 **새 Codex 실행이 실제로 요청되었거나 자동으로 시작된 경우에만** 적고, 대체 시점(그 새 실행의 요청 시각, 자동 실행이면 시작 시각 중 확인된 사실값)을 함께 적는다. push만 있고 새 실행이 없으면 대체가 아니며, 기존 실행은 그대로 "응답 없음" 판단 대상으로 남는다. "응답 없음"은 아래 2시간 무응답 규칙의 시한이 지나도 결과가 없을 때 적고, 그 규칙대로 허대표님께 보고한다. 2시간의 기준 시각은 요청 시각이며, 요청 댓글이 없는 자동 실행이면 Codex 요약 댓글에 보인 시작 시각(확인 불가면 그 실행을 일으킨 PR 생성·ready 전환 시각)이다. 실행이 대체되어도 시한은 새로 시작되지 않는다. 시한은 **대기 구간** 단위로 센다: 대기 구간은 결과 없는 실행의 기준 시각에 시작하고, **그 실행 또는 그 실행을 (연쇄로) 대체한 가장 최근 실행**의 결과가 나와야 끝난다. 대체되기 전 실행의 늦은 결과는 구간을 끝내지 않는다. 대기 구간이 2시간을 넘으면 대체 여부와 관계없이 그 규칙대로 보고한다. ④ 대체한 실행의 번호(대체됨일 때). 대체됐거나 응답이 없던 실행은 판정①의 Codex 조건(위 3)을 채우지 않는다.
- **검토 기록 전용 커밋 예외**: `docs/reviews/` 아래에 **새 검토 기록 파일을 추가만** 하는 커밋은 재검토 대상이 아니다(필터 없이 `git diff --name-status <검토 대상 HEAD>..HEAD`를 실행해 **모든 항목의 상태가 `A`이고 경로가 `docs/reviews/` 아래**임을 확인한다. `--diff-filter=A`는 추가 항목만 보여 주어 수정이 섞여도 드러나지 않으므로 쓰지 않는다). 이미 있는 검토 기록 파일을 **수정·삭제**하는 커밋은 예외가 아니며, 재검토와 함께 원 출처(검토자 회신·Slack 기록)와의 대조를 받으며, **수정 diff를 다음 검토자에게 반드시 함께 넘긴다.** 검토 기록 파일은 추가 후 고치지 않는 것을 원칙으로 한다. 판정①은 "최신 검토 대상 HEAD"를 기준으로 하며, 그 뒤에 검토 기록 전용 커밋만 있음을 위 `--name-status` 결과로 확인해 판정 기록에 그대로 붙인다. CI는 최종 HEAD에서 통과해야 한다. 검토 기록 전용 커밋에 다른 경로가 섞이면 예외가 아니다.
- 판정 기록에는 검토자 판정을 요약하지 않고 원문 기록 링크와 판정 문구를 그대로 인용한다. Codex 결과, CI·필수 검증 결과, 기준 HEAD를 함께 적는다.
- 같은 건에 검토자를 새로 띄울 때도 이전 검토 원문을 넘긴다. 이전 판정을 숨기고 새 검토자를 띄우는 것은 금지한다.
- "같은 건"은 같은 설계·작업 건을 뜻한다. PR을 나누거나 다시 열어도 같은 건이면 "수정 후 승인" 횟수(3회 상한)를 이어서 센다.
- Codex 재검토 요청 후 **2시간** 안에 응답이 없으면 통과로 보지 않고 허대표님께 보고한다.
- 교차 검토: 실행자·검토자가 같은 Claude 계열이므로, 모든 PR에서 Codex(OpenAI 계열) 검토를 필수로 한다(위 3).

- ※ 예외: 이미 존재하는 좀비(.zombie)·아카이브 파일 등 **의도적으로 보존하기로 한 파일**은 이 원칙에서 제외. 새 `.old` 백업 생성 의무는 없다.

HARU2026의 모든 사용자 기록은 다음 원칙을 따른다.

1. 모든 사용자 기록은 반드시 아래 컬렉션 안에 저장한다.

   `users/{uid}/records`

2. 문서 내부 `date` 필드는 반드시 `YYYY-MM-DD` 형식으로 유지한다.

3. 하루 단일 대표 기록은 아래 문서 ID를 사용할 수 있다.

   `users/{uid}/records/{date}`

   예:

   `users/abc123/records/2026-06-04`

4. 하루에 여러 개 생성될 수 있는 문서형 기록은 덮어쓰기 방지를 위해 아래 형식의 문서 ID를 사용할 수 있다.

   `users/{uid}/records/{date}_{type}_{timestamp}`

   예:

   `users/abc123/records/2026-06-04_growthTimeline_1717460000000`

5. 성장타임라인처럼 하루에 여러 개 생성 가능한 기록은 순수 `records/{date}`만 강제하지 않는다.

6. `users/{uid}/timelines`, `users/{uid}/growthTimelines` 같은 우회 컬렉션은 만들지 않는다.

7. 저장 경로를 변경하는 마이그레이션은 허대표님 승인 없이 진행하지 않는다.

8. 기능 구현이나 리팩터링 중에도 `users/{uid}/records` 컬렉션 원칙을 유지한다.

## HARU2026 PDF 생성 원칙

HARU2026은 PDF 생성 방식에 따라 아래 원칙을 구분한다.

### 1. 서버 PDFKit PDF

서버 PDFKit으로 PDF를 생성할 때는 다음 원칙을 지킨다.

- 자동 줄바꿈에만 의존하지 않는다.
- 긴 텍스트는 수동 줄 계산을 우선한다.
- `lineBreak: false` 적용 여부를 검토한다.
- 텍스트 블록에는 `maxHeight` 또는 명확한 높이 제한을 둔다.
- 페이지 넘김은 수동으로 제어한다.
- 빈 페이지 발생 여부를 반드시 테스트한다.
- PDF 캐시가 있는 기능은 레이아웃 변경 시 `schemaVersion`을 올려 기존 캐시와 분리한다.
- Storage URL이 재사용되는 구조인지 확인한다.

### 2. 브라우저 window.print PDF

브라우저 `window.print()` 기반 PDF는 다음 원칙을 지킨다.

- `@media print` CSS를 별도로 작성한다.
- 화면 UI와 PDF 출력 UI를 가능하면 분리한다.
- `page-break`, `break-before`, `break-after`, `break-inside`를 명확히 제어한다.
- 이미지가 모두 로드된 뒤 print가 실행되도록 한다.
- 모바일 Safari / iOS에서 깨질 수 있음을 전제로 검수한다.
- 사진이 많은 문서형 기록은 서버 PDF 방식과 비교 검토한다.

### 3. 하이브리드 원칙

HARU2026 PDF는 하나의 방식만 고집하지 않는다.

- 사진과 페이지 제어가 중요한 문서형 기록: 서버 PDFKit 우선 검토
- 단순 기록 출력: 브라우저 `window.print()` 우선 검토
- 비용, 안정성, 모바일 호환성을 함께 고려한다.

## 브랜드 로고 및 호박 상징 원칙

HARU2026의 시각 자산은 역할을 구분한다.

### 포도 로고
- 기존 HARU/HARU2026 서비스 식별용 브랜드 로고다.
- 기존 앱, 서비스 UI, favicon, 앱 아이콘, 헤더 등에 사용 중인 포도 로고를 허대표님의 명시적 승인 없이 삭제하거나 다른 이미지로 교체하지 않는다.
- 호박 이미지가 추가되더라도 기존 포도 로고를 자동으로 대체하는 것으로 해석하지 않는다.

### 호박 상징
haru2026의 브랜드 철학은 다음 문구로 표현한다.

"두 장의 큰 잎이 호박을 키우다"

의미:
- 잎 하나 = 기록관리
- 잎 둘 = 생활문제 해결
- 호박 = 구독자의 삶

호박 이미지는 haru2026의 브랜드 철학과 스토리를 설명하는 상징으로 사용한다.
주요 활용 범위는 랜딩페이지 브랜드 스토리, 하루랩/haru2026 소개, 명함, 홍보물, 소개서 등이다.

호박 이미지 사용 시 허대표님이 제공한 명함의 호박 이미지 원본을 기준으로 한다.
생성형 AI가 유사하게 다시 그린 이미지를 공식 호박 이미지로 임의 채택하지 않는다.

### 변경 금지
허대표님의 별도 승인 없이 다음 작업을 하지 않는다.
- 기존 포도 로고 삭제
- 포도 로고를 호박 이미지로 일괄 교체
- favicon 또는 앱 아이콘의 브랜드 변경
- 기존 브랜드 체계 전체 리디자인

현재 원칙:
포도 = 기존 서비스 식별 로고
호박 = "기록관리 + 생활문제 해결 → 구독자의 삶 성장"을 설명하는 브랜드 철학 상징

향후 두 자산의 통합 또는 공식 로고 변경은 허대표님의 별도 결정 후 진행한다.

const MAX_PHOTO_BYTES = 20 * 1024 * 1024;
const MAX_SELECTION_BYTES = 60 * 1024 * 1024;

export type SelectedRecordPhoto =
  | { ok: true; file: File }
  | { ok: false; message: string };

// Start every stream read in the input change handler, before inspecting
// size/EXIF or awaiting another file. Android picker metadata snapshots can
// otherwise cause ERR_UPLOAD_FILE_CHANGED. Keep only bounded memory Files.
export function startSelectedRecordPhotoReads(files: File[]): Promise<SelectedRecordPhoto>[] {
  let selectionBytes = 0;
  return files.map(async (source): Promise<SelectedRecordPhoto> => {
    const mimeType = source.type.startsWith('image/') ? source.type
      : ({ jpg: 'image/jpeg', jpeg: 'image/jpeg', png: 'image/png', webp: 'image/webp', heic: 'image/heic', heif: 'image/heif' } as Record<string, string>)[source.name.split('.').pop()?.toLowerCase() || ''];
    if (!mimeType) {
      return { ok: false, message: '이미지 형식으로 인식하지 못한 파일이 있습니다.' };
    }
    let reader: ReadableStreamDefaultReader<Uint8Array> | undefined;
    let reservedBytes = 0;
    let succeeded = false;
    const releaseBudget = () => {
      selectionBytes -= reservedBytes;
      reservedBytes = 0;
    };
    try {
      // Do not query source.size/source.lastModified or slice the source.
      reader = source.stream().getReader();
      const chunks: BlobPart[] = [];
      let totalBytes = 0;
      while (true) {
        const { done, value } = await reader.read();
        if (done) break;
        totalBytes += value.byteLength;
        if (totalBytes > MAX_PHOTO_BYTES) {
          releaseBudget();
          await reader.cancel().catch(() => {});
          return { ok: false, message: '20MB를 초과한 사진이 있습니다.' };
        }
        if (selectionBytes + value.byteLength > MAX_SELECTION_BYTES) {
          releaseBudget();
          await reader.cancel().catch(() => {});
          return { ok: false, message: '선택한 사진의 합계가 60MB를 초과했습니다. 사진을 나누어 추가해주세요.' };
        }
        selectionBytes += value.byteLength;
        reservedBytes += value.byteLength;
        chunks.push(new Uint8Array(value));
      }
      const file = new File(chunks, source.name, { type: mimeType });
      succeeded = true;
      return { ok: true, file };
    } catch {
      releaseBudget();
      await reader?.cancel().catch(() => {});
      return { ok: false, message: '사진 원본을 읽지 못했습니다. 사진을 기기에 다운로드한 뒤 다시 선택해주세요.' };
    } finally {
      if (!succeeded) releaseBudget();
      reader?.releaseLock();
    }
  });
}

// Invoke directly in the selection event, before input reset, EXIF, or any await.
export async function readSelectedRecordPhoto(source: File): Promise<File> {
  const [pending] = startSelectedRecordPhotoReads([source]);
  const result = await pending;
  if (!result.ok) {
    const error = new Error(result.message);
    error.name = 'PhotoReadError';
    throw error;
  }
  return result.file;
}

export async function readSelectedRecordPhotos(
  sources: File[], onFailure: (message: string) => void,
): Promise<File[]> {
  const pending = startSelectedRecordPhotoReads(sources);
  const files: File[] = [];
  while (pending.length) {
    const result = await pending.shift()!;
    if (result.ok) files.push(result.file);
    else onFailure(result.message);
  }
  return files;
}

// PDF attachments keep their existing validation/upload path. Only photos need
// picker snapshots; start every photo read before awaiting any preceding PDF.
export async function readSelectedPhotoAttachments(sources: File[]): Promise<File[]> {
  const photoReads = startSelectedRecordPhotoReads(sources.filter(source => source.type !== 'application/pdf'));
  const pending = sources.map(source => source.type === 'application/pdf'
    ? Promise.resolve({ ok: true as const, file: source })
    : photoReads.shift()!);
  const files: File[] = [];
  while (pending.length) {
    const result = await pending.shift()!;
    if (!result.ok) throw new Error(result.message);
    files.push(result.file);
  }
  return files;
}

export async function compressUploadPhoto(file: File, maxWidth = 800, quality = 0.85): Promise<Blob> {
  const isHeic = /image\/hei[cf]/i.test(file.type) || /\.(heic|heif)$/i.test(file.name);
  return compressRecordPhoto(file, {
    isHeic,
    compress: image => compressImage(image, maxWidth, quality),
    convertHeic: async original => {
      const bytes = new Uint8Array(await original.arrayBuffer());
      let binary = '';
      for (let offset = 0; offset < bytes.length; offset += 8192) {
        binary += String.fromCharCode(...bytes.subarray(offset, offset + 8192));
      }
      const result = await httpsCallable(functions, 'convertHeic')({ imageBase64: btoa(binary) });
      const jpeg = await decodeConvertedJpeg(result.data);
      return new File([jpeg], original.name.replace(/\.[^.]+$/, '.jpg'), { type: 'image/jpeg' });
    },
  });
}

  }
  return candidate.roadAddress || candidate.jibunAddress || '';
}

function normalizeSavedTimeline(id: string, data: any): SavedGrowthTimeline | null {
  if (data?.type !== 'growth') return null;
  if (data?.status && data.status !== 'final') return null;
  const rawItems = Array.isArray(data.items) ? data.items : [];
  const items = rawItems
    .filter((item: any) => typeof item?.url === 'string' && item.url.startsWith('http'))
    .map((item: any, index: number): TimelineItem => ({
      url: item.url,
      takenDate: typeof item.takenDate === 'string' && item.takenDate ? item.takenDate : todayKey(),
      metadataSource: item.metadataSource === 'exif' || item.metadataSource === 'manual' || item.metadataSource === 'manualRequired'
        ? item.metadataSource
        : 'manualRequired',
      memo: typeof item.memo === 'string' ? item.memo : '',
      order: typeof item.order === 'number' ? item.order : index,
      locationLabel: typeof item.locationLabel === 'string' ? item.locationLabel : '',
      locationCandidate: item.locationCandidate,
      locationStatus: item.locationStatus,
    }));
  const sortedItems = sortTimelineItems(items);
  return {
    id,
    title: typeof data.title === 'string' && data.title.trim() ? data.title : '성장타임라인',
    status: typeof data.status === 'string' ? data.status : undefined,
    createdAt: data.createdAt,
    updatedAt: data.updatedAt,
    finalizedAt: data.finalizedAt,
    periodStart: typeof data.periodStart === 'string' ? data.periodStart : sortedItems[0]?.takenDate,
    periodEnd: typeof data.periodEnd === 'string' ? data.periodEnd : sortedItems[sortedItems.length - 1]?.takenDate,
    itemCount: typeof data.itemCount === 'number' ? data.itemCount : sortedItems.length,
    items: sortedItems,
  };
}

// records 컬렉션(users/{uid}/records)에 recordType:'growthTimeline'로 저장된 타임라인 정규화
function normalizeRecordTimeline(id: string, data: any): SavedGrowthTimeline | null {
  if (data?.recordType !== 'growthTimeline') return null;
  const rawItems = Array.isArray(data.timelineItems) ? data.timelineItems : [];
  const items = rawItems
    .filter((item: any) => typeof item?.url === 'string' && item.url.startsWith('http'))
    .map((item: any, index: number): TimelineItem => ({
      url: item.url,
      takenDate: typeof item.takenDate === 'string' && item.takenDate ? item.takenDate : todayKey(),
      // 저장된 record 항목은 날짜가 확정된 상태 → '날짜 확인 필요' 배지 방지
      metadataSource: 'manual',
      memo: typeof item.memo === 'string' ? item.memo : '',
      order: typeof item.order === 'number' ? item.order : index,
      locationLabel: typeof item.locationLabel === 'string' ? item.locationLabel : '',
      locationCandidate: item.locationCandidate,
      locationStatus: item.locationStatus,
    }));
  const sortedItems = sortTimelineItems(items);
  return {
    id,
    title: typeof data.title === 'string' && data.title.trim() ? data.title : '성장타임라인',
    status: 'final',
    createdAt: data.createdAt,
    updatedAt: data.updatedAt,
    finalizedAt: undefined,
    periodStart: typeof data.periodStart === 'string' ? data.periodStart : sortedItems[0]?.takenDate,
    periodEnd: typeof data.periodEnd === 'string' ? data.periodEnd : sortedItems[sortedItems.length - 1]?.takenDate,
    itemCount: typeof data.itemCount === 'number' ? data.itemCount : sortedItems.length,
    items: sortedItems,
  };
}

export function GrowthTimelineCreator({ uid, onDone, onSavingChange }: GrowthTimelineCreatorProps) {
  const [title, setTitle] = useState('성장타임라인');
  const [items, setItems] = useState<DraftTimelineItem[]>([]);
  const [isReading, setIsReading] = useState(false);
  const [isSaving, setIsSaving] = useState(false);
  const [isDocumentOpen, setIsDocumentOpen] = useState(false);
  const fileInputRef = useRef<HTMLInputElement | null>(null);
  const previewUrlsRef = useRef<string[]>([]);
  const savingRef = useRef(false);
  const today = todayKey();

  const sortedItems = useMemo(() => sortDraftItems(items), [items]);
  const documentItems = useMemo(
    () => sortedItems.map((item, index): GrowthTimelineDocumentItem => ({
      url: item.previewUrl,
      takenDate: item.takenDate,
      metadataSource: item.metadataSource,
      memo: item.memo,
      order: index,
      locationCandidate: item.locationCandidate,
      locationStatus: item.locationStatus,
      locationLabel: item.locationLabel,
    })),
    [sortedItems]
  );
  const needsDateCheck = sortedItems.some(item => item.metadataSource === 'manualRequired');

  useEffect(() => {
    previewUrlsRef.current = items.map(item => item.previewUrl);
  }, [items]);

  useEffect(() => () => {
    previewUrlsRef.current.forEach(url => URL.revokeObjectURL(url));
  }, []);

  const handleFiles = async (event: ChangeEvent<HTMLInputElement>) => {
    const sources = Array.from(event.target.files || []);
    if (sources.length === 0) return;
    const selectedPhotos = readSelectedRecordPhotos(sources, message => toast.error(message));

    setIsReading(true);
    try {
      const files = await selectedPhotos;
      if (!files.length) return;
      const nextItems: DraftTimelineItem[] = [];
      for (let i = 0; i < files.length; i++) {
        const file = files[i];
        try {
          const meta = await readOriginalImageMeta(file);
          const hasExifDate = typeof meta.takenDate === 'string' && meta.takenDate.trim().length > 0;
          const latitude = typeof meta.latitude === 'number' ? meta.latitude : undefined;
          const longitude = typeof meta.longitude === 'number' ? meta.longitude : undefined;
          const hasGps = typeof latitude === 'number' && typeof longitude === 'number';
          let locationCandidate: ReverseGeocodeCandidate | undefined;
          let locationLabel = '';
          let locationStatus: DraftTimelineItem['locationStatus'] = hasGps ? 'loading' : 'none';

          if (hasGps) {
            try {
              const candidate = await getLocationCandidateFromGps(latitude, longitude);
              if (candidate) {
                locationCandidate = candidate;
                // 자동 인식한 장소명을 기본값으로 (사용자가 그대로 두거나 수정 가능)
                locationLabel = candidate.placeName
                  || candidate.regionLabel
                  || candidate.roadAddress
                  || candidate.jibunAddress
                  || '';
                locationStatus = 'found';
              } else {
                locationStatus = 'not_found';
              }
            } catch (error) {
              console.warn('성장타임라인 촬영장소 후보 확인 실패');
              locationStatus = 'error';
            }
          }

          const compressed = await compressImage(file, TIMELINE_IMAGE_MAX_WIDTH, TIMELINE_IMAGE_QUALITY);
          const uploadFile = new File([compressed], file.name.replace(/\.[^.]+$/, '.jpg'), { type: 'image/jpeg' });
          nextItems.push({
            id: `${Date.now()}_${i}_${Math.random().toString(36).slice(2, 8)}`,
            file: uploadFile,
            previewUrl: URL.createObjectURL(uploadFile),
            originalName: file.name,
            url: '',
            takenDate: hasExifDate ? meta.takenDate! : today,
            metadataSource: hasExifDate ? 'exif' : 'manualRequired',
            memo: '',
            order: items.length + i,
            latitude,
            longitude,
            locationCandidate,
            locationLabel,
            locationStatus,
          });
        } catch {
          toast.error('변환하지 못한 사진은 제외했습니다. 다른 사진은 유지됩니다.');
        }
      }
      setItems(prev => sortDraftItems([...prev, ...nextItems]).map((item, index) => ({ ...item, order: index })));
      if (nextItems.length) toast.success(`${nextItems.length}장의 사진을 불러왔습니다.`);
    } catch (error) {
      console.error('성장타임라인 사진 읽기 실패:', error);
      toast.error('사진 정보를 읽지 못했습니다.');
    } finally {
      setIsReading(false);
      if (fileInputRef.current) fileInputRef.current.value = '';
    }

    setItems(prev => sortDraftItems(prev.map(item => (
      item.id === id ? { ...item, takenDate, metadataSource: 'manual' } : item
    ))).map((item, index) => ({ ...item, order: index })));
  };

  const updateMemo = (id: string, memo: string) => {
    setItems(prev => prev.map(item => (item.id === id ? { ...item, memo } : item)));
  };

    setItems(prev => prev.map(item => (item.id === id ? { ...item, locationLabel } : item)));
  };

      const target = prev.find(item => item.id === id);

      return sortDraftItems(prev.filter(item => item.id !== id)).map((item, index) => ({ ...item, order: index }));
    });
  };

  const openDocumentPreview = () => {
    if (isSaving) return;
    if (sortedItems.length === 0) {

      return;

  };

    const timelineId = `growth_${Date.now()}`;
    try {
      const savedItems: TimelineRecordItem[] = [];
      for (let index = 0; index < sortedItems.length; index++) {

        const safeName = sanitizeFileName(removeFileExtension(item.originalName));

      }
      const periodStart = savedItems[0]?.takenDate || '';
      const periodEnd = savedItems[savedItems.length - 1]?.takenDate || '';
      const content = buildTimelineSummary(savedItems, periodStart, periodEnd);
      const resolvedTitle = await createTimelineTitle(title, content, buildFallbackTimelineTitle(periodStart));

        formats: ['성장타임라인'],
        format: '성장타임라인',
        recordType: 'growthTimeline',
        type: 'growthTimeline',
        source: 'growthTimeline',
        sourceAgent: 'HARU타임라인',
        title: resolvedTitle,
        content,
        timelineItems: savedItems,
        periodStart,
        periodEnd,
        itemCount: savedItems.length,
      });

      toast.success('SAYU·나의 기록에서 확인하실 수 있습니다.');
      items.forEach(item => URL.revokeObjectURL(item.previewUrl));
      setItems([]);

      setIsDocumentOpen(false);
      onDone?.(recordId);
    } catch (error) {
      console.error('HARU타임라인 최종 저장 실패:', error);
      toast.error('HARU타임라인 최종 저장에 실패했습니다.');
    } finally {
      savingRef.current = false;
      setIsSaving(false);
      onSavingChange?.(false);
    }
  };

  return (
    <div style={{ border: '1px solid #dbe8d2', borderRadius: 14, padding: 14, backgroundColor: '#fbfdf7', marginBottom: 16 }}>
      {(isReading || isSaving) && (
        <div
          style={{
            position: 'fixed',
            inset: 0,
            zIndex: 9999,
            backgroundColor: 'rgba(237,233,245,0.92)',
            display: 'flex',
            flexDirection: 'column',
            alignItems: 'center',
            justifyContent: 'center',
          }}
        >
          <div style={{ width: 240, height: 320 }}>
            <GrapeAnimation />
          </div>

            {isReading ? '사진을 읽는 중...' : '타임라인을 저장하는 중...'}
          </p>
        </div>
      )}
      <div style={{ display: 'flex', alignItems: 'center', justifyContent: 'space-between', gap: 10, marginBottom: 12 }}>
        <div>
          <p style={{ margin: 0, fontSize: 15, fontWeight: 800, color: '#355524' }}>새 성장타임라인 만들기</p>

        </div>
        <button
          type="button"
          onClick={() => fileInputRef.current?.click()}
          disabled={isReading || isSaving}
          style={{
            border: 'none',
            borderRadius: 10,
            backgroundColor: '#4E6B2A',

            padding: '10px 12px',

          }}
        >
          사진 선택

      <input

        onTitleChange={setTitle}
        onMemoChange={updatePreviewMemo}
        onFinalize={finalizeTimeline}
      />

  );
}

export function GrowthTimelineLibrary({ uid, refreshKey = 0, onEditTimeline }: GrowthTimelineLibraryProps) {
  const [timelines, setTimelines] = useState<SavedGrowthTimeline[]>([]);
  const [selectedTimeline, setSelectedTimeline] = useState<SavedGrowthTimeline | null>(null);
  const [isExpanded, setIsExpanded] = useState(false);
  const [isLoading, setIsLoading] = useState(false);
  const [deletingId, setDeletingId] = useState<string>('');
  const [editingId, setEditingId] = useState<string>('');
  const [editingTitle, setEditingTitle] = useState('');
  const [savingTitleId, setSavingTitleId] = useState<string>('');

  const startTitleEdit = (timeline: SavedGrowthTimeline) => {
    if (deletingId || savingTitleId) return;
    setEditingId(timeline.id);
    setEditingTitle(timeline.title);
  };

  const cancelTitleEdit = () => {
    if (savingTitleId) return;
    setEditingId('');
    setEditingTitle('');
  };

  const saveTitleEdit = async (timeline: SavedGrowthTimeline) => {
    if (savingTitleId || deletingId) return;
    const nextTitle = editingTitle.trim();
    if (!nextTitle) {
      toast.warning('제목을 입력해주세요.');
      return;
    }
    if (nextTitle === timeline.title) {
      cancelTitleEdit();
      return;
    }

    setSavingTitleId(timeline.id);
    try {
      const updatedAt = new Date().toISOString();
      await updateDoc(doc(db, 'users', uid, 'records', timeline.id), {
        title: nextTitle,
        updatedAt,
      });
      setTimelines(prev => prev.map(item => (
        item.id === timeline.id ? { ...item, title: nextTitle, updatedAt } : item
      )));
      setSelectedTimeline(prev => (
        prev?.id === timeline.id ? { ...prev, title: nextTitle, updatedAt } : prev
      ));
      setEditingId('');
      setEditingTitle('');
      toast.success('타임라인 제목을 수정했습니다.');
    } catch (error) {
      console.error('타임라인 제목 수정 실패:', error);
      toast.error('제목 수정에 실패했습니다.');
    } finally {
      setSavingTitleId('');
    }
  };

  const handleDelete = async (timeline: SavedGrowthTimeline) => {
    if (deletingId || savingTitleId) return;
    const ok = window.confirm(`'${timeline.title}' 타임라인을 삭제할까요?\n삭제하면 되돌릴 수 없습니다.`);
    if (!ok) return;
    setDeletingId(timeline.id);
    let imageCleanupFailed = false;
    try {
      const recordRef = doc(db, 'users', uid, 'records', timeline.id);
      const recordSnap = await getDoc(recordRef);
      const recordData = recordSnap.exists() ? recordSnap.data() : null;
      const rawTimelineItems = Array.isArray(recordData?.timelineItems) ? recordData.timelineItems : [];

    } finally {

function chunkedPhoto(count, options = {}) {
  let index = 0;
  return {name: 'chunked.jpg', type: 'image/jpeg', stream: () => ({getReader: () => ({
    async read() {
      if (index === count) { if (options.fail) throw new Error('provider read failed'); return {done: true}; }
      index++;
      return {done: false, value: new Uint8Array(MiB)};
    },
    cancel: options.cancel || (async () => {}), releaseLock() {},
  })})};
}

test('read failures refund consumed bytes before slow cancellation finishes', async () => {
  let finishCancel;
  const reads = startSelectedRecordPhotoReads([
    chunkedPhoto(10, {fail: true, cancel: () => new Promise(resolve => { finishCancel = resolve; })}),
    ...Array.from({length: 3}, () => chunkedPhoto(20)),
  ]);
  const valid = await Promise.all(reads.slice(1));
  assert.equal(valid.every(r => r.ok), true);
  assert.equal(typeof finishCancel, 'function');
  finishCancel();
  assert.equal((await reads[0]).ok, false);
});
test('oversized files refund previously accepted chunks for later valid files', async () => {

  const later = Array.from({length: 3}, () => {

새 기록 사진 업로드 수정(PR #275/276)이 사유·나의 기록 수정과 비서의 별도 사진 선택 경로에 빠져 있었습니다. 선택 직후 원본을 읽기 전에 size/EXIF를 확인하거나 input을 초기화하면 Android에서 원본 읽기가 실패할 수 있고, 수정 화면은 HEIC 서버 우선 변환 때문에 긴 대기도 남아 있었습니다.

## 주요 변경
- 나의 기록 수정·성장타임라인·독서/주식/보조장부/가계부 OCR·식물/약 비서·정보금고·하루LAW 첨부에서 사진 선택 이벤트 중 즉시 스트림 읽기를 시작합니다. 사진을 메모리 File로 확보한 뒤 후속 처리를 합니다.
- 사진 MIME이 비어 있는 Android 파일은 알려진 사진 확장자로 보완합니다. 사진당20MiB·선택당60MiB 읽기 제한으로 과도한 원본 메모리 보관을 차단합니다.
- 기록 수정은 기존 1600px·0.82 화질을 유지하면서 기기 압축을 먼저 시도합니다. 실패한 HEIC만 기존 서버 변환으로 대체합니다. 다른 흐름도 기존 해상도·품질을 유지합니다.
- 식물 HEIC를 원본/썸네일용으로 두 번 변환하던 동작을 한 번으로 줄이고, 성장타임라인은 미리보기 JPEG를 저장 때 재사용합니다. 사진 일부 실패 때 성공 사진은 유지합니다.
- 정보금고는 기기 내 HEIC 변환으로 확인용 이미지를 지원하고, 실패 시 JPG 재선택을 안내합니다. 외부 변환 서비스에는 보내지 않으며 사진 읽기 중 저장·닫기를 차단합니다. 하루LAW는 원본 첨부의 바이트/화질 및 기존7MB·총량 정책을 유지하며 PDF는 변경하지 않습니다.
- 실제 입력별 범위·제외 범위는 docs/qa/2026-10-17-photo-entrypoints.md에 기록했습니다. 새 기능·라우터·홈화면·모바일 앱 변경 없음.

- 실패한 파일이 차지하던 읽기 용량을 즉시 반환해 정상 사진의 연쇄 실패를 막습니다. OCR은 이전 선택이나 닫힌 기록의 늦은 읽기 결과로 새 선택을 덮어쓰지 않습니다.
