## 필수 보완

**1. 거래로 펼치는 규칙을 기존 `expandRecord`와 같게 고정하고, 같은지 테스트로 확인**
- 현재 규칙: `household_entries` 배열이 있으면 배열만 씁니다. 배열이 없거나, 비었거나, 파싱에 실패하면 레거시 단일 필드로 1건을 만듭니다. (`HouseholdPage.tsx:55-83`)
- 월 문서는 첫 거래를 `household_type`·`household_amount` 같은 상위 필드에도 복제해 저장합니다. (`householdSaveService.ts:44-51, 116-118`) 새 유틸이 배열과 레거시 필드를 **둘 다 펼치면 첫 거래가 두 번 잡힙니다.**
- 새 유틸 테스트에 다음을 넣어야 합니다.
  - 529건 합성 데이터로 구 `expandRecord`와 새 유틸의 건수·금액 합계·메모 문자열을 1:1 비교
  - 입력 객체를 deep-freeze하거나 처리 전후를 비교해 원본이 바뀌지 않았는지 확인

**2. 거래가 아닌 문서가 가짜 거래로 잡히는 경로 처리**
- `isHousehold`는 키가 `household_`로 시작하기만 하면 가계부 문서로 봅니다. (`:89-91`)
- 그래서 `household_entries`가 `"[]"`인 문서나 `household_importKeys`만 있는 문서는 레거시 경로로 넘어갑니다. 그 결과 유형도 금액도 없는 "기타" 거래 1건이 생깁니다.
- 설계 결정이 필요합니다. 기존 동작을 유지하되 "확인 필요"로 따로 셀지, 제외하되 제외 건수를 표시할지 정해야 합니다. 어느 쪽이든 **조용히 사라지거나 조용히 늘어나면 안 됩니다.**

**3. 날짜 정규화 정책을 일 단위로 확장**
- 지금은 월만 검사합니다. 날짜를 읽을 수 없으면 기록 문서 날짜로 대체하는데, 월 문서 날짜는 `YYYY-MM-01`입니다. (`:51-53`, `householdSaveService.ts:26, 122`) 그래서 날짜가 깨진 거래는 **1일 거래로 보입니다.**
- 직접 기간 선택이 들어오면 일 단위 비교가 필요합니다. 다음을 정해야 합니다.
  - `2026.7.3`처럼 한 자리 월·일, `2026.07`처럼 월만 있는 값, 공백·슬래시가 섞인 값을 어떻게 받을지
  - 날짜 대체가 일어난 거래는 "날짜 보정됨" 표시를 하고 건수를 보일지
- 저장 쪽에서 이미 쓰는 `householdDate()`(`householdDuplicates`)가 pure 함수라면 재사용을 권합니다. 저장 판정과 조회 판정이 어긋나지 않게 하기 위해서입니다. 다만 그 함수는 잘못된 값에 throw하므로 감싸서 써야 합니다.
- 기간 경계는 `YYYY-MM-DD` **문자열로 양끝 포함 비교**하고 `new Date('YYYY-MM-DD')` 파싱은 쓰지 않습니다. 이 형식은 UTC로 해석돼 날짜가 하루 밀릴 수 있습니다.

**4. 계정 전환 경쟁 처리: 예산 쪽에 실제 결함이 있음**
```ts
// HouseholdPage.tsx:138-147 — 문서가 없으면 setBudget을 하지 않음
getDoc(ref).then(snap => { if (snap.exists()) { setBudget(data); } })
```
- A계정 예산이 있는 상태에서 예산이 없는 B계정으로 바꾸면 **A의 예산이 그대로 남습니다.**
- 기록을 불러오는 쪽도 늦게 도착한 이전 uid의 응답을 막지 못합니다.
- 두 effect 모두에 다음을 적용해야 합니다.
  - uid가 바뀌면 상태를 먼저 초기화
  - `let alive = true` 후 cleanup에서 `false`로 바꾸고, 결과를 반영할 때 uid가 같은지 확인
  ```ts
  useEffect(() => { let alive = true; setRecords([]); setLoadError(null); setLoading(true);
    getRecords(uid).then(r => alive && setRecords(r.filter(isHousehold)))
      .catch(e => alive && setLoadError(e)).finally(() => alive && setLoading(false));
    return () => { alive = false; }; }, [uid]);
  ```
- 조회 실패도 바로잡아야 합니다. 지금은 `console.error`만 하고 "기록이 없습니다"로 보입니다. (`:133`) 0건 상태와 실패 상태를 구분해야 합니다.

**5. 음수 금액 표시와 합계 정합성**
- 화면 표시: `EntryRow`는 부호 문자열에 금액을 그대로 붙입니다. (`:487`) 음수 지출(환불 등)이면 `--5,000원`이 됩니다. 이번 개편에서 고쳐야 합니다.
- 합계와 분해 불일치: 합계는 음수를 그대로 더하는데, 카테고리 집계는 `amt <= 0`을 뺍니다. (`:172`) 그래서 **카테고리 합계와 지출 합계가 달라집니다.** 둘 중 하나를 골라야 합니다.
  - 카테고리도 순액(음수 포함)으로 집계
  - 차이를 "환불·음수 ○원 별도"로 표시
- 금액을 읽을 수 없는 거래는 지금 0원으로 조용히 합산됩니다. (`parseAmount`의 `?? 0`) "금액 확인 필요 n건"으로 드러내야 합니다.

**6. 유형 분류에서 빠지는 거래**
- 레거시 데이터에는 거래 종류가 빈 값이거나 수입·지출·이체가 아닌 값이 있을 수 있습니다.
- 필터를 수입·지출·이체 셋만 두면 `전체 ≠ 수입+지출+이체` 건수가 됩니다. "기타/미분류" 항목이나 카운트를 추가해야 합니다. 합계 규칙은 `summarizeHouseholdEntries`대로 수입·지출에서 제외합니다.

**7. 비교 기간 정의를 명세에 고정하고 경계 테스트 작성**
- 월 선택의 직전기간은 **달력 기준 전월**로 합니다. 31일 같은 일수 기준이 아닙니다.
- 직접 기간의 직전기간은 같은 일수를 바로 앞에 둡니다.
- 전년동기에서 2/29는 2/28로 맞추고, 그렇게 맞췄다는 표시를 합니다.
- 기준값이 0이면 "계산 불가"로 표시합니다(설계에 이미 반영됨). 기준값이 음수이면 증감률 부호가 뒤집히므로 이 경우도 "계산 불가" 또는 절대 증감만 표시합니다.
- "전체" 기간은 비교 대상이 없으므로 비교 탭을 비활성화합니다.

## 필수 지적

**1. iOS 입력창 확대 재발 (`HouseholdPage.css:210-221, 792-795, 857-860`)**
```css
.household-dashboard input, .household-dashboard select { font-size: 14px; }
@media (max-width:600px){ .hh-date-inputs input { font-size: 12px; } .hh-category select { font-size: 12px; } }
```

- `frontend/.claude/CLAUDE.md`의 실패 이력에 "모바일 텍스트 입력 줌 → fontSize: 16 필수"가 있습니다. 이전 설계 검토 권고에도 들어 있었습니다.
- 해당 입력창: 검색, 월·날짜 선택, 연도·카테고리 선택, 예산 금액.
- 제안:
```css

/* 모바일 블록의 .hh-date-inputs input / .hh-category select 의 12px 삭제

```

## 비차단 권고

- **날짜 형식 누락:** `"2026.07.03."`(끝 점)과 `"2026. 7. 3"`(점 뒤 공백)을 읽지 못합니다. 대체 날짜 경고가 뜨므로 조용히 틀리지는 않습니다. 하지만 은행 원본에 이런 형식이 있으면 경고가 대량으로 뜹니다. 저장 쪽 날짜 함수와 같은 규칙을 공유하거나, 정규화 앞에 아래 처리를 넣는 것을 권합니다.
  ```ts
  raw.replace(/\.\s*/g, "-").replace(/-$/, "")
  ```
- **경고 문구:** `:504` "날짜가 없거나 잘못되면 기록 저장일로"는 사실과 다릅니다. 실제로는 기록 문서 날짜이고, 월 문서는 1일입니다. "기록 문서 날짜(월별 문서는 1일)"로 고치기를 권합니다.
- **동등성 테스트 범위:** 범주·거래처·결제수단은 비교하지 않습니다. 새 코드는 배열 항목의 빈 범주를 "기타"로 바꾸는데(구 코드는 빈 값), 의도된 변경이라면 PR 설명에 적어 두세요.
- **SSR 테스트:** `useState` 호출 순서 index로 mock합니다. 상태가 추가되면 조용히 깨질 수 있습니다.
- **진입 버튼:** "은행 내역 가져오기" 버튼이 `/record`에서 가계부 작성창을 바로 여는지는 브라우저 근거에 없습니다. preview에서 한 번 확인해 주세요.

## 규모·승인 범위·멈춤 조건

- **규모:** 중규모(대 경계). 기존 페이지 안에 새 조회 기능을 넣은 작업입니다.
- **승인 범위:** `validation.md:5`에 허대표님의 2026-10-29 명시 승인 원문(PR → main → 운영 배포)이 있어 범위 안입니다. 8.1절의 2026-10-07 세션 승인은 이어받지 않으므로, 판정 기록에 이 원문을 인용해야 합니다.
- **멈춤 조건:** 해당 없음. 근거는 실행자가 밝힌 범위와 제가 읽은 코드입니다. 저장 경로·Rules·Functions·AI 호출·라우터는 바뀌지 않았고, 쓰기는 기존 예산 설정 저장뿐입니다(`users/{uid}/settings/householdBudget`).
  - **조건:** CC가 PR에 `git diff --name-status main...HEAD`를 첨부해 변경이 화면·유틸·테스트·fixture·`docs/reviews`뿐임을 보여야 합니다. `householdSaveService`·`FormatModal`·`firestoreService`·`App.tsx`·`routes.tsx`·Rules가 섞여 있으면 멈춰야 합니다.
- **판정① 남은 조건:** 수정 후 최신 HEAD에서 CI 통과, Codex 재검토 완료, 이 검토자의 재검토 "승인"이 모두 필요합니다.

## 운영 E2E 한계

합성 529건 검증은 운영 검증이 아닙니다. 배포 후 판정은 **🔍 추가 E2E 필요**로 두고, 허대표님께 아래 확인을 요청해야 합니다.

1. "전체" 건수, 날짜 미확인 건수, 제외 안내 건수를 합하면 529건인지. 새 화면은 날짜 없는 거래를 기간 집계에서 빼고, 빈 문서를 가짜 거래로 세지 않습니다. 그래서 예전 화면 숫자와 다를 수 있고, 차이는 안내 문구로 설명돼야 합니다.
2. 아는 메모 한 건이 검색되고 줄바꿈이 그대로인지.
3. 아이폰 PWA에서 검색창·날짜를 눌러도 화면이 확대되지 않는지(필수 지적 1 확인).
4. "은행 내역 가져오기" 버튼이 가계부 작성창으로 가는지.
