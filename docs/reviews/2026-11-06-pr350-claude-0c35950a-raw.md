## 지적 사항

1. **중간 — 2절 "문제 2", 4.3 M의 정의.** "월 범위 조회는 가계부·AI 로그까지 전부 읽는다"는 사실과 다릅니다.
   - AI 로그는 `date`가 없어 월 범위 쿼리에 안 잡힙니다.
   - 실제로 함께 읽히는 것은 결과 대화 메모·성장타임라인·가계부 월 문서·보조장부·주식 문서입니다.
   - 가계부 월 문서는 거래 JSON 전체를 담아 클 수 있습니다. 구독 중 가계부를 저장할 때마다 이 큰 문서가 다시 내려옵니다(읽기 1회 + 전송량).
   - 7절의 "비서 기록이 formats를 갖는가"는 위처럼 대부분 코드로 답할 수 있습니다. 남는 미확인은 "운영 데이터에 다른 형태의 옛 문서가 있는가"로 좁혀야 합니다.

2. **중간 — 4.5 월 변경과 4.1 기간 사이의 모순.**
   - 쿼리 상한은 `end = 오늘`인데, 재구독은 "월 키"가 바뀔 때만 한다고 했습니다.
   - 그러면 자정을 넘겨 홈에 머무는 동안 새 날짜(`date = 새 오늘`)로 쓴 기록이 쿼리 범위 밖이 되어 빠집니다.
   - 해결 방법은 둘 중 하나입니다: (가) 서버 상한을 "다음 달 1일 미만"으로 두고, 오늘 이후는 클라이언트에서 거른다. (나) 날짜 키로 재구독한다(하루 1회 M 추가).
   - 또 하나: `now`는 1분마다 새 `Date`가 됩니다. range 객체를 effect 의존값에 넣으면 1분마다 재구독(M 읽기)이 일어납니다. 의존값은 문자열 키로 고정한다고 적어야 합니다.

3. **중간 — 3절 '불러오는 중'과 4.5 오프라인 처리.** `useSnsRecords`의 `loading = fromCache && empty`를 그대로 쓰면 숫자가 틀리게 보이는 순간이 생깁니다.
   - 예: 방금 저장하고 홈으로 오면, 첫 스냅샷이 캐시에서 오면서 대기 중 쓰기 문서만 들어 있을 수 있습니다. 이때 "1편"처럼 부분 수가 잠깐 보입니다. "0편을 보여 주지 않는다" 원칙을 확장해 **카운트는 `!fromCache` 이후에만** 보여 줘야 합니다.
   - 반대로 `serverReady`(`!hasPendingWrites` 포함)를 표시 조건으로 쓰면, 저장 직후 스켈레톤이 오래 남습니다. 두 기준 중 무엇을 쓸지 문서에 정해야 합니다.
   - 오프라인이거나 서버가 응답하지 않으면 "불러오는 중"이 끝나지 않습니다. 시간 제한 후 실패 상태로 넘기는 규칙이 필요합니다.
   - 기장 회신의 "실패 시 재시도·기존 캐시 시각 표시"와 "중복 요청 합치기"가 반영되지 않았습니다. 반영하거나, B에서는 필요 없는 이유를 적어야 합니다.

4. **중간 — 4.3 B 비용 서술과 4.5 수명 설계.**
   - '전체 보기'로 바꿀 때 구독을 해제하면, 'my'로 돌아올 때마다 M을 다시 읽습니다. '전체 보기' 전환은 탭뿐 아니라 작성칸의 형식 보기 버튼(`onBrowseFormats`, `HomePageV2.tsx:1104-1107`)으로도 일어납니다.

   - 선택 사항: 홈을 떠난 뒤 짧게 구독을 유지하는 방식으로 재마운트 비용을 줄일 수 있습니다.
