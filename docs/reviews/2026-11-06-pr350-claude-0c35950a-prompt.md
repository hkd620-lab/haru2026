1. 문서가 인용한 코드 사실을 직접 대조하세요. 2절 표의 파일·줄 근거(`HomePageV2.tsx:1152`·`:1141`·`:1248`·`:555`, `recordStats.ts:131/195/203`, `formatRegistry.ts:51`, `firestoreService.ts:827`, `firebase.ts:22-24`, `firestore.rules:198`, `SayuPage.tsx:2576-2638`·`:3255-3295`, `useSnsRecords.ts`)가 실제로 `origin/main`에서 그 내용인지. 틀린 줄 번호·과장·사실과 다른 서술이 있으면 적으세요.
2. 문서의 핵심 주장 두 가지가 맞는지.
   - "`users/{uid}/records`를 쓰는 코드가 13개 파일에 흩어져 있다"(검색 기준 포함). 직접 같은 방식으로 세어 보고, 숫자와 파일 목록이 맞는지, 캐시 무효화가 현실적으로 어려운지 판단하세요.
   - "월 범위 조회는 비서 기록까지 전부 읽는다": `getRecordsInRange`가 형식으로 거르지 않는지, 가계부·AI 로그 등이 같은 컬렉션에 들어 있는지.
3. 조회 방식 비교(4.3)의 타당성. A(일회성 조회 + TTL 5분 + 무효화) / B(`onSnapshot` 구독) / C(일회성 조회, 캐시 없음) 비교에서 Firestore 읽기 과금 방식에 대한 서술이 틀리지 않았는지(구독 시작 시 문서 수만큼 읽기, 이후 변경된 문서당 1회, 메모리 캐시에서 재구독 시 동작 등). 확실하지 않은 부분은 문서가 "확인 못 함"으로 적었는지. 권고 B가 합리적인지, A가 더 나은 이유는 없는지 반박해 보세요.
4. 4.4의 서버 필터 주장: `where('formats', 'array-contains-any', 11개)` + 날짜 범위가 복합 인덱스를 요구하는지, `array-contains-any`의 값 개수 한도, 서버 `count()`를 지금 쓰지 않는 이유가 타당한지. `firestore.indexes.json`에 이미 비슷한 인덱스가 있는지도 확인하세요.
5. 데이터 정의(4.1·4.2)가 기존 통계·합본과 같은 기준인지: `STATS_MERGE_RECORD_FORMATS.some(f => recordHasFormat(r, f))`, 문서 id 중복 제거, `getStatsPeriodRange('month')`(월초~오늘), 최근 3건 정렬·제목·형식 선택 규칙. 규칙 사이에 모순이나 빠진 경계(예: 한 문서에 여러 형식, 날짜 형식이 `YYYY-MM-DD`가 아닌 문서, `updatedAt` 타입이 문자열인지 Timestamp인지)가 있는지.
