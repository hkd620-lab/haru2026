## 2. 변경이 정확한가

### 핵심 로직 (`elderBook.ts:420-443`)

```ts
if (stack.length && char === stack[stack.length - 1]) {   // 닫힘
  stack.pop();
  if (!stack.length) quotes.push(text.slice(start, i + 1)); // 최상위 구간 전체
} else if (pairs[char]) { ... push }                       // 열림
else { throw new Error("Unbalanced quotation marks"); }    // 짝이 맞지 않는 닫힘
```

- **같은 텍스트는 같은 결과가 나옵니다.** 원문과 결과에 같은 함수를 쓰기 때문에, 직선 `"`/`'`처럼 모호한 표기도 양쪽에서 같은 방식으로 파싱됩니다. 그래서 인용 구간이 실제로 바뀌지 않았다면 오탐이 생기지 않습니다.
- 비교 기준은 **최상위 구간 전체를 그대로 비교하는 것**이고, 구간 수와 순서가 같아야 합니다(`:495-496`). 그래서 문구, 띄어쓰기, 문장부호, 따옴표 종류, 중첩 내부, 삭제, 추가, 중복, 재정렬이 모두 잡힙니다. 비교할 때 어떤 정규화도 하지 않으므로 우회 경로는 찾지 못했습니다.
- `originalQuotes[pending.length]`(`:494`)는 매 반복에서 push하거나 throw하므로 반복 인덱스와 항상 같습니다. 맞는 코드이고, `drafted`의 순서(`:458` 정렬)와도 맞습니다.
- 빈 결과는 `polishQuotations('')`이 `[]`를 반환한 뒤 `!content`에서 막힙니다. `finish_reason !== "stop"`이면 잘린 응답이나 필터 응답이 막힙니다.
- 모든 장을 검증한 뒤에 쓰도록 바뀌었습니다(`:503-515`). 뒤쪽 장에서 실패해도 앞 장의 기존 `polished`와 책 `stage`가 덮어써지지 않습니다. 의도대로 동작합니다.
- 오류 메시지에 원고 원문이 들어가지 않습니다(`:464, :492, :497`). 내부 `Error`는 catch에서 버려집니다.

**정확성 결함은 찾지 못했습니다.**

### 참고: 범위가 약간 넓어진 부분 (차단 사유는 아님)
커밋 제목은 "인용문 원문 보존 검사 추가"입니다. 실제로는 ① `finish_reason` 검사, ② 빈 결과 차단, ③ 일괄 저장(모두 성공해야 저장)으로의 전환도 들어 있습니다. PR 본문과 validation.md에 모두 적혀 있고, 같은 목적("잘못된 결과를 저장하지 않음")의 범위 안입니다. CLAUDE.md가 말하는 "커밋 메시지와 실제 변경의 불일치" 멈춤 조건에는 해당하지 않는다고 판단합니다.

## 3. 직접 인용문 보존 효과와 한계

**효과**
- 프롬프트 규칙(`:477`)과 저장 전 검증이 이중으로 걸립니다. 그래서 운영 E2E에서 발견된 유형(인용문 안 문구나 띄어쓰기 변경)은 최소한 **저장되지 않습니다**.

**한계** (validation.md 27-30줄에 대부분 적혀 있고, 제가 덧붙인 것은 ★로 표시)
1. 따옴표가 없는 인용, 블록 인용, 인용 밖의 화자나 문맥 변경은 검증하지 않습니다.
2. 이것은 **보존이 아니라 차단**입니다. 자동 복원이나 재시도가 없어서, 막히면 사용자는 전체를 다시 실행하는 수밖에 없습니다.
3. ★ **일괄 성공 확률 위험.** 장별 불일치율이 p이면 N개 장이 한 번에 통과할 확률은 (1−p)^N입니다. 운영 사본 1회에서 1/8 장이 걸렸는데, 같은 비율이 이어진다면 8개 장 일괄 통과는 약 36%입니다(추정). 새 프롬프트로 이 비율이 얼마나 줄어드는지는 **아직 측정하지 않았습니다**. 계속 실패하면 재실행이 반복되고, 그만큼 실제 비용이 늘 수 있습니다. 코드 결함은 아니지만 운영 E2E에서 반드시 측정해야 합니다.
4. ★ **초고 단계 거부는 원인 장을 알려주지 않습니다.** `:464` 메시지에 어느 장인지 정보가 없어서, 장이 8개 이상이면 사용자가 모든 초고를 직접 훑어봐야 합니다. `'90년대`, `students'`처럼 직선 apostrophe가 단어 경계에 오면 열림으로 해석되어 초고 자체가 거부됩니다(`:430` 규칙은 양옆이 모두 영숫자일 때만 건너뜀). 초고를 수정할 수 있는 UI가 있는지는 **확인하지 못했습니다**(frontend는 읽지 않음).
5. 지원하지 않는 표기: `〈〉`, `《》`, `«»`, 전각 `＂` 등. 한국어 도서 관행상 영향은 작다고 봅니다.
6. 쓰기 단계 원자성 문제는 기존과 같습니다. 초고를 읽은 뒤 최대 540초 동안 초고가 바뀌어도 감지하지 않는 것도 기존과 같습니다.

**비차단 개선 제안 스케치** (승인 조건 아님)
```ts
// :462-466 — 원문 대신 장 순서/제목만 노출
const originalQuotes = drafted.map((c) => {
  try { return polishQuotations(c.draft); } catch {
    throw new HttpsError("failed-precondition",
      `「${c.title ?? c.id}」 초고의 따옴표 짝을 확인해주세요. 기존 윤문은 변경하지 않았습니다.`);
  }

```
결과 검증 실패(`:497`)에도 장 제목을 넣으면 운영 E2E에서 원인을 추적하기 쉬워집니다. 장 제목은 원고 원문이 아니지만, 넣을지는 허대표님 정책 판단입니다.

- 회귀 테스트(`:61-84`)는 모델, 한도, 리전, 경로를 계속 고정합니다.

**빠진 부분 (비차단)**
- 오류 메시지에 원고 원문이 없다는 점을 단언하는 테스트가 없습니다. 지금은 코드 리뷰로만 보장됩니다.

- `finish_reason`이 `undefined`인 응답에 대한 테스트가 없습니다. 현재 코드는 차단하는데, 이 동작이 맞는지는 실제 API 응답 형식에 달려 있습니다.
