## ① Gemini 검색어 전송 조건, 실패 시 일반 검색, 비용, 키

**확인된 점**
- **명시적 요청일 때만 전송합니다.**
  - 클라이언트는 `searchAiEnabled`가 참이고, 제출 버튼이 `value="ai"`일 때만 `searchAiConsentVersion`을 보냅니다.
  - Enter 키는 `requestSubmit()`을 인자 없이 부르므로 submitter가 null입니다. 따라서 Enter로는 일반 검색만 됩니다.
  - 새로고침하면 ref가 초기화되므로, 같은 주소를 다시 열어도 AI 전송이 되풀이되지 않습니다.
- **서버도 이중으로 막습니다.**
  - 전송 조건: `searchAiConsentVersion === 1`, 첫 페이지, 검색어 있음, 검색 연산자 없음.
  - `interpretSearch` 안에서도 `config.searchAiEnabled`와 `isPolicyAccepted`를 다시 확인합니다.
  - 일반 동의 확인은 `policyRequired`와 관계없이 적용됩니다.
- **실패하면 일반 검색으로 넘어갑니다.** 예외는 `try/catch`가 잡습니다. 모델 출력이 형식에 안 맞으면 `parseSearchIntent`가 null을 돌려주고, 원래 조건으로 YouTube 검색을 합니다. 모델 제한시간은 4초입니다.
- **비용은 검색 한도 안에 묶입니다.** `reserveQuota`가 Gemini 호출보다 먼저 실행되므로, 사용자 일일 검색 횟수와 전체 YouTube 할당량이 AI 호출 횟수의 상한이 됩니다. 한 번의 호출도 작습니다(입력 500자 이하, 출력 192토큰, thinking MINIMAL).
- **키:** 기존 전용 키 `VIDEO_FINDER_GEMINI_API_KEY`를 그대로 씁니다. 다른 기능의 키를 재사용하지 않습니다.

**P2-1. 검색 동의 기록이 남지 않음**
- 영상 질문은 `aiConsentVersion`과 시각을 저장합니다. 검색은 클릭할 때마다 동의를 받지만 서버에 기록하지 않습니다.
- 화면 안내도 일부 항목과 링크뿐입니다.
- 국외 이전의 근거를 「동의」로 삼는다면, 증빙과 고지 항목(받는 자, 국가, 항목, 기간, 거부 방법)이 충분한지 스위치를 켜기 전에 법률 검토를 받아야 합니다.
- AI 동의를 철회해도 검색 AI는 계속 쓸 수 있습니다. 클릭할 때만 전송되므로 기능 결함은 아니지만, 철회 문구에서 범위를 구분해 주길 권합니다.

**P2-2. AI를 쓰지 못한 사실을 알려주지 않음**
- 스위치 꺼짐, 일반 동의 없음, 모델 실패 중 어느 경우든 사용자는 AI 검색이 된 것으로 여깁니다.
- **재현:** `policyRequired=false`이고 일반 동의를 하지 않은 계정에서 「동의하고 AI로 찾기」를 누릅니다. 알림 없이 일반 검색 결과가 나옵니다.
- **수정:** 요청은 있었는데 intent가 null이면 「AI 해석 없이 일반 검색으로 찾았어요」를 notice에 붙입니다.

**P2-3. 검색 AI 호출에 사용량 기록과 별도 상한이 없음**
- 질문 경로와 달리 `logged` 래퍼나 호출 횟수 기록이 없습니다.
- 개발자 초기화와 겹치면 전체 YouTube 할당량만 상한으로 남습니다.
- 스위치를 켜기 전에 호출 횟수 로그나 전역 일일 상한을 두길 권합니다.

**P2-4. 구형 iOS 입력 문제**
- `requestSubmit`은 Safari 16 미만에 없습니다. `preventDefault()` 다음에 오류가 나서 Enter가 아무 동작도 하지 않습니다.
- `SubmitEvent.submitter`는 Safari 15.4 미만에 없습니다. AI 버튼이 조용히 일반 검색으로 바뀝니다. 안전한 쪽으로 실패하지만 사용자는 모릅니다.
- Safari에서 한글 조합 중 Enter를 누르면 `isComposing`이 false로 오는 사례가 있습니다. `keyCode === 229` 확인을 추가하길 권합니다.

## ② 모델이 뽑은 날짜와 기존 UI 필터·페이징

**확인된 점**
- **UI 필터가 우선입니다.** `recentDays`는 `filters.period === 'all'`일 때만 적용됩니다. 사용자가 기간을 골랐으면 모델 값은 무시됩니다.
- **날짜 계산:** 한국 시간 오늘 0시에서 (N−1)일을 빼서 `publishedAfter`에 넣습니다. 「최근 7일」은 오늘을 포함한 7일입니다.
- **원래 조건 유지:** 구독자 조건과 정렬(`filterAndSortVideos`)은 원래 `filters`를 씁니다. 검색 이력도 원래 검색어로 남습니다.
- **페이징:** 다음 페이지 커서에 intent가 base64url로 담깁니다. 다음 페이지에서는 모델을 다시 부르지 않고, 같은 검색어와 기간을 다시 적용합니다.
  - 길이 계산: 160자 한글 JSON은 약 680자로, 정규식 상한 800 안입니다.
  - 손상된 커서는 `reserveQuota`보다 먼저 거절되므로 할당량이 차감되지 않습니다.
- **클라이언트 캐시:** `ai|` 접두사로 캐시 키를 나눴습니다. `loadMore`는 요청에 저장된 `cacheKey`를 씁니다.
- **커서 조작:** 클라이언트가 커서를 조작해도 임의 검색어로 검색하는 것과 같아서 권한 문제는 없습니다.

**확인 필요 (P1 후보). 보충 검색과 최신순 보충 경로가 어떤 조건을 쓰는지**
- diff에 보이지 않는 `supplemented`·`dateRelevance` 보충 경로가 문제입니다.
- 이 경로가 `params`를 복사해 쓰면 문제없습니다. 반대로 `buildSearchParams(filters, …)`를 원래 `filters`로 다시 만들면 두 가지가 생깁니다.
  - 검색어가 원래 긴 문장으로 돌아갑니다.
  - `publishedAfter`가 빠져 기간 밖 영상이 섞입니다.
- **확인 방법:** `createVideoFinderService.search`의 `first = await youtube.search(params)`부터 `details`까지 구간에서, 두 번째 `youtube.search` 인자가 무엇에서 나오는지 봅니다.
- **테스트:** 가짜 YouTube 클라이언트로 `sort:'date'`, AI intent `{query:'치과 소식', recentDays:7}`을 줍니다. 모든 `search` 호출 인자의 `q`와 `publishedAfter`를 단언합니다.

**기록:** 같은 주소를 직접 다시 제출하면 AI 없이 새로 검색해 할당량 1회를 씁니다. 뒤로 가기로 이전 AI 기록 항목에 돌아갈 때도 같습니다. 의도된 보수적 동작입니다.

## ③ 개발자·일반 계정의 초기화 권한과 전체 한도

**확인된 점**
- **권한 판단은 서버가 합니다.** 기준은 로그인 정보로 정해진 `uid`의 `canResetSearchQuota(uid)`입니다. 본문의 `uid`는 무시되고, 테스트도 그렇게 확인합니다.
- **일반 계정:** `permission-denied`로 거절됩니다. `status()`에 플래그가 나오지 않아 버튼도 보이지 않습니다.
- **초기화 범위:** `users/{uid}/rateLimits/videoFinderSearch` 한 문서만 `{day, count:0}`으로 병합합니다. 활성 계정 확인을 트랜잭션 안에서 합니다.
- **전체 한도는 그대로입니다.** `videoFinderQuota/{day}`는 건드리지 않습니다. 에뮬레이터 테스트가 개발자 5→0, 일반 사용자 3 유지, 전체 102 유지를 단언합니다.
- **경로:** HARU와 독립 사이트가 같은 access 서비스를 쓰므로 판단 기준이 같습니다.

**확인 필요**
- `isInternalDeveloperUid`가 서버 쪽 허용 목록인지 확인해야 합니다. 클라이언트가 바꿀 수 있는 클레임이나 프로필 필드면 안 됩니다. 테스트는 이 함수를 주입한 가짜로 대체해서, 실제 판정은 시험하지 않습니다.

**P2-5. 테스트 보강**
- 일반 계정 `status()`의 `canResetSearchQuota`가 undefined인지 단언을 추가합니다.
- 초기화 기록 로그(누가, 언제) 1줄을 권합니다.

## ④ 프리미엄 영상 질문의 오타 처리와 되묻기

**확인된 점**
- 프롬프트에 오타·구어체를 보정하라는 지시와 되묻기 조건이 들어갔습니다. 되묻기는 `supported:false`이면서 `needsClarification:true`일 때만 인정됩니다. 이때 답변 문구는 서버가 고정한 문장이고, timestamps와 요약은 비웁니다.
- 되묻기 응답은 `release`로 예약을 풀고 사용자 질문 횟수와 분석 시간을 차감하지 않습니다. 답변 기록도 저장하지 않습니다.
- 클라이언트는 되묻기 턴을 `previousRequestIds`에서 빼고 「메모로 옮기기」를 숨깁니다. 저장되지 않은 요청 ID 때문에 다음 질문이 거절되는 일이 없습니다.

**P1-1. 첫 분석에서 되묻기가 나오면 공급자 한도만 줄고 분석 결과는 버려짐**
- **배경:** 이전 판정의 「실패해도 공급자 기간 한도가 빠진다」를 보면, `release`는 공급자 카운터(하루 15회, 기간 10,800초)를 돌려주지 않는 것으로 보입니다(확인 필요).
- **현상:** 되묻기가 나오면 아래 세 가지가 동시에 일어납니다.
  - 60분 영상 분석 비용은 이미 발생했습니다.
  - 요약을 저장하지 않으므로 다음 질문에서 영상 전체를 다시 분석합니다.
  - 사용자 화면의 남은 분석 시간은 7,200초 그대로입니다.
- **결과:** 짧거나 모호한 질문(「응」, 「?」, 「그거」)이 세 번 되묻기로 끝나면 공급자 기간 한도 10,800초가 바닥납니다. 그러면 유료 사용자는 남은 표시가 있는데도 구독 기간 내내 질문할 수 없습니다.
- **재현(단위 테스트):**
  1. 가짜 모델의 `analyzeVideo`가 `{supported:false, needsClarification:true}`를 돌려주게 합니다.

- **수정안(택1):**

  - (b) 요약이 없는 첫 분석 질문에서는 되묻기를 끄고 최선의 답변을 받습니다. 요약 기반 후속 질문에서만 되묻기를 허용합니다.
  - (c) 아주 짧은 질문은 서버에서 모델 호출 전에 되묻습니다. 비용 0입니다.

**기록:** 요약 기반 후속 질문에서 나온 되묻기는 텍스트 호출이라 비용이 작습니다. 공급자 하루 15회 상한으로 묶이므로 차단 사유가 아닙니다.
