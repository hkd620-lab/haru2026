## 확인한 사실 (근거)

- **편집 키로 쓸 수 있는 값이 없음**: 재가져오기 식별키는 파일 지문과 원본 행에서 만들어지고 분류와는 무관합니다(`householdKakaoImport.ts:141`). 그래서 분류를 바꿔도 재가져오기에서 `already`로 판정되는 것은 유지됩니다. 반면 id가 없는 거래는 식별자가 모두 `manual:undefined`로 같아집니다(`householdDuplicates.ts:29`). 대시보드 `sourceKey`는 걸러낸 뒤의 위치이고, `record.id`가 없으면 `recordIndex`로 대체됩니다(`householdDashboard.ts:88`).
- **레거시 판정 기준이 두 군데서 다름**: 대시보드는 JSON이 깨졌거나, `[]`이거나, 유효한 거래가 하나도 없으면 레거시 단건 필드로 표시합니다(`householdDashboard.ts:59-82`). 저장 서비스는 `[]`이면 빈 배열로 보고, JSON이 깨졌으면 예외를 던집니다(`householdDuplicates.ts:34-45`).
- **빈 행 문제가 은행 경로에 남음**: FormatModal 직접 입력 경로는 빈 기본 행 1개를 미리보기 대상에 포함합니다(`FormatModal.tsx:570,600-603`). 그 결과 `previewHouseholdSave`가 total 1, unchecked 1로 계산하고 "중복 확인 후 저장 (1건 확인 필요)"이 표시됩니다(`householdSavePreview.ts:26,40`). CC 설계는 현금 시트만 분리하므로, 은행 버튼으로 들어가는 FormatModal에는 이 표시가 그대로 남습니다.
- **은행 미리보기 분류가 고정 목록**: 이체는 `['이체']` 하나뿐이고 직접 입력이 없습니다(`FormatModal.tsx:5347,5364-5367,5387-5391`). 분류를 바꾸면 해당 행이 '확인 필요'로 돌아가고 이전 중복 선택 토큰도 무효가 됩니다(`householdSavePreview.ts:9,23`, `householdDuplicates.ts:71`). 다시 확인하는 시점은 창 focus 때뿐입니다(`FormatModal.tsx:649-654`).
- **AI 질문이 `household_sayu` 문자열만 읽음**: Functions는 `record[sourceKey]` 문자열을 그대로 읽습니다(`functions/src/index.ts:2958-2962`). 가계부의 sourceKey는 `household_sayu`로 고정입니다(`index.ts:250`, `resultChatConfig.ts:164`). 검색 원문은 `household_sayu`와 나머지 `household_*` 문자열을 합친 것입니다. 여기에는 `household_entries` JSON과, 첫 거래를 복사한 `household_memo`도 들어갑니다(`SayuPage.tsx:421-435`, `householdSaveService.ts:47-50`). SayuModal 화면은 entries가 있으면 entries를 우선 표시합니다(`SayuModal.tsx:657,2577`).
- **sayu는 추가 저장 때마다 덧붙여짐**: 추가 거래의 sayu 블록이 `'\n\n'`로 이어집니다(`householdSaveService.ts:113-115`). 그래서 사용자가 sayu를 고친 적이 없으면, 현재 sayu는 전체 entries로 다시 만든 문자열과 같습니다.
- **Rules**: `users/{uid}/settings/{id}`는 본인만 읽고 쓸 수 있습니다(`firestore.rules:262,327`). records update는 필드 제한이 없습니다(`firestore.rules:203-208`). 따라서 이번 단위에 Rules 변경은 필요 없습니다.
- **진입 경로**: RecordPage는 `location.state.format`을 읽은 뒤 state를 지웁니다(`RecordPage.tsx:561-568`). FormatModal props에는 진입 모드가 없습니다(`FormatModal.tsx:463`).

## 필수 수정

### M1. 편집 위치 식별 규칙 (요청 1)
CC 설계에는 "id나 importSource가 있으면 식별키로 찾는다"는 경로가 있습니다. 그런데 중복 id나 `manual:undefined`가 있으면 엉뚱한 거래를 찾게 됩니다. 다음으로 바꿔야 합니다.
1. **기본 키는 `recordId + rawIndex`**로 하고, 그 위치의 원본 객체 `householdDigest`가 fingerprint와 일치하는지 확인합니다. identity는 추가 확인용으로만 씁니다. 식별키로 다른 위치를 검색하는 대체 경로는 두지 않습니다. 배열은 추가만 되므로 위치는 안정적이고, 위치가 달라졌으면 충돌로 처리하는 것이 맞습니다.
2. 같은 요청 안에 같은 위치가 두 번 있으면 거부합니다.
3. **배열인지 레거시인지는 문서 모양으로 정합니다.** id 접두사(`legacy:`)로 판단하지 않습니다. 대시보드와 편집 서비스가 **같은 판정 함수 하나**를 쓰게 하고, 트랜잭션 안에서 현재 문서로 다시 판정합니다. 열 때와 결과가 다르면 충돌입니다. 예: 열 때는 레거시였는데 그 사이 같은 월 문서에 거래가 추가된 경우.
4. 실제 `record.id`가 없는 행이나 JSON이 깨진 문서는 편집 버튼을 막습니다.

테스트 추가: 중복 id, id 없는 거래 두 건, 내용이 완전히 같은 두 건을 각각 편집하는 경우. 레거시 문서를 열어 둔 사이 거래가 추가되어 충돌하는 경우. `[]`와 레거시 필드가 함께 있는 문서.

### M2. 은행 진입 화면 구분과 미리보기 분류 (요청 2)
**판단: 전용 은행 모달로 분리하지 않습니다. `RecordPage → FormatModal`에 진입 모드를 넘깁니다.**
- 가져오기의 갱신, 중복 판정, 토큰 처리는 FormatModal 안에서 복잡하게 얽혀 있습니다. 이를 복제하면 회귀 위험이 큽니다. App.tsx와 routes.tsx는 그대로 둡니다.
- 진입 방식은 `navigate('/record', { state: { format:'HARU가계부', from:'/household', householdEntry:'bank' } })`입니다. RecordPage는 state를 지우기 **전에** 이 값을 저장해 FormatModal prop(예: `householdEntryMode`)으로 넘깁니다. prop이 없을 때는 기존 동작을 유지해, 다른 경로와 다른 형식에 영향이 없게 합니다.
- 은행 모드에서는 파일 선택을 맨 위에 두고, 직접 입력 행은 접거나 숨깁니다.
- **빈 행 수정은 두 모드 모두에 적용합니다.** 금액과 거래처가 모두 빈 행은 `householdSaveRows`와 미리보기 건수에서 뺍니다.
- 은행 미리보기에 다음을 적용합니다.
  - 유형별 사용자 분류와 직접 입력. 이체에는 기본 분류와 사용자 분류를 함께 보여 줍니다.
  - 세부분류.
  - 거래처 규칙 제안. 규칙은 **파싱 직후, 첫 중복 확인 전에** 적용해야 불필요한 '확인 필요'가 생기지 않습니다.
  - `categorySource`를 함께 저장합니다.
- `already` 행은 분류 컨트롤을 비활성화하고 "이미 저장됨(저장된 분류 유지)"이라고 표시합니다. 그래야 재가져오기 화면에 파서 기본값이 보여서 사용자가 수정 내용이 되돌아갔다고 오해하지 않습니다.
- 직접 입력 칸에서 글자를 칠 때마다 행이 '확인 필요'로 바뀌지 않도록, 확정 시점(blur 또는 확인)에만 entry에 반영합니다.

### M3. 메모 편집 후 `household_sayu` 불일치 (요청 3)
지금 설계대로 sayu를 그대로 두면 두 가지 문제가 생깁니다. AI 질문은 예전 메모를 근거로 답하고, 검색은 예전 메모와 새 메모 양쪽에 걸립니다. Functions를 바꾸지 않는 최소한의 방법은 **조건부 재생성**입니다.
1. 편집 트랜잭션 안에서, 현재 `household_sayu`가 **편집 전 entries로 `fields()` 규칙을 적용해 만든 문자열과 정확히 같을 때만** 편집 후 entries로 다시 만들어 함께 씁니다. 같다는 것은 사용자가 본문을 쓴 적이 없다는 뜻입니다.
2. 같지 않으면 사용자 본문으로 보고 **건드리지 않습니다.** 대신 SayuModal 가계부 화면에 "거래 목록이 최신 기준입니다. 기록 본문은 작성 당시 내용입니다"라는 안내를 표시합니다.
3. 첫 거래를 복사해 둔 최상위 `household_memo`와 `household_category`도 같은 방식으로 처리합니다. 편집 전 첫 거래 값과 같을 때만 갱신합니다. 이렇게 하면 검색에 예전 값이 남지 않습니다.
4. 레거시 단건 문서는 sayu를 재생성하지 않습니다. 비교가 실패하므로 자연히 보존됩니다.
5. 현재 sayu 형식에는 분류가 들어가지 않으므로 분류만 바꾼 경우에는 sayu가 바뀌지 않습니다. AI가 분류까지 읽게 하려면 Functions 변경이 필요하므로 후속으로 분리합니다.

테스트 추가: 재생성 문서와 사용자 본문 문서를 각각 편집한 결과. 동시 추가와 겹쳤을 때 재시도 후 다시 비교하는지.

### M4. 카테고리 관리를 단순 선택으로 축소하지 않기 (요청 4)
CC 설계는 이름 바꾸기를 범위에서 뺐고, 관리 화면도 분명하지 않습니다. 다음을 이번 단위에 포함합니다.
- 유형별(수입/지출/이체) 관리 화면: 분류 추가, 세부분류 추가, 보관, 보관 해제.
- **이름 바꾸기 = 새 분류 추가 + 기존 분류 보관.** 과거 거래는 자동으로 재분류하지 않습니다. 사용자가 원하면 기존 분류의 거래를 직접 골라 기존 일괄 편집 경로로 옮깁니다. 이때 대상 건수를 미리 보여 주고 충돌 검사를 거칩니다.
- 보관한 분류와 **설정에는 없지만 기존 거래에 쓰인 분류**는 필터, 통계, 편집 화면에서 계속 보이게 합니다. 예: 529건에 들어 있는 사용자 문자열.

### M5. 설정 문서의 안전성 (요청 1)
- 읽고 고치고 쓰는 작업은 반드시 트랜잭션으로 합니다. 예산 저장의 `setDoc(merge:false)` 패턴(`HouseholdPage.tsx:251-254`)을 따라 하지 않습니다. 기본 목록을 문서에 써 넣지 않습니다.
- 불러오기에 실패하면 기본 목록과 기존 거래에서 모은 분류를 보여 줍니다. 변경은 트랜잭션으로만 시도하고, 실패하면 오류를 표시합니다.
- 거래처 규칙 키에 `.`이나 `|`가 들어갈 수 있으므로 점 경로 `update`를 쓰지 않습니다. 맵 전체를 쓰거나 키를 해시합니다.
- 분류 추가와 거래 저장은 원자적이지 않습니다. 설정 저장이 실패해도 분류 목록에 거래에 쓰인 분류를 합쳐 보여 주면 재사용이 끊기지 않습니다.
- 계정이 바뀌면 분류 목록, 규칙, 편집 시트, 선택 모드를 모두 초기화합니다. 저장은 시작할 때의 uid를 기록해 두고, 그 사이 계정이 바뀌었으면 결과를 버립니다.

### M6. 현금 저장의 실패와 재시도
- 실패 후 같은 id로 재시도했는데 결과가 `already>0`이면 "이미 저장됨(첫 시도 내용)"이라고 알리고 목록을 다시 불러옵니다. 실패 후 사용자가 내용을 고쳤더라도 성공으로 표시하지 않습니다.
- 기본 날짜는 **KST 로컬 날짜**입니다. `toISOString()`을 쓰면 오전 9시 이전에 하루 전 날짜가 됩니다.
- 금액은 양수만 받고 부호는 유형으로 정합니다.
- 실패하면 입력값을 그대로 두고 오류를 표시합니다.

### M7. '분류 확인 필요'와 규칙 적용 기준
- 대시보드 복사본은 빈 분류를 `기타`로 바꿉니다(`householdDashboard.ts:97`). 따라서 판정은 **원본 entry**로 합니다.
- 여기에 "이 분류로 확정" 동작을 둡니다. 분류는 그대로 두고 `categorySource:'user'`만 씁니다. 이 동작이 없으면 일부러 `기타`를 고른 거래가 목록에서 빠지지 않습니다.
- 새로 가져오는 거래는 파서가 매핑한 분류 **모두**(`기타`가 아닌 것 포함)에 `import-default`를 붙입니다. 규칙은 분류가 비었거나 `import-default`인, **아직 저장 전**인 거래에만 적용해서 파서 매핑보다 우선하게 합니다.

## 작업 규모와 멈춤 조건 (요청 5)

- **작업 규모: 대.** 새 컴포넌트와 서비스가 3–4개이고, 기존 저장 데이터를 편집하는 경로와 FormatModal·RecordPage 수정이 들어갑니다.
- **멈춤 조건: 이번 단위는 해당 없음.**
  - '새 기능 착수'는 사용자가 이미 보완사항 전체 구현과 Hosting 배포를 승인했으므로 다시 승인받을 필요가 없습니다.
  - App.tsx, routes.tsx, 홈 화면은 바꾸지 않습니다. RecordPage는 라우터 파일이 아니고 수정 금지 목록에도 없습니다.
  - Rules, Functions, AI, 인증, 결제는 바꾸지 않습니다. 비용도 늘지 않습니다.
