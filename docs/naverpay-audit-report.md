## 3. 약관-기능 일치 조사 (핵심)

### 3-A. 환불 방식 ⭐ 결제형 최우선 요건

**판정: ⚠️ 자동 환불 로직 미구현 — 수동 이메일 처리 구조**

- **조사 파일**: `functions/src/index.ts` 전체 grep (refund/환불/cancel)
- **결과**: `refund` 키워드 **0건**. 환불 처리 Function 없음.
- **실제 구조**: 
  - `RefundPage.tsx`: "harul2026lab@gmail.com으로 문의" 안내만 표시
  - `SettingsPage.tsx` > "환불 문의" 버튼: RefundPage로 이동
  - PortOne API의 `cancelPayment` 또는 `refund` 엔드포인트 호출 코드 없음
- **약관 기준**: 제10조 제5항 "결제한 수단과 동일한 방법으로 환불함을 원칙"
- **코드 현실**: 자동 환불 없음 → 이메일 요청 후 **수동 처리**

> **결제형 요건 관점**: 네이버페이 결제형은 "원결제수단 취소" 방식을 기본으로 요구합니다. 수동 이메일 처리도 운영상 불가하진 않으나, 심사 시 "환불 처리 절차"를 묻는 항목이 있을 경우 API 연동 없이 수동 처리한다는 점을 명확히 해야 합니다.  
> **조치 필요**: PortOne 환불 API(`POST https://api.portone.io/payments/{paymentId}/cancel`) 연동 또는, 심사 제출 자료에 "수동 이메일 접수 후 3~5 영업일 내 원결제수단 취소" 절차를 구체적으로 명시.

### 3-B. 빌링키 해지 — 약관 제9조 제3항

**판정: ⚠️ Firestore만 처리, PortOne 서버 빌링키 해지 미호출**

- **조사 파일**: `functions/src/index.ts` L4167~4236 (`cancelSubscription` 함수)
- **Firestore 처리**: `billingKey: null`, `status: 'cancelled'` 저장 ✅
- **PortOne API 호출**: `DELETE https://api.portone.io/billing-keys/{billingKey}` **호출 없음** ❌
- **결과**: Firestore에서 billingKey가 null로 처리되므로 스케줄러(`scheduledBillingJob`)에서 다음 결제 시 `!billingKey` 체크로 과결제 방지됨. 실질적 과결제 위험은 낮음.
- **잠재 위험**: PortOne 서버에 빌링키가 살아있을 수 있어, 외부에서 해당 billingKey로 결제를 시도할 수 있는 이론적 가능성 존재.

> **조치 권고**: `cancelSubscription` 함수에서 Firestore null 처리 외에 `DELETE https://api.portone.io/billing-keys/{billingKey}` API 추가 호출 권장. 단, 현재도 자동갱신 차단은 되므로 심사 통과 자체에 결정적 영향은 낮음.
