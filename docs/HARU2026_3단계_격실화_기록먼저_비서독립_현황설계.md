## 3. 설계 원칙

- 기존 Firestore 경로·문서 ID 규칙·저장 필드를 바꾸지 않는다. 마이그레이션 없음.
- 동작을 바꾸는 PR과 구조만 바꾸는 PR을 섞지 않는다. 구조 PR은 "화면·저장 결과 동일"을 검증 기준으로 한다.
- 기능 폴더는 공용 기반(인증·기록 저장/조회·사용량 계측·공통 UI)만 import하고, **다른 기능 폴더를 직접 import하지 않는다.**
- **CLAUDE.md 「CC 코드 수정 원칙」과의 관계**: 이 원칙은 "요청된 부분만 수정·기존 함수·import를 건드리지 말 것"을 요구한다. P2·P3·P3.5 구조 PR은 2026-10-01 허대표님 3단계 지시("기능별 격실화 … 작은 PR로 실행")를 요청 근거로 하여, 각 PR 표에 적은 파일·함수만 옮기는 '요청된 부분'으로 본다. 표에 없는 파일은 고치지 않는다. 이 해석이 맞는지는 §6-9에서 허대표님 확인을 받는다.
- 홈화면·라우터·새 기능 파일을 건드리는 작업은 동작 동일 구조 변경이라도 CLAUDE.md 「반드시 멈추고 보고」 해석상 **허대표님 결정 후** 착수한다(§6-1).

### 4.1 비서 등록부 (비서 독립·관련 비서 연결의 기반)

`frontend/src/app/assistants/registry.ts`(신규)에 비서마다 하나의 항목을 둔다.

```ts

type AssistantEntry =
```

- **물리 파일은 둘로 나눈다**: 홈 메타(`assistants/homeRegistry.ts`: `id`·`label`·`entry`·`legacyKeys`·`homeCard`·노출 플래그)와 SAYU 어댑터(`assistants/sayuAdapters.ts`: `id`로 연결되는 `sayu`·`originalRecords`). 위 타입은 논리 구조다. 이렇게 해야 HomePageV2가 SAYU 로더를 import하지 않는다(§3 기능 간 import 금지, 번들 크기).

- **홈 개인화 키 보존**: '내 HARU' 저장값(`selectedAgents`)은 `getAgentKey`(`HomePageV2.tsx:556-559`)의 결과 `action:${action}` / `` `path:${agent.path || 'none'}:${JSON.stringify(agent.state || {})}` ``다. 등록부는 이 키를 **같은 문자열로** 만들어야 한다(`|| 'none'`, state 키 순서 포함). 클릭 시 붙는 `from`·`resetAssistantScroll`(`:1786-1792`(검))은 키에 들어가지 않는다.
- **관련 비서 연결은 별도 추천 등록부**로 둔다. 현재 `RECOMMENDATION_RULES`(`assistantRecommendations.ts:25-150`)는 health(`/sayu-health`)·hospital(`/sayu-health/hospital`)·medicine(`/sayu-health/drug`)처럼 한 비서 안의 하위 화면으로 가는 규칙과, finance·childcare·travel·life처럼 홈 비서가 아닌 `/record`로 가는 규칙을 함께 가진다. 비서 1개당 추천 1개로 묶으면 규칙을 버리거나 엉뚱한 홈 카드를 만들게 되므로, 추천은 다음처럼 **규칙마다 자기 이동 대상**을 갖는다.

```ts
// frontend/src/app/assistants/recommendationRegistry.ts(신규)
type RecommendationRule = {
  id: string;                 // 'health' | 'hospital' | 'medicine' | 'law' | 'finance' | … (기존 id 그대로)
  category: string;
  title: string; description: string; actionLabel: string;
  keywords: string[];
  destination: { path: string; state?: Record<string, unknown> }; // 기존 targetPath를 그대로 옮김

};
```

- P1에서 기존 규칙의 순서·키워드·문구·이동 대상을 그대로 옮기고, 추천 함수 출력이 변경 전과 같음을 고정 입력 테스트로 확인한다. 하루LAW 추천의 이동 대상이 전자소송연습비서(`/legal-assistant`)로 어긋난 현 상태는 **동작 변경**이므로 P1에서는 보존하고, 바로잡는 것은 별도 결정(§6-5)으로 둔다.
- **SAYU 세 갈래 통합**: 비서 탭(`fromRecord`·`fromSource`), 기록 탭 구조화 뷰(`structuredView`), 성장타임라인(`timelineView`)을 모두 등록부로 표현하고, SayuPage에는 비서별 코드를 남기지 않는다.
- **비서 기록의 형식 통계 혼입**: 직접작성영어일기·성장기록·배뇨일지가 `formats`에 들어가 형식 통계에 섞이는 현 상태는 기존 데이터라 **이번 설계에서 바꾸지 않는다**. 새 비서부터는 `formats`가 아니라 `sourceAgent`로 식별한다.

### 4.2 형식 등록부 (단일 형식 정의)

`frontend/src/app/records/formatRegistry.ts`(신규)에 형식 라벨·접두어·표시 색·SAYU/내보내기/합본/공개 허용 여부를 한 곳에 둔다. 1.2의 정의 중 P3.5 대상 21곳(LibraryPage 3곳 제외)을 이 등록부 참조로 바꾼다.

- **소비처별 키는 하나로 합치지 않고 이름 붙은 역할로 보존한다.** 같은 형식이라도 소비처마다 키가 다르다: 육아일기는 저장 필드 접두어 `child`(`haruTypes.ts:85`)와 통계·미래전망 키 `parenting`(`firestoreService.ts:1271`, `ProphecyFromRecord.tsx:12`), 성장기록은 `growth`(`haruTypes.ts:86`)와 SAYU 구조화 뷰 키 `child_measure`(`SayuPage.tsx:2235`). 등록부 항목은 `{ label, fieldPrefix, keys: { stats?, sayu?, prophecy?, export?, ... } }`처럼 역할별 값을 갖고, 각 소비처는 자기 역할 값을 읽는다. 역할 값이 없으면 `fieldPrefix`를 쓴다.
- 역할 값을 하나로 통일하는 것은 통계·미래전망·SAYU 동작을 바꾸므로 **구조 PR(P3.5)에서는 하지 않고**, 필요하면 별도 승인된 동작 변경으로 다룬다. Functions 쪽 3곳(`index.ts:5173`, `index.ts:2393`, `epubExport.ts:22`)은 같은 정의를 복사한 Functions 공유 상수 파일로 맞추고, 프론트·Functions 값 일치를 테스트로 고정한다. 교체는 소비처 기능별로 나눠 진행한다(§5 P3.5a~d).

### 4.3 기록 먼저 / 형식 나중

목표 흐름(9/28 등록안):

```
홈 '나의 일상 기록하기' → 자유 작성(본문, 선택: 제목·사진) → 저장
  → 저장 직후 "이 기록을 어떤 형식으로 정리할까요?" 제안(건너뛰기 가능)
  → SAYU에서 언제든 형식 지정·변경
기존 형식 카드는 '형식으로 바로 쓰기' 보조 경로로 유지
```

저장 데이터 선택지:

| 안 | 저장 형태 | 판단 |
|---|---|---|
| A (철회) | `formats: ['메모']` + `memo_*` | 통계·SAYU·캘린더가 미분류 기록을 실제 메모로 집계·표시 → 형식 통계 오염, "건너뛰고 나중에 분류"와 모순 |
| **B (권장)** | `formats: []` + `entryMode: 'freeform'` + `freeform_title`/`freeform_content`(+선택 사진) | 미분류가 데이터에 명시됨. 형식 통계에 섞이지 않음. 빈 배열은 기존 가드에서 오류 없음. Rules 변경 0 |

B안 규칙:

1. **미분류 판정**: `entryMode === 'freeform'` && `freeform_content`가 비어 있지 않음 && `formats.length === 0`. 세 조건을 모두 본다. `formats.length === 0`만으로는 LibraryPage 초기화·레거시 성장 측정 문서가 섞이고, `entryMode`만으로는 형식을 지정한 뒤에도 「미분류」로 다시 나타난다.
   - 상태 전이: 자유 저장 → **미분류**(`formats: []`) → 형식 지정 → **분류됨**(`formats: [선택 형식]`, `entryMode`는 `'freeform'` 유지 = "자유 기록에서 출발" 표시, `freeform_*` 보존) → 형식을 모두 지움 → 다시 **미분류**(문서 삭제 없음).
2. **삭제 보호**: `entryMode === 'freeform'` 문서는 `formats`가 비어도 **문서를 삭제하지 않고 미분류로 되돌린다**. `SayuPage.tsx:2918-2921`, `RecordDetailPage.tsx:189-192`의 "formats 비면 삭제"를 이 조건으로 고친다. 자유 기록 자체의 삭제는 별도 명시 동작으로만 한다.
3. **본문 필드**: 기존 `content`는 RecordPage가 형식 기록에도 `''`로 저장(`:1104`)하므로 미분류 본문과 구분이 안 된다. 그래서 `freeform_content`를 새로 쓴다.
4. **형식 지정**: `freeform_*` → 선택 형식 필드로 변환하되 `freeform_*` 원문은 보존한다. 본문 중심 형식(일기·에세이·메모)부터 연다.
