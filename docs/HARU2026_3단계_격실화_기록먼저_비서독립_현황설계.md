### 1.1 홈 — 형식을 먼저 고르는 구조

- `frontend/src/app/pages/HomePageV2.tsx` (2,611줄). 로그인 사용자의 `/`는 `HomeOrLanding` → `HomePageV2` (`App.tsx:141-149`).
- 섹션 순서: 「HARU 기록」(`:1653`) → 「비서」(`:1747`) → 「분석 도구」(`:1987`). '내 HARU' 개인화(`homeViewMode 'my'|'all'`, `:593-598`)가 이미 있다.

## 2. 문제 정리 — 격실이 깨지는 지점

1. **대형 공용 파일**: FormatModal 6,930 · SayuPage 6,914 · PlantDetectivePage 5,044 · HomePageV2 2,611 · RecordPage 2,006 · Functions index 16,055줄. 기능 하나의 수정이 큰 파일 전체 회귀가 된다.

4. **형식 먼저**: 기록 시작 전 형식 선택이 필수라 9/28 UX 목표와 반대.

## 3. 설계 원칙

- 기존 Firestore 경로·문서 ID 규칙·저장 필드를 바꾸지 않는다. 마이그레이션 없음.
- 동작을 바꾸는 PR과 구조만 바꾸는 PR을 섞지 않는다. 구조 PR은 "화면·저장 결과 동일"을 검증 기준으로 한다.
- 기능 폴더는 공용 기반(인증·`firestoreService.saveRecord`·사용량 계측·공통 UI)만 import하고, **다른 기능 폴더를 직접 import하지 않는다.**
- 홈화면·라우터·새 기능은 CLAUDE.md상 대규모 → 허대표님 승인 후 착수.

## 4. 목표 구조

### 4.1 비서 등록부 (비서 독립의 기반)

`frontend/src/app/assistants/registry.ts`(신규)에 비서마다 하나의 항목을 둔다.

```ts
type AssistantDefinition = {
  id: string;                 // 'haruLaw', 'plantDetective' …
  label: string;              // 홈·SAYU 표시명
  route: string;              // 독립 진입 경로
  hiddenForGeneralUsers?: boolean;
  homeCard: { sub: string; tag: string; variant: string; icon: ReactNode };
  sayu?: {                    // SAYU 비서 탭 표시 어댑터
    matches(record: HaruRecord): boolean;
    toEntries(record: HaruRecord, ctx: SayuEntryContext): FlatSayuEntry[];
  };
  originalRecords?: OriginalAssistantKind; // 별도 컬렉션 원본 조회(기존 PR #241 방식)
};
```

- 홈 「비서」 섹션과 `HIDDEN_AGENT_LABELS`를 등록부에서 읽는다.
- SayuPage의 `assistantEntries`(`:4532-4585`)를 `registry.flatMap(a => a.sayu)`로 조립한다. 비서별 빌더 코드는 각 비서 폴더로 옮긴다.
- 효과: 새 비서 추가가 "비서 폴더 + 등록부 1줄"로 줄고, SayuPage를 열지 않는다.

### 4.2 기록 먼저 / 형식 나중

목표 흐름(9/28 등록안):

```
홈 '나의 일상 기록하기' → 자유 작성(본문, 선택: 제목·사진) → 저장
  → 저장 직후 "이 기록을 어떤 형식으로 정리할까요?" 제안(건너뛰기 가능)
  → SAYU에서 언제든 형식 지정·변경
기존 형식 카드는 '형식으로 바로 쓰기' 보조 경로로 유지
```

저장 데이터 선택지:

| 안 | 저장 형태 | 장점 | 비용 |
|---|---|---|---|
| **A (권장 1차)** | `formats: ['메모']` + `memo_title`/`memo_content`, `entryMode: 'freeform'` | 기존 `메모` 형식 재사용 → 읽는 쪽 18곳·통계·SAYU 수정 0. Rules 변경 0 | "미분류"를 메모와 구분하려면 `entryMode`로 판별 |
| B | `formats: []` + `unclassified: true` | 의미가 정확함 | 18곳 가드 수정 + 통계·SAYU 미분류 표시 신설 → 회귀 범위 큼 |

- 1차는 A안. 형식 지정은 "메모 → 선택 형식" 변환이며, 변환 규칙(어느 필드로 옮길지)은 형식별로 다르므로 P5에서 일기·에세이·메모처럼 본문 중심 형식부터 연다.
- 기존 형식 카드 진입(`/record` + `state.format`)과 저장 결과는 그대로 둔다.

### 4.3 기능별 격실 (폴더·Functions)

- 프론트: `frontend/src/app/assistants/<id>/`, `frontend/src/app/records/<format>/` 단위로 점진 이동. 한 PR에 한 기능만.
- RecordPage에서 하루LAW를 분리해 독립 라우트(예: `/haru-law`)로 둔다. 기존 `/record` + `category: '하루LAW'` 진입은 새 라우트로 넘기는 호환 처리를 남긴다.
- Functions: `index.ts`의 기능 묶음을 파일로 옮기고 `index.ts`는 re-export만 한다. **함수 이름·region(`asia-northeast3`)·트리거 설정이 바뀌지 않음**을 export 목록 diff로 검증하고, 배포는 옮긴 함수만 `--only`로 한다.
