# HARU2026 하네스 엔지니어링 공용문건

> 문서 위치: `~/HARU2026/docs/HARU2026_HARNESS_ENGINEERING.md`
> 최종 갱신: 2026년 5월
> 대상: 허대표님 · 시박사 · 기장(CCD) · CC 공용 참고 기준문서

---

## 1. 문서 목적

이 문서는 HARU2026을 개발·검토·운영하는 모든 협업자가 공통으로 참고하는 **하네스 엔지니어링 기준문서**다.

HARU2026은 단순히 Gemini나 다른 AI 모델을 호출하는 앱이 아니다. 사용자의 기록을 목적별 입력 형식, 저장 구조, AI 비서, 외부 전문 API, 검수 절차, 배포 규칙으로 감싸서 AI가 안정적으로 작동하도록 만드는 **하네스(harness, 묶음 구조) 기반 AI 라이프 플랫폼**이다.

이 문서는 다음 협업자가 함께 참고한다.

```text
허대표님   = 최종 의사결정자 · 방향 결정 · 사업 판단
시박사     = 전략 · 기획 · 제품 구조 설계 · CC/기장 지시문 작성 · 위험 정리
기장(CCD)  = 메인 개발(공장장) · 구조 판단 · 핵심 문제 해결
CC         = 보조 개발 · 검수 보조 · 부분 기능 · 테스트
```

### 1.1 역할은 고정 서열이 아니라 실적 기준 배치다 (중요)

위 역할 배치는 **고정된 서열이 아니라, 2026년 5월 현재 시점의 실적 기준 배치**다.

```text
- 현재(2026.05): 기장(CCD)이 메인 개발(공장장), CC가 보조 개발·검수.
- 평가 기준: 안정성 · 문제추적 정확도 · 구조 보존 · 방향 일치.
- 위 기준으로 더 나은 성능을 보이는 AI가 메인 개발(공장장)을 맡는다.
- 도구는 신앙이 아니라 연장이며, 실적으로 선택한다.
- 따라서 메인 개발자는 AI 성능 변화에 따라 언제든 교체될 수 있다.
```

## 2. HARU2026의 핵심 정의

HARU2026은 "기록앱"만이 아니다. 사용자의 일상 기록을 목적별 형식으로 입력받고, AI 다듬기, 통계, 합본, 검색, 전문 API, AI 비서실로 연결하는 **하네스 기반 AI 라이프 컴파일러**다.

```text
HARU2026의 경쟁력은 특정 AI 모델 하나가 아니라,
사용자의 삶을 기록 형식, 저장 구조, 전문 API, AI 비서,
통계, 합본, 검수 절차로 묶는 하네스 구조에 있다.
```

## 3. HARU2026의 하네스 구성

### 3.1 입력 하네스

HARU2026은 사용자가 무질서하게 쓰는 구조가 아니다. 기록 목적에 따라 입력 형식을 나누고, 각 형식마다 필드를 제공한다.

```text
일기 · 에세이 · 여행기록 · 업무일지 · 일반보고 · 선교보고
육아일기 · 반려동물 관찰 · 텃밭일기 · 투자일기 · 독서사유
하루LAW · 하루식물탐정 · HARU보조장부
```

입력 하네스의 목적:

```text
1. 사용자가 쉽게 기록하게 한다.
2. AI가 기록의 목적을 오해하지 않게 한다.
3. 나중에 검색·통계·합본·비서 분석이 가능하게 한다.
4. 기록이 단순 문장이 아니라 자산화 가능한 데이터가 되게 한다.
```

### 3.2 저장 하네스

기록 저장 경로는 반드시 유지한다.

```text
users/{uid}/records/{date}
```

금지 사항:

```text
- users/{uid}/records/{date} 경로 변경 금지
- 기존 records 구조 임의 리팩터링 금지
- 웹과 모바일이 다른 저장 경로를 쓰도록 변경 금지
```

식물도감·클라우드 연결·자산 관리 같은 별도 기능은 필요 시 별도 컬렉션을 쓸 수 있으나, 하루 기록의 기본 경로는 절대 변경하지 않는다.

### 3.3 프롬프트 하네스

HARU2026의 AI는 사용자의 기록을 마음대로 재창작하지 않는다.

SAYU(사유) 다듬기 원칙:

```text
1. 원문 감정을 보존한다.
2. 원문 사실을 보존한다.
3. 사용자가 쓰지 않은 사건을 추가하지 않는다.
4. 과장하지 않는다.
5. 교훈을 임의로 붙이지 않는다.
6. 문장만 자연스럽게 정리한다.
7. 사용자의 삶을 존중하는 절제된 문체를 사용한다.
```

문체 원칙: 과장 없는 문체 · 사실 기반 해석 · 사용자 기록 우선 · 공감하되 지어내지 않음 · 불확실한 것은 불확실하다고 표시.

### 3.4 도구 하네스

HARU2026은 Gemini 하나에 모든 판단을 맡기지 않는다. 영역별로 전문 API·공공데이터·사용자 기록을 조합한다.

| 영역 | 하네스 방식 |
|---|---|
| 하루LAW | 법령·판례·행정정보 기반 |
| 하루식물탐정 | Plant.id, PlantNet, 국립생물자원관 등 전문 데이터 기반 |
| 약사도우미 | 식약처 의약품 정보 기반 |
| 명의찾기 | 증상·진료과·병원 정보 기반 |
| 투자일기 | 사용자 투자 기록과 시장 데이터 기반 |
| 영어일기 | 사용자 원문 기록 기반 영어 학습 |
| 독서사유 | 책별 누적 기록 기반 사유 확장 |
| 보조장부 | 거래 기록·증빙·통계 기반 정리 |

도구 하네스의 원칙:

```text
- AI가 사실을 만들어내지 않게 한다.
- 전문 영역은 전문 데이터와 연결한다.
- Gemini는 해석과 설명을 담당한다.
- 판단 근거가 필요한 영역은 출처·데이터 기반을 우선한다.
```

### 3.5 오케스트레이션 하네스

기록이 단계별로 흐르는 구조다.

```text
기록 입력 → SAYU 다듬기 → 저장 → 검색·분류 → 통계
→ 주간·월간·분기·연간 합본 → AI 비서실 해석 → 장기 자산화
```

### 3.6 실패 대응 하네스

오류는 모델 탓으로 돌리지 않고, 하네스를 보강하는 재료로 삼는다.

```text
1. 오류 로그를 확인한다.
2. 원인을 기록한다.
3. 같은 오류가 반복되지 않도록 지시문·체크리스트를 보강한다.
4. 필요 시 AGENTS.md / CLAUDE.md 맨 아래에 규칙을 추가한다.
5. 안전장치 우회 명령어를 쓰지 않는다.
6. 막히면 반드시 '왜 막혔는지' 이유를 설명하고 멈춘다.
```

금지 명령: `--force`, `--no-verify`

Vite 빌드에서 `ENOTEMPTY` 오류 시 먼저 1회 시도:

```bash
cd ~/HARU2026/frontend
rm -rf dist
npm run build
```

## 4. 협업 하네스

### 4.1 역할 구분 (현재 배치 — 1.1의 실적 기준 교체 원칙 적용)

| 역할 | 담당 | 책임 |
|---|---|---|
| 총괄·최종결정 | 허대표님 | 최종 방향 · 사용자 감각 · 사업 판단 |
| 전략·설계 | 시박사 | 구조 설계 · 작업 지시문 작성 · 위험 정리 |
| 메인 개발(공장장) | 기장(CCD) | 메인 개발 · 구조 판단 · 핵심 문제 해결 |
| 보조 개발·검수 | CC | 부분 기능 · 검수 보조 · 테스트 |

> 시박사는 지시서에서 '무엇을·왜·어떤 원칙 안에서'를 전달하되, 구체적 구현 방식 판단은 기장에게 맡긴다.

### 4.2 작업 원칙

```text
1. 허대표님의 요청 범위만 수정한다.
2. 요청하지 않은 기능을 임의로 추가하지 않는다.
3. 기존 작동 구조를 함부로 정리하지 않는다.
4. 실제 작동 파일과 좀비 파일을 구분한다.
5. 수정 전 백업한다.
6. 빌드 후 배포한다.
7. main 머지와 feature 브랜치 push까지 완료한다.
8. 안정성 우선 · Firestore 경로 유지 최우선 · 기장의 구조 판단 존중.
```

## 7. AI API 하네스

```text
1. 클라이언트에서 AI API Key 직접 노출 금지
2. Functions 리전은 asia-northeast3 기준

4. 전문 API와 Gemini 역할을 분리한다

6. 공공데이터/전문 API는 사실 기반 담당
```

`getGrammarExplain` 관련 Functions 수정·배포 시, 배포 후 반드시 캐시 삭제 명령 포함:

```bash
firebase firestore:delete grammarCache --recursive --project haru2026-8abb8
```

## 9. 검수 하네스 (이밸루에이터 체계)

### 9.1 검수의 기준 (필수)

```text
- 모든 검수는 작업 지시서의 '완료 조건'을 기준으로 한다.
- 완료 조건이 없으면 검수를 시작하지 말고 완료 조건을 먼저 요청한다.
- 빌드 통과 ≠ 기능 작동. 만든 사람이 아닌 사용자 입장에서 냉정하게 검증한다.
```

### 9.2 기술 검수 명령

```bash
# 웹앱
cd ~/HARU2026/frontend && npm run build
# 모바일
cd ~/HARU2026/mobile && flutter analyze
# Functions
cd ~/HARU2026/functions && npm run build
```

웹과 모바일이 함께 수정되면 각각 별도 검수한다.

### 9.3 기술 검수 항목

```text
1. Firestore 경로 users/{uid}/records/{date} 유지
2. Functions 리전 asia-northeast3 유지
3. 요청 범위 밖 코드 변경 없음
4. 좀비 파일 수정 없음
5. 가격 정책 훼손 없음
6. .env 누락 여부 확인
7. 로그인·기록·SAYU·설정·하단 네비게이션 영향 확인
```

### 9.4 기능 동작 검수 (실제 사용자 입장) — 신규

빌드 통과만으로 끝내지 않고, preview URL에서 직접 검증한다.

```text
- 저장 후 새로고침 → 데이터가 남아있는가
- 빈 입력·잘못된 입력에서 에러가 안 나는가
- 모바일 화면에서 글자 잘림이 없는가
- 이번에 만든 기능이 실제로 의도대로 작동하는가
※ 버튼을 직접 눌러봤는지, 결과를 눈으로 확인했는지 반드시 보고한다.
```

### 9.5 검수 완료 보고 양식

```text
- 빌드: ✅/❌
- 영향 파일: (목록)
- 기술 검수 항목: ✅/❌
- 완료 조건별: ✅/❌ (각 조건의 직접 확인 방법 한 줄)
- 막힌 부분: (있으면 반드시 '왜' 막혔는지 설명하고 멈출 것)
- 최종 판정: 머지 가능 / 수정 필요
```

## 10. Git 하네스

모든 작업은 기본적으로 `feature/new-formats` 브랜치에서 진행한다. 작업 전 `git pull`로 최신 상태를 받고 시작한다.

작업 완료 후 main 머지와 push까지 수행한다.

```bash
cd ~/HARU2026
git checkout main
git merge feature/new-formats
git push origin main
git checkout feature/new-formats
git push origin feature/new-formats
```

원칙: GitHub 원격 저장소 = 진실의 원천 / 작업 전 git pull 필수 / main 직접 수정 금지 / `git add .` 금지(수정 파일만 명시적 add) / 동시 코드 수정 금지.

## 11. 배포 규모 분류

| 규모 | 예시 | 배포 방식 |
|---|---|---|
| 소규모 | 색상·문구·단일 버그 수정 | feature → PR → preview 확인 → merge → 자동배포 |
| 중규모 | 컴포넌트 1~2개 수정 | 로컬 확인 → PR → preview → merge |
| 대규모 | 홈화면 개편·새 기능·라우터 변경 | 허대표님 승인 후 PR → preview → merge |

대규모 작업은 허대표님 승인 없이 직접 배포하지 않는다. 기본 배포는 GitHub Actions 자동배포이며, 수동 firebase deploy는 긴급·복구용 전용이다.

## 13. CC/기장 작업 지시문 표준 형식

시박사가 지시문을 줄 때는 아래 형식을 사용한다.

```text
[1] 작업 목적   - 한 줄로 명확히
[2] 작업 규모   - 소규모/중규모/대규모 + 이유
[3] 수정 대상 파일 - ~/HARU2026/... 경로, 좀비 파일 제외 여부 명시
[4] 수정 지시문  - 백업 명령 / 수정 위치 / before·after / 요청 범위 외 수정 금지
[5] 완료 조건   - '무엇이 충족되면 완성인지' 구체적으로 명시 (이밸루에이터 기준)
[6] 검수·배포 절차 - 빌드/분석 / 영향 페이지 / 경로·리전 확인 / 배포 / Git push
```

> [5] 완료 조건은 9.1 검수 기준과 짝을 이룬다. 완료 조건 없는 지시문은 검수가 시작될 수 없다.

## 14. HARU2026 하네스의 최종 방향

```text
사용자의 삶에서 발생하는 기록을
목적별 형식으로 수집하고,
AI와 전문 API로 해석하며,
통계와 합본으로 장기 자산화하고,
필요한 순간에 비서가 꺼내 쓰는
하네스 기반 AI 라이프 컴파일러.
```

모델은 바뀔 수 있다. Gemini, OpenAI, Claude, 국산 LLM은 언제든 교체될 수 있다. 메인 개발을 맡는 AI도 실적에 따라 교체될 수 있다.

그러나 HARU2026의 기록 구조·저장 구조·비서 구조·검수 구조·사용자 경험 구조는 쉽게 복제하기 어렵다.

**HARU2026의 진짜 자산은 모델이 아니라 하네스다.**
