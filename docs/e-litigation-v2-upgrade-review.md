## 1. 현재 구현 요약

확인 범위: `App.tsx`(라우팅), `LawsuitPracticePage.tsx`, `LegalCasesPage.tsx`, `LegalCaseDetailPage.tsx`, `legalCasesService.ts`, `legalCaseTypes.ts`, `firestore.rules`, `storage.rules`, `functions/src/generateLawsuitClaimReason.ts`, 홈 진입점 3곳.

### A. 전자소송연습 — `/lawsuit-practice` (869줄)

11단계 위저드다.

```
0 로그인(연습) → 1 서류 → 2 사건유형 → 3 동의 → 4 기본정보
→ 5 당사자 → 6 청구취지 → 7 청구원인 → 8 증거 → 9 확인 → 10 제출
```

| 항목 | 실제 구현 상태 |
|---|---|
| 상태 저장 | **전부 `useState` 로컬. Firestore 저장 없음.** 새로고침·이탈 시 전량 소실 |
| 서류 종류 | 민사소장 1종만 활성. 지급명령·답변서·준비서면은 `disabled` |
| 사건유형 | 중고거래 1종만 활성. 임대차·임금체불은 "다음 버전 예정" |
| 사례 안내 | 하단에 6개 사례 카드(대여금·중고거래·물품대금·용역대금·임대차보증금·지급명령) — **안내 텍스트 전용, 흐름과 연결 안 됨** |
| 전문가 상담 경고 | 8개 유형(다투는 사건·고액·손해배상 산정·명도/가압류/가처분·가사·형사연계·계약해석 복잡·기한 중요) 명시 |
| 청구원인 AI | `generateLawsuitClaimReason` (Gemini 3.1-flash-lite, asia-northeast3, 인증필수, CORS allowlist, 입력 sanitize+길이제한, 법조항·판례 인용 금지 프롬프트). `caseType === '중고거래'`만 허용 |
| AI 횟수 제한 | `claimReasonAiRemaining` = **클라이언트 `useState` 3회**. 서버 쿼터 없음 |
| 증거 | 실제 업로드 없음. `DUMMY_EVIDENCE` 5개 문자열을 순서대로 추가하는 시늉 |
| 제출 | `makeMockCaseNumber()` 랜덤 `2026가소XXXXX` |
| 완료 화면 | `buildPracticeTimeline` 5단계 안내 + `/legal-cases` 이동 버튼 (LawsuitPracticePage.tsx:799) |

### B. 제출 후 사건관리 — `/legal-cases`, `/legal-cases/:caseId`

```
users/{uid}/legalCases/{caseId}
users/{uid}/legalCases/{caseId}/documents/{documentId}
```

- **rules**: `firestore.rules:364-370` — `request.auth.uid == uid` 일치 시 read/write. 서브컬렉션 동일. 정상.
- **storage.rules**: `legalCases` 관련 경로 **없음** (1차에서 파일 업로드 제외했으므로 일관됨).
- **목록**: 상태 배지 7종, `오늘 송달 미확인` 배지, 상단 요약 배너, `간편연습 샘플 사건 만들기`.
- **상세 4탭**: 사건정보 / 체크리스트(7항목) / 송달기록 / 보정·기한.
- **기한 표시**: `getUserInputDueLabel()`는 **사용자가 입력한 `dueDateByUserInput`과 오늘의 단순 차이**만 계산. 법정기한 계산 코드 없음.
- **주의 문구**: 사건정보·송달기록·보정·기한 탭 하단에 간주송달/기한 비확정 문구 고정 배치.

## 2. 잘된 점 (그대로 유지할 가치가 있는 부분)

1. **안전선이 문구가 아니라 코드로 지켜지고 있다.**
   `getUserInputDueLabel`은 사용자 입력 날짜 차이만 계산한다. 송달일 추정·초일산입·휴일처리·간주송달 계산 코드는 저장소 어디에도 없다. `generateLawsuitClaimReason` 프롬프트는 법조항 번호·판례 인용을 명시적으로 금지하고, 입력에 없는 인물·금액·일자·장소 생성을 금지한다. **이 설계는 v2에서도 한 글자도 완화하지 않는다.**

2. **전문가 상담 필요 사건 8종 경고.** 이 제품의 법적 리스크를 실질적으로 낮추는 가장 중요한 UI다. 확대·상시 노출 대상.

3. **데이터 경로 분리가 정확하다.** `users/{uid}/records/{date}` 무손상, `legalCases`는 완전 별도 컬렉션, rules도 기존 블록 훼손 없이 추가됨.

4. **Functions 보안 기본기.** 인증 필수 + CORS allowlist + 입력 sanitize + 길이 상한 + 리전 명시. 신규 AI 기능도 이 틀을 그대로 따르면 된다.

5. **연습 → 관리 링크가 이미 존재한다.** 통합의 씨앗은 이미 심겨 있다. 문제는 그 반대 방향과 진입점이다.

## 3. 부족한 점 (사용자 관점)

### 🔴 매우 중요

**3-1. `/legal-cases`에 홈 진입점이 없다.**
홈 카드 3곳(`HomePage.tsx:71`, `HomePageV2.tsx:326`, `assistantRecommendations.ts:59`)이 **전부 `/lawsuit-practice`만 가리킨다.** `/legal-cases`를 가리키는 곳은 `LawsuitPracticePage.tsx:799`(모의제출 완료 화면) 하나뿐이다.

> 이미 소송을 제출한 사용자가 사건관리 화면에 도달하려면, **연습 11단계를 전부 통과해 모의 사건번호를 받아야 한다.**

허대표님의 6절 가설이 코드로 확인됐다. 두 기능은 "분리"된 게 아니라 사건관리가 사실상 **은닉**돼 있다. 가장 먼저 고칠 항목.

**3-2. "오늘 할 일"이 없다.**
진입 시 첫 화면이 사건 DB 목록이다. `todayUncheckedCount` 배너가 유일한 오늘 신호인데 "N건 있습니다"로 끝나고 **클릭도 안 된다**(`<div>`). 기한 임박 문서는 목록 화면에 전혀 노출되지 않고, 사건 상세의 보정·기한 탭까지 들어가야 보인다.

**3-3. 연습 결과가 1바이트도 남지 않는다.**
청구취지·청구원인·증거목록을 힘들게 작성해도 새로고침 한 번에 사라진다. AI 초안 3회를 다 써서 만든 문장도 마찬가지다. HARU2026 핵심 철학 **"내 기록이 가치 있어졌다고 느끼게 하는 앱"**과 정면으로 충돌한다. 연습 결과를 사건으로 승격하는 경로도 없다.

**3-4. 법원 문서를 받은 사용자를 위한 입구가 없다.**
현재 구조는 사용자가 **스스로** 문서 종류를 판단하고, 기한 문구를 읽어내고, 폼에 옮겨 적어야 한다. 초보자에게 가장 어려운 지점을 그대로 사용자에게 남겨두고 있다. 허대표님이 지목한 세 번째 입구가 필요한 이유가 여기 있다.

### 🟡 중요

**3-5. 진행 위치가 보이지 않는다.** `status`는 드롭다운 7개 값일 뿐이다. `준비→제출→접수→송달→대응→종결` 어디인지 시각화가 없고, 상태 전이 규칙도 없어 `제출준비`에서 `종결`로 바로 점프된다.

**3-6. 송달기록 탭과 보정·기한 탭이 사실상 같은 목록이다.** 송달기록 탭은 `documents` **전체**를 필터 없이 보여준다(LegalCaseDetailPage.tsx:542). 보정·기한 탭만 `deadlineDocuments`로 거른다. 보정명령을 등록하면 양쪽에 다 뜬다.

**3-7. AI 횟수 제한이 클라이언트에만 있다.** `claimReasonAiRemaining`은 `useState`다. 새로고침하면 3회가 복구된다. 서버 쿼터도, 구독 게이트도 없다. 하루LAW는 프리미엄 일 5회 제한이 있는데 이 기능만 사실상 무제한 호출이 가능하다. **비용·남용 리스크.**

**3-8. 샘플 사건 체크리스트가 메모 문자열이다.** `createSampleLegalCase`가 `"□ 사건명과 사건유형을 확인했다"` 같은 텍스트를 `memo` 필드에 통째로 박는다(legalCasesService.ts:159-175). 체크 불가, 진행률 계산 불가.

**3-9. 연습 사건유형이 중고거래 1종뿐이다.** 화면은 6개 사례를 소개하지만 실제 흐름과 AI는 중고거래만 받는다. 특히 **지급명령**은 나홀로 소송 수요가 가장 큰데 비활성이고, 사건관리 쪽 `LegalCaseType`에는 이미 `'지급명령'`이 있어 양쪽이 어긋난다.

### 🟢 보완

- **3-10.** 목록 정렬이 `updatedAt desc` 고정. 기한 임박순 정렬 없음.
- **3-11.** `updateDocument`/`deleteDocument`가 서비스에 있으나 UI에서 호출되지 않는다. 문서 오타를 고칠 방법이 없다(완료 체크박스만 가능).
- **3-12.** `deleteLegalCase` 미사용. 사건 삭제 UI 없음 → **개인정보 삭제 요청 대응 불가.**
- **3-13.** `LegalCaseDetailPage.statusClassName`에 `'제출준비'` case 누락 → 목록은 보라, 상세는 회색.
- **3-14.** 상세 탭이 URL에 없어 새로고침 시 항상 사건정보 탭으로 돌아간다.

## 4. 목표 UX 구조 — 3개 입구

전자소송비서 홈을 세 입구로 재설계한다. **기존 두 페이지를 버리지 않고 각 입구의 목적지로 재배치**하는 방식이다.

| 입구 | 사용자 상태 | 목적 | 목적지 |
|---|---|---|---|
| ① 새로 소송을 준비하고 있어요 | 아직 제출 전 | 절차 이해 + 서류 연습 + 제출 전 점검 | 기존 `/lawsuit-practice` (+ 결과 저장 추가) |
| ② 이미 소송을 제출했어요 | 제출 완료, 진행 중 | 진행 놓치지 않기 | 기존 `/legal-cases` (+ 직접 진입) |
| ③ 법원에서 문서를 받았어요 | 문서 수령, 무엇을 할지 모름 | 문서 이해 → 체크리스트 → 기록 | **신규** `/legal-cases/document-helper` |

**세 입구를 잇는 연결선(가장 중요):**

```
① 연습 완료 ──[이 내용으로 사건 만들기]──→ ② 사건 (status: 제출준비)
③ 문서 등록 ──[이 사건에 연결]──────────→ ② 사건 문서/기한
② 사건 상세 ──[이 절차 다시 연습하기]───→ ①
```

현재는 ①→② 링크 하나만 있고, 그마저도 **데이터를 옮기지 않는 단순 이동**이다. v2의 핵심은 이 연결선에 데이터를 흘려보내는 것이다.

## 5. 화면 구조

### 5-1. 전자소송비서 홈 (신규) — `/legal-assistant`

| 항목 | 내용 |
|---|---|
| 목적 | "지금 내가 어디에 있는지" 30초 안에 판단시키기 |
| 주요 정보 | 오늘 할 일 요약(최대 3건) / 3개 입구 카드 / 전문가 상담 필요 사건 경고 배너 |
| 버튼 | `오늘 할 일 전체보기` `새로 준비 중이에요` `이미 제출했어요` `법원 문서를 받았어요` |
| 사용자 행동 | 자기 상황에 맞는 카드 1개 선택 |
| 다음 화면 | 오늘 할 일 / `/lawsuit-practice` / `/legal-cases` / 문서 도우미 |

> 홈 카드 3곳(`HomePage.tsx:71`, `HomePageV2.tsx:326`, `assistantRecommendations.ts:59`)의 목적지를 `/lawsuit-practice` → `/legal-assistant`로 바꾼다. **기존 두 페이지의 URL은 그대로 살려둔다**(북마크·기존 링크 보존).

### 5-2. 오늘 할 일 — `/legal-assistant` 내 섹션 + 전체보기

| 항목 | 내용 |
|---|---|
| 목적 | 사건 DB가 아니라 **오늘의 행동**을 보여준다 |
| 주요 정보 | 사건명 / 상태 / **사용자가 입력한 기한** / 확인 필요 항목 / 진행 `2/5 완료` |
| 버튼 | `확인하기`(사건 상세로) `오늘 확인했습니다`(`lastCheckedAt` 갱신) |
| 사용자 행동 | 항목 1개 처리 후 즉시 반영 |
| 다음 화면 | 사건 상세 해당 탭 |

**생성 규칙 (AI 판단·기한 계산 일절 없음, 전부 기존 저장값의 단순 조회):**

| 카드 종류 | 조건 (전부 이미 저장된 값) |
|---|---|
| 송달 확인 | `status ∉ {종결, 보류}` AND `lastCheckedAt ≠ 오늘` |
| 기한 임박 | `documents.dueDateByUserInput` 존재 AND `isCompleted === false` AND (입력일 − 오늘) ≤ 3 |
| 기한 경과 | 위와 같고 (입력일 − 오늘) < 0 → **"입력된 기한이 지났습니다 (기한 직접 확인 필요)"** 문구 유지 |
| 대응 미완료 | `requiresAction === true` AND `isCompleted === false` |
| 체크리스트 미완 | `checklistSubmit`에 `false`가 있고 `status === '제출완료'` |

> ⚠️ **"기한 임박"의 기준은 오직 사용자가 직접 입력한 날짜다.** AI가 문서에서 뽑은 날짜를 기한으로 승격시키지 않는다. 이 규칙이 v2 전체의 안전 축이다.

### 5-3. 사건목록 — `/legal-cases` (기존 개선)

| 항목 | 내용 |
|---|---|
| 목적 | 전체 사건 조망 |
| 주요 정보 | 사건명 / 사건번호 / 법원 / 상태 배지 / 진행지도 미니바 / 마지막 송달확인일 / 기한 임박 배지 |
| 버튼 | `+ 사건 추가` `정렬(기한임박순 / 최근수정순)` |
| 사용자 행동 | 사건 선택 |
| 다음 화면 | 사건 상세 |

추가: **사건 삭제**(3-12 대응, 2단계 확인 필수), 기한 임박순 정렬(3-10).

### 5-4. 사건 상세 — `/legal-cases/:caseId` (기존 유지 + 진행지도)

기존 4탭 구조를 **유지**한다. 상단에 진행지도를 얹고, 탭 상태를 URL 쿼리(`?tab=deadline`)로 보존한다(3-14).

송달기록 탭 필터를 명확히 한다(3-6). **저장 필드를 추가하지 않고 `documentType` 기준으로 분류 규칙만 확정**하는 방향을 권고한다(마이그레이션 불필요):

| 탭 | 표시 대상 |
|---|---|
| 송달기록 | 전체 문서 (수령 기록 관점) — 단 "보정·기한 항목"은 별도 배지로 구분 표시 |
| 보정·기한 | 현행 `deadlineDocuments` 필터 유지 |

### 5-5. 사건 진행지도 (사건 상세 상단, 신규 컴포넌트)

```
준비 ✓ → 제출 ✓ → 접수 ✓ → 송달 ● → 대응 → 종결
```

**기존 `status` 7값을 6단계에 매핑한다. 저장 필드 추가 없음(파생값).**

| status | 단계 |
|---|---|
| 제출준비 | 준비 |
| 제출완료 | 제출 · 접수 |
| 송달확인중 | 송달 |
| 보정필요 / 추가서류필요 | 대응 |
| 종결 | 종결 |
| 보류 | (진행 정지 — 회색 전체 표시) |

그 아래 고정 문구:

```
다음으로 확인할 것
전자송달 문서를 확인하세요.
마지막 확인: 2026년 7월 31일
[오늘 확인했습니다]
```

> ⚠️ "다음으로 확인할 것"은 **status → 안내문 고정 매핑 테이블**로 만든다. AI가 생성하지 않는다. 이 문구가 법적 조언으로 읽히지 않도록 "확인하세요" 형태로만 쓰고, 절차 진행을 단정하지 않는다.

### 5-6. 법원 문서 도우미 (신규) — `/legal-cases/document-helper`

| 항목 | 내용 |
|---|---|
| 목적 | 문서를 받은 사용자가 **다음 행동**을 이해하게 한다 |
| 주요 정보 | 3단 구성: ①문서에서 확인된 정보 ②확인할 일 ③HARU 기능 |
| 버튼 | `사진 등록` `체크리스트 만들기` `기한 기록하기` `이 사건에 연결` |
| 사용자 행동 | 등록 → **추출 결과 검토·수정** → 사건에 저장 |
| 다음 화면 | 사건 상세 (보정·기한 탭) |

**화면 문구 골격:**

```
문서에서 확인된 정보  ※ 아래는 AI가 문서에서 읽어낸 후보입니다. 반드시 원문과 대조하세요.
  문서 종류(후보)   보정명령        [수정]
  법원              ○○지방법원      [수정]
  사건번호          2026가단12345   [수정]
  문서에 표시된 날짜 2026.07.28.     [수정]
  기한 관련 문구     "송달일부터 7일 이내"   ← 원문 그대로 인용
  요구사항          주소 보정, 주민등록초본 제출

  ⚠️ 문서에는 '송달일부터 7일 이내'라고 기재되어 있습니다.
     정확한 기준일과 기간 계산은 법원 문서 및 전자소송포털 안내를 확인하세요.
     [내가 확인한 기한 직접 입력하기]  ← 여기서만 dueDateByUserInput이 생긴다
```

**절대 규칙 3가지:**
1. 추출은 **문구 인용**까지. 날짜 계산·확정은 하지 않는다.
2. `2026.08.05.`처럼 **문서에 명시된 절대 날짜**만 "문서에 표시된 날짜"로 뽑는다. 상대 기간("송달일부터 7일")은 **원문 문구 그대로 인용만** 하고 날짜로 변환하지 않는다.
3. AI가 뽑은 어떤 날짜도 `dueDateByUserInput`에 **자동 기입하지 않는다.** 사용자가 별도 필드에 직접 입력할 때만 기한이 된다.

### 5-7. 보정 체크리스트 (2차 후보, 화면 설계만)

| 항목 | 내용 |
|---|---|
| 목적 | 보정명령 요구사항을 항목으로 나눠 진행률 관리 |
| 주요 정보 | 항목별 체크 / `2 / 6 완료` / 사용자 입력 기한 |
| 버튼 | `항목 추가` `완료 기록` |
| 사용자 행동 | 항목 체크 |

> 항목은 **법원 문서에 적힌 요구사항**에서만 만든다. "법적으로 이것도 필요하다" 류의 AI 추가는 금지.

## 6. 데이터 구조 영향

### 6-1. 기존 구조로 그대로 가능한 것

| 기능 | 사용하는 기존 필드 |
|---|---|
| 오늘 할 일 | `status`, `lastCheckedAt`, `checklistSubmit`, `documents.dueDateByUserInput` / `.isCompleted` / `.requiresAction` |
| 진행지도 | `status` (파생 매핑, 저장 없음) |
| 기한 임박순 정렬 | `documents.dueDateByUserInput` (클라이언트 정렬) |
| 사건 삭제 | `deleteLegalCase` (이미 존재, UI만 없음) |
| 문서 수정/삭제 | `updateDocument` / `deleteDocument` (이미 존재, UI만 없음) |
| 연습 결과를 사건으로 저장 | `status: '제출준비'` 값이 이미 타입에 존재 |

**즉 1차 핵심 3기능(홈 3입구 / 오늘 할 일 / 진행지도)은 저장 구조 변경 없이 구현 가능하다.**

### 6-2. 추가 필드가 필요한 것 (⚠️ 이 문서에서 확정하지 않음 — 코장 설계 후 허대표 승인)

| 용도 | 필요한 것 | 성격 |
|---|---|---|
| 연습 결과 저장 | `LegalCase`에 청구취지·청구원인·증거목록을 담을 자리 (예: `practiceDraft` 맵) | 신규 optional 필드. 기존 문서 영향 없음, 마이그레이션 불필요 |
| 문서 추출 결과 보관 | `documents/{id}`에 "AI가 읽어낸 후보" 보관 자리 (예: `extractedHints` 맵) | **`dueDateByUserInput`과 반드시 물리적으로 분리된 필드여야 함** |
| 보정 체크리스트 | 요구사항 항목 배열 | 2차 |

### 6-3. 성능 주의

"오늘 할 일"은 사건 N개마다 `documents` 서브컬렉션을 읽어야 해 **N+1 쿼리**가 된다. 개인 사용자의 사건 수가 적으므로 1차는 허용 가능하나, `collectionGroup('documents')` 전환은 **rules 추가가 필요**하므로 별도 검토 대상이다(현재 rules로는 collectionGroup 쿼리가 막힌다).

### 6-4. 불변 원칙

- `users/{uid}/records/{date}` — **변경 없음.** v2 어느 기능도 이 경로를 건드리지 않는다.
- `users/{uid}/legalCases/...` 기존 필드 — 이름·의미 변경 없음. 추가만.

## 7. AI 처리 구조 (법원 문서 도우미)

### 7-1. 흐름

```
사용자 사진 등록
   ↓ (base64, 클라이언트 → Functions 직접 전달. Storage 경유 안 함)
Functions: extractCourtDocumentHints (신규, asia-northeast3)
   ↓ Gemini에 이미지 + 추출 전용 프롬프트
텍스트 추출 결과(JSON) — "후보"로만 표기
   ↓
프론트: 사용자에게 전부 노출 + 항목별 [수정] 제공
   ↓ 사용자가 확인·수정·승인
사건 문서로 저장 (extractedHints)
   ↓ 사용자가 별도로 직접 입력할 때만
dueDateByUserInput 생성 → 오늘 할 일에 반영
```

### 7-2. 이미 있는 안전 패턴을 그대로 재사용한다

`functions/src/index.ts`의 **`extractLedgerTextFromImage`(가계부 영수증 OCR)** 가 정확히 같은 문제를 이미 풀어놨다. 신규 Function은 이 패턴을 복사한다:

| 패턴 | 위치 |
|---|---|
| MIME allowlist (jpg/png/webp) | index.ts:3180 |
| 장당 7MB 상한 / 최대 3장 | index.ts:3171, 3191 |
| **base64는 메모리에만. Storage 저장 안 함** | index.ts:3175-3202 |
| **호출 후 `inlineData.data = ''` 로 스크럽** (로그·에러에 원문 유출 차단) | index.ts:3205-3210 |
| 인증 필수 + CORS allowlist + 리전 명시 | generateLawsuitClaimReason.ts:23-33 |

**이 결정의 의미: 법원 문서 원본 이미지를 서버에 저장하지 않는다.** Storage rules 신설, 파일 삭제 정책, 백업 보관 범위 문제가 통째로 사라진다. 1차에서는 **저장하지 않는 설계**를 강력히 권고한다.

### 7-3. 프롬프트 규칙 (필수)

**허용:** 문서 종류 후보 분류 / 법원명 추출 / 사건번호 추출 / **문서에 인쇄된 절대 날짜** 추출 / 기한 관련 **문구 원문 인용** / 요구사항 항목 정리 / 요약

**금지 (프롬프트에 명시):**
- 날짜 계산·기한 확정 (`송달일 + 7일` 같은 연산 일절 금지)
- 간주송달일 추정
- 법조항·판례 인용
- 문서에 없는 사실 생성
- 승소 가능성·법적 효과 언급
- "언제까지 하셔야 합니다" 류 단정 표현
- 마크다운 기호 (기존 HARUraw 원칙과 동일)

**출력은 순수 JSON.** 각 필드에 `confidence` 대신 **원문 인용 근거(`sourceText`)** 를 함께 담아 사용자가 대조할 수 있게 한다. (신뢰도 점수는 "AI가 확신함"으로 오독될 수 있어 권하지 않는다.)

### 7-4. 쿼터

3-7 문제와 함께 처리한다. `generateLawsuitClaimReason`과 신규 Function 모두 **서버 측 일일 호출 카운트 + 구독 등급 게이트**를 붙인다. 하루LAW(프리미엄 일 5회) 패턴을 따르되 등급·횟수는 허대표 결정 사항.

### 10-6. 위험 사항 (코장 주의)

1. **기한 계산 로직을 절대 새로 만들지 말 것.** 오늘 할 일의 D-day는 `getUserInputDueLabel`과 **동일한 계산 방식만** 쓴다. 별도 구현 금지 — 공용 함수로 추출해 한 곳에서만 계산한다.
2. `LawsuitPracticePage.tsx`는 **버튼 1개 추가**까지만. 위저드 상태·조건부 렌더링 건드리면 중단하고 보고.
3. 홈 진입점 3곳 중 하나라도 빠뜨리면 사용자가 옛 경로로 계속 들어온다. 3곳 모두 확인.
4. 사건 삭제는 되돌릴 수 없다. 2단계 확인 + 사건명 표시 필수.
5. `collectionGroup` 쿼리는 **현재 rules로 막힌다.** 1차에서 쓰지 말 것.
6. `documents` 저장 필드를 새로 추가하는 방향(송달/보정 구분자 등)은 **마이그레이션 이슈**가 있으므로, 1차에서는 `documentType` 기반 분류 규칙으로 해결하고 필드 추가는 하지 않는다.

## 11. 최종 판단 기준 점검

> "전자소송을 처음 하는 사람이 이 비서를 보고 **'지금 내가 무엇을 해야 하는지 알겠다'**고 느끼는가?"

**현재:** 아니오. 홈에서 들어가면 11단계 연습 위저드가 시작되고, 실제 사건을 가진 사용자는 자기 자리를 찾지 못한다.

**1차 이후:** 예. 홈에서 자기 상황(준비 중 / 제출함 / 문서 받음)을 고르고, 사건이 있으면 오늘 할 일 3건이 바로 보이고, 사건을 열면 지도에서 자기 위치가 보인다.

> HARU2026 핵심 철학 **"내 기록이 가치 있어졌다고 느끼게 하는 앱"** 과의 연결:
> `기록 → 정리 → 진행상태 → 다음 행동`. 현재는 "기록"에서 멈춰 있다. 진행지도가 "진행상태"를, 오늘 할 일이 "다음 행동"을 담당한다. 연습 결과 저장(1-6)이 이 사슬의 첫 고리다.
