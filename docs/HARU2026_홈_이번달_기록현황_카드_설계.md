## 1. 목적과 범위

**무엇을**: 로그인 후 홈의 '내 하루기록' 탭이 지금은 비어 있다(기록 영역이 '전체 보기'에서만 그려진다). 이 탭 안에 "이번 달 n편"과 "이번 달 최근 기록 3개"를 보여 주는 카드를 넣는다.

**왜**: 기록을 써도 홈에서 쌓이는 보람이 보이지 않는다. 핵심 철학 "내 기록이 가치 있어졌다고 느끼게 하는 앱"이 홈에서 드러나지 않는다.

**하지 않는 것**
- "월간 생활문서까지 n편" 같은 목표·달성 문구. 20편에서 월간 문서가 자동 생성된다는 조건은 코드에 없다(안내 페이지의 20개는 예시).
- 새 AI 호출, 새 저장 필드, 새 Firestore 컬렉션, 저장 경로 변경, 마이그레이션, Rules 변경. **읽기 전용**이다.
- 지난달 기록 표시(월 0건일 때). 필요하면 별도 제한 조회가 필요하므로 이번 범위에서 뺀다.
- '전체 보기' 탭에는 카드를 넣지 않는다.
- 비서가 만든 기록(AI 로그, 결과 대화 메모, 성장타임라인)과 가계부·보조장부·주식 기록은 세지 않는다.

### 이 사실들이 만드는 문제 두 가지

1. **캐시 무효화가 어렵다.** 기장은 "uid+월+집계기준 키, 메모리 TTL 5분, 저장·수정·삭제 후 무효화"를 권고했다. 그런데 기록을 쓰는 곳이 13개 파일에 흩어져 있어서, 한 곳에서 무효화하면 나머지 경로로 쓴 기록은 최대 5분 동안 홈에 반영되지 않는다. 사용자가 가장 자주 겪을 장면이 "방금 쓴 기록이 홈에 안 보임"이다.
2. **월 범위 조회는 비서 기록까지 전부 읽는다.** 서버 쿼리가 기록 형식으로 거르지 않기 때문에, 가계부·AI 로그가 많은 계정은 "n편"에 들어가지 않는 문서까지 읽는다. 통계 화면도 같은 방식이지만 홈은 방문 빈도가 훨씬 높다.

**탭하면**: `navigate('/sayu', { state: { filterFormat: <그 기록의 한글 형식명>, openRecordId: <문서 id> } })`. SAYU가 이미 이 상태를 받아 그 기록의 월·형식으로 연다(`SayuPage.tsx:2576-2638`).

## 4. 데이터 설계

### 4.1 무엇을 세는가
- **편 = 문서 id를 중복 제거한 수**. 하루 = 1편이 아니고(`{date}_{type}_{timestamp}` 문서가 있을 수 있음), 형식 수·날짜 수와 다르다.
- 포함 조건: `STATS_MERGE_RECORD_FORMATS.some((format) => recordHasFormat(record, format))`. 즉 통계·합본과 같은 기준이다.
- `hasSayu`(SAYU 완료)는 합본의 완료 조건이므로 작성 현황 수에는 더하지 않는다.
- 기간: `getStatsPeriodRange('month', now)`의 `start`~`end`(월초~오늘). `-31` 같은 가짜 월말이나 미래 날짜를 쓰지 않는다.

```ts
// 제안(적용 안 함)
const range = getStatsPeriodRange('month', now);           // { start: '2026-11-01', end: '2026-11-06' }
const mine = docs
  .filter((r) => STATS_MERGE_RECORD_FORMATS.some((f) => recordHasFormat(r, f)))   // 비서 기록 제외 포함
  .sort(byDateDescThenUpdatedAtDesc);
const count = new Set(mine.map((r) => r.id)).size;
const recent = mine.slice(0, 3);
```

### 4.2 최근 3건의 제목·형식
- 형식: 문서의 `formats` 순서에서 처음 나오는 11종 중 하나. 한글 형식명(예: `일기`)을 그대로 쓴다. 카드의 SAYU 이동 상태에도 같은 이름을 쓴다.
- 제목: `{prefix}_title`이 있으면 그것(20자), 없으면 `getOriginalBody(record, format)`의 첫 줄(20자), 그것도 없으면 `(내용 없음)`.
- 같은 날짜 안의 순서는 `updatedAt`(있으면), 없으면 문서 id.
- SAYU 목록의 제목 규칙(`SayuPage.tsx:3255-3295`, AI 제목 포함)을 그대로 복제하지 않는다. 카드용으로 단순하게 만들고, 두 곳의 제목이 다를 수 있음을 문서에 남긴다.

### 4.3 조회 방식 세 가지와 비용

M = 이번 달 `users/{uid}/records` 문서 수(비서 기록 포함). 읽기 횟수는 **방문(홈이 마운트될 때)마다 M**이 기본이다. Firestore는 메모리 캐시만 쓰므로 홈을 떠났다 돌아오면 다시 읽는다.

| 안 | 방식 | 신선도 | 읽기 | 구현 복잡도 | 문제 |
|---|---|---|---|---|---|
| **A** | `getRecordsInRange` 한 번 + 메모리 TTL 5분 + 저장·수정·삭제 후 무효화(기장 권고) | 무효화한 경로만 즉시. 놓친 경로는 최대 5분 | 홈 마운트 중 TTL 안이면 0, 아니면 M | 중 (13개 쓰기 경로 중 무효화 위치 선정) | 가장 흔한 장면(방금 쓰고 홈으로)에서 낡은 값 위험 |
| **B** | `onSnapshot`으로 월 범위 구독(홈이 보이는 동안만) | **항상 최신**. 내 쓰기는 대기 중 쓰기 포함해 즉시 반영 | 마운트마다 M + 구독 중 바뀐 문서당 1 | 중 (`useSnsRecords`와 같은 패턴) | 마운트마다 M. 구독 중 비서 기록 변경도 1건씩 읽음 |
| **C** | `getRecordsInRange` 한 번, 캐시 없음 | 마운트 안에서만 | 마운트마다 M | 하 | 홈 방문이 잦을수록 읽기 증가, 방금 쓴 기록은 다음 마운트에 반영 |

**CC 권고: B로 시작한다.** 이유는 무효화 코드를 13개 파일에 넣지 않아도 항상 최신이 되기 때문이다. 읽기 횟수는 C와 같은 수준(마운트마다 M)이고, 홈에서 머무는 동안 바뀐 문서만 추가로 읽는다. 기장의 A는 안전한 절충이지만 무효화 누락 위험이 있어 "13개 경로를 모두 다룰 수 있는가"에 대한 기장의 판단을 묻는다.

> 읽기 비용을 단가로 환산하지 않는다. 하루 읽기 ≈ 활성 사용자 수 × 하루 홈 마운트 횟수 × M(+ 구독 중 변경분). 예: 1,000명 × 5회 × 30건 = 150,000 읽기/일. 단가와 무료 할당은 Firebase 요금표로 따로 확인해야 하며 이 문서는 확정하지 않는다.

### 4.4 읽기를 줄이는 2단계 (구현 후 측정해서 필요할 때만)
- **서버 쪽에서 형식으로 거르기**: `where('formats', 'array-contains-any', STATS_MERGE_RECORD_FORMATS)` + 날짜 범위. 11개라 `array-contains-any` 한도(30) 안이다. 의미는 `recordHasFormat`의 `formats` 배열 조건과 같다(비서 기록 제외는 클라이언트에서 계속). **복합 인덱스(formats + date)가 필요**하고 `firestore.indexes.json` 변경과 인덱스 배포가 따른다. 인덱스 배포는 대표님 확인이 필요한 별도 작업으로 다룬다.
- **개수만 서버 집계(`count()`)**: 비서 제외 조건이 세 필드 값 비교이고 과거 문서는 그 필드가 없을 수 있어 `!=`·`not-in`을 붙이면 누락될 수 있다. 현재 데이터에서 클라이언트 필터와 같은 값이라고 선언할 수 없으므로 **지금은 쓰지 않는다.**

### 4.5 구독 수명과 계정·월 변경
- 구독은 `homeViewMode === 'my'`이고 로그인했고 온보딩 확인이 끝난 동안만 연다. '전체 보기'로 바꾸거나 홈을 떠나면 해제한다.
- 계정이 바뀌면(`uid`) 즉시 해제하고 새로 연다. 이전 계정의 결과를 한 순간도 그리지 않는다(`useSnsRecords`의 세션 비교 패턴).
- 월이 바뀌면(자정 이후 홈에 머물러 있을 때) `now`(`HomePageV2.tsx:555`, 1분마다 갱신)에서 월 키를 만들어 다시 연다.
- 개인정보를 공용 `localStorage`에 남기지 않는다. 메모리 안에서만 다룬다.
- 오프라인: `snapshot.metadata.fromCache`이고 비어 있으면 "불러오는 중", 서버 확정 전 값은 0건으로 단정하지 않는다.

## 6. 결정이 필요한 것

**기장께**
1. 조회 방식: CC는 **B(구독)** 를 권고한다. 13개 쓰기 경로 때문에 A의 "저장 후 무효화"가 누락될 수 있다는 근거(2절)에 대한 판단. A를 고집한다면 무효화할 경로 목록을 정해 주기 바란다.
2. 구독을 홈 마운트 동안만 연다는 수명 설계가 맞는지, 비서 기록이 많은 계정의 마운트당 읽기 M을 허용할 수 있는지.
3. 2단계(`formats` 배열 서버 필터 + 복합 인덱스)를 1차 구현에 넣을지, 측정 후로 미룰지. CC는 측정 후를 권고한다.
4. 제목 규칙(4.2)이 SAYU 목록 제목과 달라도 되는지.

**허대표님께**
1. 카드 문구와 위치(3절)가 맞는지. 특히 0건 문구 "이번 달 아직 남긴 기록이 없어요. 오늘의 한 줄부터 시작해 보세요."
2. 비서 기록·가계부·주식을 "n편"에 넣지 않는 기준이 맞는지(통계·합본과 같은 11종).
3. 월 0건일 때 지난달 기록을 보여 주지 않는 범위가 맞는지.
4. 읽기 비용을 구현 후 측정해서 필요하면 2단계로 줄이는 순서에 동의하는지. 인덱스 배포가 필요해지면 별도 승인이 필요하다.
