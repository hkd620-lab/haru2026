## 1. 목적과 범위

**무엇을**: 로그인 후 홈의 '내 하루기록' 탭에는 작성칸(`HomePageV2.tsx:1093`)과 비서실(`:1249`)만 그려지고, **기록 영역은 '전체 보기'에서만 그려진다**(`:1152`). 이 탭 안에 "이번 달 n편"과 "이번 달 최근 기록 3개"를 보여 주는 카드를 넣는다.

**왜**: 기록을 써도 홈에서 쌓이는 보람이 보이지 않는다. 핵심 철학 "내 기록이 가치 있어졌다고 느끼게 하는 앱"이 홈에서 드러나지 않는다.

**하지 않는 것**
- "월간 생활문서까지 n편" 같은 목표·달성 문구. 20편에서 월간 문서가 자동 생성된다는 조건은 코드에 없다(안내 페이지의 20개는 예시).
- 새 AI 호출, 새 저장 필드, 새 Firestore 컬렉션, 저장 경로 변경, 마이그레이션, Rules 변경. **읽기 전용**이다.
- 지난달 기록 표시(월 0건일 때). 필요하면 별도 제한 조회가 필요하므로 이번 범위에서 뺐다.
- '전체 보기' 탭에는 카드를 넣지 않는다.
- 비서가 만든 기록(결과 대화 메모, 성장타임라인)과 가계부·보조장부·주식 기록은 세지 않는다.

### 이 사실들이 만드는 문제 두 가지

1. **캐시 무효화가 어렵다.** 기장은 "uid+월+집계기준 키, 메모리 TTL 5분, 저장·수정·삭제 후 무효화"를 권고했다. 그런데 기록을 쓰는 곳이 클라이언트 13개 파일에 흩어져 있고, **Functions와 다른 기기·탭이 쓴 기록은 클라이언트 무효화로 원천적으로 잡을 수 없다.** 놓치면 최대 5분 동안 홈에 반영되지 않는다. 가장 흔한 장면이 "방금 쓴 기록이 홈에 안 보임"이다.
2. **월 범위 조회는 "n편"에 안 들어가는 비서 문서도 읽는다.** 서버 쿼리가 형식으로 거르지 않으므로 결과 대화 메모·성장타임라인·가계부 월 문서·보조장부·주식 문서가 함께 내려온다(AI 로그는 `date`가 없어 제외). 특히 가계부 월 문서는 크고, 구독 중 가계부를 저장할 때마다 문서 전체가 다시 내려온다(읽기 1회 + 전송량). 통계 화면도 같은 방식이지만 홈은 방문 빈도가 훨씬 높다.

## 3. 화면 설계

**위치**: '내 하루기록' 탭이 선택됐을 때(`homeViewMode === 'my'`), 탭 토글(`HomePageV2.tsx:1116-1146`) 바로 아래, 비서실 영역(`:1248` 주석, 조건 `:1249`) 위. 개인화 스켈레톤(`:1149`)이 끝난 뒤에 그린다. '전체 보기'에서는 카드만 숨긴다(구독은 유지, 4.5).

```
 [내 하루기록] [전체 보기]

 ┌──────────────────────────────────────────┐
 │ 이번 달 기록                              │
 │ 7편                         11월 1일~6일  │
 │ ──────────────────────────────────────── │
 │ 일기 · 11/6      산책하며 든 생각          │  → 눌러서 SAYU에서 열기
 │ 메모 · 11/5      병원 예약 확인            │
 │ 독서사유 · 11/4  어린 왕자                 │
 └──────────────────────────────────────────┘
```

| 상태 | 표시 | 비고 |
|---|---|---|
| 불러오는 중 | 자리만 잡은 스켈레톤(`aria-busy="true"`). **숫자를 보여 주지 않는다** | 아래 3.1 규칙 |
| 1건 이상 | "이번 달 기록 n편" + 최근 3건(형식·날짜·제목) | 3건 미만이면 있는 만큼만 |
| 0건 | "이번 달 아직 남긴 기록이 없어요. 오늘의 한 줄부터 시작해 보세요." + 기존 작성 동선 버튼(홈 입력칸으로 이동) | 서버 확정 후에만. 지난달 기록은 보여 주지 않는다 |
| 조회 실패 | "기록 현황을 불러오지 못했어요" + `다시 시도` 버튼(`role="alert"`). 이미 보여 준 값이 있으면 그 값은 유지하고 "마지막으로 확인한 시각 HH:mm"을 덧붙인다 | **0건과 구분한다**. 다시 시도 = 구독을 새로 연다 |
| 비로그인·온보딩 확인 전 | 카드를 그리지 않는다 | 기존 `ready` 조건 재사용 |

문구 원칙: 새 약속·목표를 만들지 않는다("n편째"·"월간 문서까지" 금지). 14px 이상, 진한 글색(기존 12~13px 연회색 보조 글씨를 쓰지 않는다).

**접근성**: 최근 기록 행은 `button` 요소, 카드 제목은 영역 이름(`aria-labelledby`), 불러오는 중 `aria-busy`, 실패 `role="alert"`, 개수 갱신은 `aria-live="polite"`. 기존 `tablist`(`HomePageV2.tsx:1129`)와 카드를 `tabpanel`로 연결할지는 구현 때 기존 마크업과 맞춰 정한다.

**탭하면**: `navigate('/sayu', { state: { filterFormat: <그 기록의 한글 형식명>, openRecordId: <문서 id> } })`. SAYU가 이미 이 상태를 받아 그 기록의 월·형식으로 연다(`SayuPage.tsx:2575-2641`). 두 가지를 알고 간다: SAYU는 마운트할 때 전체 컬렉션을 읽고(`getRecords`, `:2180`), 라우트 처리 시점에 기록을 못 찾으면 한 번 더 읽는다(`:2607`). 카드가 이 진입로를 늘리므로 전체 읽기 빈도가 늘 수 있다(4.3 비용). 못 찾았을 때 안내가 "저장한 메모를 찾지 못했습니다"(`:2612`)로 메모 전용 문구라 일기 등에서는 어색하다. 이 문구는 이번 범위에서 고치지 않고 후속으로 남긴다.

### 3.1 숫자를 보여 주는 조건
- 서버에서 확정된 첫 스냅샷(`!metadata.fromCache`)을 **한 번도 받지 못했으면** 숫자를 보여 주지 않는다. 캐시 스냅샷에 대기 중 쓰기 문서만 들어 있으면 "1편" 같은 부분 수가 잠깐 보일 수 있기 때문이다.
- 한 번 서버 확정을 받은 뒤에는 이후 스냅샷(대기 중 쓰기 포함)으로 값을 갱신한다. 저장 직후 스켈레톤이 다시 나타나지 않게 `!hasPendingWrites`는 표시 조건에 쓰지 않는다.
- **시간 제한(8초)**
  - 시작: 구독을 열 때, 월이 바뀌어 재구독할 때(세션 키가 바뀔 때마다 새로 시작). 해제: 첫 서버 확정(`!fromCache`) 스냅샷, 언마운트, 세션 키 변경.
  - 8초가 지나도 서버 확정이 없으면 실패 상태로 넘기지만 **리스너는 끊지 않는다.** 늦게 서버 확정 스냅샷이 오면 실패 상태를 풀고 숫자를 보여 준다(느린 망에서 큰 가계부 월 문서가 내려오는 경우).
  - 오류 콜백이 오면 실패 상태다. SDK 일반 동작상 오류 뒤 리스너는 끝나므로(실측 안 함) `다시 시도`는 구독을 새로 열고 **M을 다시 읽는다**(4.3 비용에 포함).
  - **이미 확정한 값은 같은 세션 키(`uid:monthKey`) 안에서만 유지한다.** 월이 바뀐 뒤 실패하면 지난달 값을 남기지 않는다. `useSnsRecords`는 오류가 나면 `records: []`로 비우므로(`useSnsRecords.ts:47-50`) 이 점은 그 패턴과 다르다.
  - 서버 확정을 받은 뒤 오프라인이 되어 `fromCache` 스냅샷만 오면 실패로 넘기지 않고 마지막 확정 값을 유지한다. "마지막으로 확인한 시각"은 **마지막 `!fromCache` 스냅샷을 받은 시각**이다.
- 구독이 하나뿐이므로 "중복 요청 합치기"(기장 회신)는 따로 필요 없다. 같은 월 구독을 여러 컴포넌트가 열지 않도록 훅을 홈 한 곳에서만 호출한다.

## 4. 데이터 설계

### 4.1 무엇을 세는가
- **편 = 문서 1개**(문서 id 기준). 하루 = 1편이 아니다(`{date}_{type}_{timestamp}` 문서가 있을 수 있다). 형식 수·날짜 수와 다르다.
- 포함 조건: `STATS_MERGE_RECORD_FORMATS.some((format) => recordHasFormat(record, format))`. 포함 조건만 통계·합본과 같다. 단위가 '편(문서)'이라서 통계 화면의 형식별 합계와는 같지 않을 수 있다(한 문서에 형식이 여럿이면 통계는 형식마다 한 번씩 센다).
- `hasSayu`(SAYU 완료)는 합본의 완료 조건이므로 작성 현황 수에는 더하지 않는다.
- **기간**: 서버 쿼리는 월초(`>= YYYY-MM-01`)부터 **다음 달 1일 미만**(`< 다음달-01`)까지 건다. 클라이언트에서 `date <= todayKey`로 한 번 더 거른다(통계의 월초~오늘과 같은 의미). 서버 범위가 그 달에 묶여 있으므로 **월이 바뀌면 재구독이 필요하고**, 같은 달 안에서 날짜만 바뀌면(자정) 재구독 없이 새 날짜 기록이 들어온다.
- **기장 제안과 다른 점과 대가**: 기장은 "'-31' 가짜 월말·미래 날짜 포함 대신 기존 기준(월초~오늘)과 맞추기"를 요구했다. 이 설계는 서버가 **오늘 이후 날짜 문서도 읽는다**(읽기 과금 대상, 클라이언트에서 거름). 기장의 대안(일 변경 시 재구독)은 서버 범위가 통계와 같아지지만 자정마다 M 읽기가 한 번 더 생기고 세션 키가 바뀌어 스켈레톤이 다시 나타난다. 오늘 이후 날짜로 저장되는 문서가 얼마나 있는지는 확인하지 못했다(7절). 어느 쪽을 쓸지는 6절 기장 질문으로 둔다.
- **`todayKey` 갱신**: `now`(`HomePageV2.tsx:555`)는 60초마다 새로 만들어지므로 자정 직후 최대 약 60초, 백그라운드·PWA 재개 때는 더 늦을 수 있다. 구독 스냅샷을 받을 때와 `visibilitychange`에서 `todayKey`를 다시 계산한다. `todayKey`는 필터에만 쓰고 재구독 조건에 넣지 않는다.
- 미래 날짜(오늘 이후)와 지난달 문서는 세지 않는다.

```ts
// 제안(적용 안 함)
const monthKey = todayKey.slice(0, 7);                         // '2026-11' — effect 의존값은 이 문자열만
const start = `${monthKey}-01`;
const nextStart = firstDayOfNextMonth(monthKey);               // '2026-12-01'
// onSnapshot(query(col, where('date', '>=', start), where('date', '<', nextStart), orderBy('date', 'desc')), ...)

const mine = docs
  .filter((r) => typeof r.date === 'string' && r.date.slice(0, 10) <= todayKey)
  .filter((r) => STATS_MERGE_RECORD_FORMATS.some((f) => recordHasFormat(r, f)))   // 비서 기록 제외 포함
  .sort(byDateDescThenUpdatedMsDesc);
const count = mine.length;        // 한 스냅샷의 문서 id는 유일하므로 별도 중복 제거는 필요 없다
const recent = mine.slice(0, 3);
```

**경계와 알려진 한계**
- `date`는 `YYYY-MM-DD` 문자열이라고 가정한다. 상한이 `< 다음달-01`이라 `'2026-11-06T…'`처럼 시각이 붙은 문자열도 사전순으로 범위 안에 들어오고 `slice(0, 10)`으로 센다. **Timestamp 타입 `date`만 범위 쿼리에서 빠진다.** 통계의 `<= 오늘`은 오늘 날짜에 시각이 붙은 문서를 빼므로 오늘 하루에 한해 카드와 통계 결과가 다를 수 있다.
- **비서가 만들었지만 11종으로 저장돼 '편'에 세어지는 문서가 있다**: 예) AI가 만든 HARU미래전망 이야기는 `formats: ['에세이']`로 저장된다(`NovelStoryPage.tsx:64-70`). 통계도 같은 판정이다. 이 문서의 날짜는 `toISOString()`(UTC) 기준이라 한국 시간 0~9시에 저장하면 전날 날짜가 된다.
- 월 범위 쿼리에는 들어오지만 11종이 아니라 세지 않는 문서(성장기록·배뇨일지·SNS 일기 등)도 M에 포함된다(2절 표).
- `formats` 배열이 없는 옛 문서는 세지 않는다. SAYU 목록은 필드 접두어로 보충하므로(`SayuPage.tsx:3257-3259`) **홈의 수와 SAYU 목록 수가 다를 수 있다.** SAYU는 미완료 독서를 목록에서 빼는데(`:3256`) 카드에는 보일 수 있다.
- 이 차이를 사용자 문구로 약속하지 않는다("n편"은 홈 기준이라고 문서에만 남긴다).

### 4.2 최근 3건의 제목·형식·순서
- **형식**: 문서의 `formats` 순서에서 처음 나오는 11종 중 하나. 한글 형식명(예: `일기`)을 화면과 SAYU 이동 상태에 그대로 쓴다.
- **제목**(위에서부터 처음 비어 있지 않은 것, 20자): ① `{prefix}_title` ② 형식별 대표 필드(메모 `memo_title`, 독서사유 `reading_book_title`) ③ `getOriginalBody(record, format)`의 첫 줄 ④ `(내용 없음)`. SAYU 목록의 제목 규칙(`SayuPage.tsx:3250-3296`, AI 제목 포함)을 그대로 복제하지 않는다. 카드용으로 단순하게 만들며 두 곳의 제목이 다를 수 있다. 11종 각각에 ① 필드가 실제로 채워지는지는 구현 때 형식마다 확인한다.
- **순서**: 날짜 내림차순, 같은 날은 `updatedAt` 내림차순, 그것도 없으면 문서 id.
- **`updatedAt`은 타입이 섞여 있다**: ISO 문자열(`firestoreService.ts:466`, `:870`), Timestamp(`serverTimestamp`, `RecordPage.tsx:893`, `SayuPage.tsx`), 쓰기 대기 중에는 `null`. 밀리초 숫자로 정규화하는 함수(문자열→`Date.parse`, Timestamp→`toMillis()`, 그 외→0)를 만들고 시험한다.

### 4.3 조회 방식 세 가지와 비용

M = 이번 달 월 범위 쿼리에 잡히는 문서 수(결과 대화 메모·성장타임라인·가계부 월 문서·보조장부·주식 포함, AI 로그는 제외). 읽기 횟수는 **방문(홈이 마운트될 때)마다 M**이 기본이다. Firestore는 메모리 캐시만 쓰므로 홈을 떠났다 돌아오면 다시 읽을 가능성이 높다.

| 안 | 방식 | 신선도 | 읽기 | 구현 복잡도 | 문제 |
|---|---|---|---|---|---|
| **A** | `getRecordsInRange` 한 번 + 메모리 TTL 5분 + 저장·수정·삭제 후 무효화(기장 권고) | 무효화한 경로만 즉시. 놓친 경로(13개 파일 일부, Functions, 다른 기기)는 최대 5분 | 마운트가 5분 안에 되풀이되면 **B보다 적다**(TTL 안이면 0), 아니면 M | 중 (13개 쓰기 경로에서 무효화 위치 선정) | 가장 흔한 장면(방금 쓰고 홈으로)에서 낡은 값 위험. Functions·다른 기기 쓰기는 클라이언트 무효화로 못 잡음 |
| **B** | `onSnapshot`으로 월 범위 구독(홈이 마운트된 동안) | **항상 최신**. 내 쓰기는 대기 중 쓰기 포함해 즉시 반영, Functions·다른 기기 쓰기도 반영 | 마운트마다 M + 구독 중 바뀐 문서당 1 | 중 (`useSnsRecords`와 같은 패턴) | 홈 재방문이 잦으면 A보다 읽기가 많다. 구독 중 가계부를 저장하면 큰 문서가 다시 내려온다(읽기 1 + 전송량) |
| **C** | `getRecordsInRange` 한 번, 캐시 없음 | 마운트 안에서만 | 마운트마다 M | 하 | 방금 쓴 기록은 다음 마운트에 반영 |

**CC 권고: B로 시작한다.** 쓰기 경로가 13개 파일에 Functions와 다른 기기까지 더해져 있어 A의 무효화로는 완결할 수 없기 때문이다. 읽기는 C와 같은 수준(마운트마다 M)이고 홈에 머무는 동안 바뀐 문서만 추가로 읽는다. 다만 홈 재방문이 잦은 사용자에게는 A가 읽기를 더 줄인다는 점은 인정한다. 이 차이를 구현 후 측정해서 필요하면 4.4의 줄이기로 간다.

> 읽기 비용을 단가로 환산하지 않는다. 하루 읽기 ≈ 활성 사용자 수 × 하루 홈 마운트 횟수 × M(+ 구독 중 변경분) + (카드로 SAYU에 들어갈 때마다 SAYU가 읽는 전체 컬렉션). 예: 1,000명 × 5회 × 30건 = 150,000 읽기/일(SAYU 이동분 제외). 단가와 무료 할당은 Firebase 요금표로 따로 확인해야 하며 이 문서는 확정하지 않는다.

### 4.4 읽기를 줄이는 2단계 (구현 후 측정해서 필요할 때만)
- **서버 쪽에서 형식으로 거르기**: `where('formats', 'array-contains-any', STATS_MERGE_RECORD_FORMATS)` + 날짜 범위. 11개라 `array-contains-any` 한도(30) 안이다. 의미는 `recordHasFormat`의 `formats` 배열 조건과 같다(비서 기록 제외는 클라이언트에서 계속). **복합 인덱스(formats + date)가 필요**하다(`firestore.indexes.json`의 records 인덱스는 `type + createdAt` 하나뿐, 공식 문서 기준 판단이며 실제 쿼리로는 확인하지 못함). 인덱스 배포는 대표님 확인이 필요한 별도 작업으로 다룬다. 단 결과 대화 메모는 `formats: ['메모']`라서 서버 필터를 써도 계속 내려오므로 줄어드는 양은 가계부 월 문서·보조장부·주식·성장타임라인 쪽이다.
- **개수만 서버 집계(`count()`)**: 지금은 쓰지 않는다. 비서 제외 조건이 세 필드 값 비교이고 과거 문서는 그 필드가 없을 수 있어 `!=`·`not-in`을 붙이면 누락될 수 있다. 그리고 결과 대화 메모가 `formats: ['메모']`라서 `count()`는 이 문서를 그대로 세어 과대 집계가 된다. 현재 데이터에서 클라이언트 필터와 같은 값이라고 선언할 수 없다.

### 4.5 구독 수명과 계정·월 변경
- 구독은 **홈이 마운트돼 있고** 로그인했고 온보딩 확인이 끝난 동안 유지한다. '전체 보기'로 바꾸면 카드만 숨기고 구독은 끊지 않는다(`homeViewMode`는 탭 토글 외에 작성칸의 형식 보기 버튼 `onBrowseFormats`, `:1104-1107`로도 바뀌며, 끊으면 'my'로 돌아올 때마다 M을 다시 읽는다). 홈을 떠나면(언마운트) 해제한다.
- **세션 키**: `uid`와 `monthKey`를 함께 쓴다. 상태가 현재 `uid:monthKey`와 일치할 때만 그린다(`useSnsRecords`의 `state.session === session` 패턴 확장). 로그아웃하면 `uid`가 없어져 구독이 해제되고, 계정이 바뀌면 이전 계정 결과를 한 순간도 그리지 않으며, 월이 바뀌어 재구독하기 직전에 지난달 결과가 그려지지 않는다.
- **재구독 조건은 `monthKey` 문자열뿐이다**(서버 범위가 그 달에 묶여 있기 때문). `now`는 1분마다 새 `Date`가 되므로 range 객체를 effect 의존값에 넣으면 1분마다 재구독(M 읽기)이 일어난다. 의존값은 `uid`와 `monthKey` 문자열로 고정한다. 날짜가 바뀌어도(`todayKey`) 재구독하지 않고 클라이언트 필터만 다시 계산한다(4.1).
- 개인정보를 공용 `localStorage`에 남기지 않는다. 메모리 안에서만 다룬다.
- 오프라인: 서버 확정 전에는 숫자를 보여 주지 않고(3.1), 8초 안에 서버 확정이 없으면 실패 상태로 넘긴다.

배포·롤백: 별도 기능 플래그 없이 PR 병합 시 반영한다. 읽기 전용이라 되돌릴 데이터가 없고, 문제가 생기면 PR을 되돌리면 된다. 병합 전 대표님 확인, 병합 후 실서비스 번들 확인과 로그인 상태 화면 확인(대표님)을 한다.

## 6. 결정이 필요한 것

**기장께**
1. 조회 방식: CC는 **B(구독)** 를 권고한다. 쓰기 경로가 13개 파일 + Functions + 다른 기기라 A의 "저장 후 무효화"가 완결되지 않는다는 근거(2절). A를 고집한다면 무효화할 경로 목록과 Functions·다른 기기 쓰기를 어떻게 다룰지 정해 주기 바란다.
2. 구독을 **홈이 마운트된 동안** 유지(탭 전환으로 끊지 않음)하는 수명이 맞는지, 가계부 월 문서가 큰 계정의 마운트당 읽기·전송량을 허용할 수 있는지.
3. 서버 확정 전 숫자를 숨기고 8초 시간 제한 뒤 실패로 넘기는 규칙(3.1)이 맞는지. 8초가 적절한지.
4. 2단계(`formats` 서버 필터 + 복합 인덱스)를 1차에 넣을지 측정 후로 미룰지. CC는 측정 후를 권고한다.
5. 카드 제목 규칙(4.2)이 SAYU 목록 제목과 달라도 되는지.
6. **서버 상한 방식**: CC 설계(서버에서 다음 달 1일 미만까지 읽고 클라이언트에서 오늘까지 거름, 자정 재구독 없음, 오늘 이후 날짜 문서도 읽음)와 기장 제안(월초~오늘로 서버 범위를 통계와 같게 하고 날짜가 바뀔 때 재구독, 자정마다 M 읽기 추가)의 선택. CC는 전자를 권고한다.

**허대표님께**
1. 카드 문구와 위치(3절)가 맞는지. 특히 0건 문구 "이번 달 아직 남긴 기록이 없어요. 오늘의 한 줄부터 시작해 보세요."
2. 결과 대화 메모·성장타임라인·가계부·보조장부·주식을 "n편"에 넣지 않는 기준이 맞는지(통계·합본과 같은 11종).
3. 월 0건일 때 지난달 기록을 보여 주지 않는 범위가 맞는지.
4. 홈이 열릴 때마다 읽기가 늘어나는 것(비용이 늘어나는 변경)을 받아들이고, 구현 후 측정해서 필요하면 2단계로 줄이는 순서에 동의하는지. 인덱스 배포가 필요해지면 별도 승인이 필요하다.
5. 카드로 SAYU에 들어가는 길이 생겨 SAYU의 전체 기록 읽기 빈도가 늘 수 있다는 점.

## 7. 확인하지 못한 것
- 실제 운영 사용자의 월 문서 수 분포(M)와 가계부 월 문서 크기. 구현 후 측정이 필요하다.
- 운영 데이터에 코드와 다른 모양의 옛 문서가 있는지: `date`가 시각 포함 문자열이거나 Timestamp인 문서, `formats`가 없는 문서가 얼마나 있는지.
- `memoryLocalCache`에서 구독을 해제한 뒤 같은 쿼리를 다시 열 때 SDK가 서버에서 전체를 다시 읽는지의 정확한 동작. 기본 가비지 수집이 즉시 방식이라 다시 읽을 가능성이 높아 보이지만 문서 기준 추정이고 실측이 필요하다.
- 복합 인덱스(formats + date)가 필요하다는 판단을 실제 쿼리로 확인하지 못했다.
- 11종 각각에서 `{prefix}_title`이 실제로 채워지는 정도.
- 오늘 이후 날짜로 저장할 수 있는 화면이 있는지, 그런 문서가 운영 데이터에 얼마나 있는지(4.1 대가).
- `onSnapshot` 오류 뒤 리스너 상태와 `다시 시도` 때의 정확한 읽기 과금(SDK 실측 안 함).
- 콘솔에 따로 만든 인덱스 제외 설정이 있는지, 월 범위 쿼리를 실제로 실행했을 때의 결과(기존 `getRecordsInRange`와 같은 모양이라 단일 필드 자동 인덱스로 동작한다고 판단).
- 실서비스 화면 배치와 모바일 폭에서의 모양.
- 타입 검사(프로젝트에 typescript 없음).
