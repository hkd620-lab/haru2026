- 정책 버전: 1.0
- 시행일: 2026-09-24
- 공식 프로젝트: HARU2026
- Slack 워크스페이스: `harulab-hq`

이 문서는 HARU2026 Slack 운영정책의 단일 원본이다.

## 1. 정책 목적

Slack은 의사결정·검증·인수인계를 위한 작업 장부다.

- GitHub: 코드·커밋·PR의 기준
- Firebase 및 운영 환경: 배포·운영 상태의 기준
- Slack: 확정된 상태 변화와 다음 행동을 공유하는 장부

Slack을 코드, 긴 보고서, 전체 로그를 보관하는 장소로 사용하지 않는다.

## 2. 적용 대상

- 기타 HARU2026 작업에 참여하는 AI 또는 사람

## 4. Slack에 기록할 사건

다음처럼 상태가 실제로 변했을 때만 기록한다.

- 새로운 독립 작업 시작
- 범위 또는 결정 변경
- PR 생성
- 중요한 리뷰 지적
- main 병합
- 배포 성공 또는 실패
- 운영 E2E 완료
- 보안 문제나 운영 장애 발견
- 장애 복구
- 작업 최종 완료
- 다음 작업자에게 인수인계
- 허대표님의 결정이 필요한 사안

단순히 AI 대화가 한 번 끝날 때마다 기록하지 않는다.

## 5. 기록하지 않을 내용

- AI 답변 전문
- 긴 지시서나 감사보고서 전문
- 빌드·테스트 로그 전문
- 코드 diff 전문
- 일반적인 진행 중 메시지
- GitHub 자동 알림과 동일한 내용
- 확인되지 않은 추측
- 동일 상태의 반복 보고

## 6. 보안 금지사항

다음 정보는 Slack에 기록하지 않는다.

- 비밀번호
- API 키
- 토큰과 인증정보
- 결제·카드 정보
- 개인정보
- 사용자 첨부파일 내용
- 운영 비밀값과 환경변수 원문

## 7. 기록 방식

독립 작업마다 대표 메시지 또는 대표 스레드 하나를 사용한다. 같은 작업의 진행 상황은 해당 스레드에 답글로 추가한다.

다음 경우에만 새 최상위 메시지를 허용한다.

- 최종 완료
- 감사 판정 변경
- 새로운 장애
- 기존 작업과 독립된 새 작업

메시지는 권장 5~7개 항목, 한글 약 700자 이내로 작성한다.

표준 형식:

```text
[작업명 — 현재 상태]
• 판정:
• 기준 PR·SHA:
• 확인 결과:
• 배포·운영 상태:
• 남은 일:
• 다음 행동:
```

## 8. AI 작업자의 책임

- 새 독립 작업 시작 전, 인수인계 전, 상태가 불확실할 때 관련 Slack 기록을 확인한다.
- 매 대화·매 명령마다 기계적으로 검색하지 않는다.
- 기존 대표 메시지와 스레드가 있는지 확인한 뒤 기록한다.
- 동일 내용이 이미 있으면 중복 게시하지 않는다.
- Slack 접근이 안 되면 게시했다고 표현하지 않는다.
- 이 경우 최종 보고에 게시 가능한 `Slack 기록용 확정 요약`을 제공한다.
- 실행자는 확인된 개발 사실을 보고한다.
- 공식 감사 판정은 시박사(ChatGPT)가 증거를 확인한 후 확정하고, 공식 Slack 기록을 게시한다.

## 9. 완료 판정 기준

다음 증거 사슬을 구분해서 기록한다.

`요구사항 → 코드 → 테스트 → 커밋·PR → main 병합 → 배포 → 운영 E2E → 의도한 결과`

PR 생성만으로 배포 완료라고 기록하지 않는다. 테스트 통과만으로 운영 정상이라고 기록하지 않는다.

## 10. 최종 원칙

Slack에는 다음 네 가지만 남긴다.

- 무엇이 확인되었는가
- 어디까지 완료되었는가
- 무엇이 남았는가
- 누가 다음 행동을 하는가
